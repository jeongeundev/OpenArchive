# Architecture Decision Records

## 철학
심사 포인트(DB 계층 정합성 자동화, 고가용성, 정형+벡터 하이브리드)를 정확히 타격하는 최소 구현. 외부 인프라 의존성을 늘리지 않고 openSQL(PostgreSQL) 표준 기능으로 해결한다. 데모 규모에서 의미 없는 최적화·추상화는 만들지 않는다.

### ADR-001: 트랜잭셔널 아웃박스로 임베딩 잡을 생성한다
> 기동(전달) 방식은 **ADR-009**에서 개정됨 — 폴링이 주 경로, NOTIFY는 최적화.
**결정**: 문서 INSERT/UPDATE 트리거가 같은 트랜잭션 안에서 `embedding_jobs`에 잡을 기록하고 `pg_notify`로 워커를 깨운다. 문서당 pending 잡 1개는 파셜 유니크 인덱스로 강제(코얼레싱). 외부 큐(Redis/Kafka)나 pg_cron 폴링은 쓰지 않는다.
**이유**: "임베딩 갱신이 DB 계층에서 자동 트리거되고 원본-벡터 정합성이 유지된다"는 심사 핵심을 구조적으로 보장한다. 문서만 커밋되고 잡이 유실되는 경우가 불가능하며, NOTIFY는 커밋 시에만 발행되므로 유령 이벤트도 없다. 외부 큐를 쓰면 정합성 책임이 DB 밖으로 나가 과제 취지와 어긋난다.
**트레이드오프**: NOTIFY는 휘발성이라 워커 폴링이 필요하다. 처리량 확장은 외부 큐보다 불리하나 데모 규모에서 무관하다.

**보강 (2026-08-04)**: 조사 결과 **`pg_cron`은 OpenSQL 번들 익스텐션에 포함**되어 있다(`docs/OPENSQL_RESEARCH.md` §1). 즉 "쓸 수 없어서 안 쓰는" 것이 아니라 **"쓸 수 있지만 선택하지 않는"** 것이다. 선택하지 않는 이유: `pg_cron`은 고정 주기 스케줄러라 "문서 변경 시점에 잡이 생성된다"는 이벤트 기반 정합성 서사와 맞지 않고, 트리거+아웃박스가 이미 그 역할을 원자적으로 수행한다. 잡 **생성**은 트리거가, 잡 **소비**는 워커가 담당하며 `pg_cron`이 낄 자리가 없다.

**기동 방식은 ADR-009에서 개정됨** — 폴링이 주 경로, NOTIFY가 최적화.

### ADR-002: 벡터 인덱스는 HNSW
**결정**: `document_chunks.embedding`에 `hnsw (embedding vector_cosine_ops)` 인덱스. IVFFlat은 쓰지 않는다.
**이유**: IVFFlat은 인덱스 생성 시점에 데이터가 있어야 클러스터 품질이 확보된다(빈 테이블에 만들면 recall 붕괴, 데이터 축적 후 재빌드 필요). 이 플랫폼은 "문서가 계속 유입되는" 시나리오라 증분 삽입에 강한 HNSW가 맞다. 코사인 거리는 BGE-M3 정규화 임베딩과 궁합이 맞다.
**트레이드오프**: 빌드 시간·메모리가 IVFFlat보다 크지만 데모 규모(수천~수만 청크)에서 무의미하다.

**보강 (2026-08-04)**: 조사 결과 OpenSQL은 **`pgvector`와 `pgvectorscale`을 함께 번들**한다(`docs/OPENSQL_RESEARCH.md` §1·§8). 즉 선택지는 2개가 아니라 3개였다.

| 후보 | 판단 |
|---|---|
| IVFFlat | 기각 — 인덱스 생성 시점에 데이터가 필요. 증분 유입 시나리오와 불일치 |
| **HNSW** | **채택** — 증분 삽입에 강하고 pgvector 표준 기능이라 이식성이 높다 |
| vectorscale (StreamingDiskANN) | 보류 — 배포판 `METADATA`의 이름은 `pgvectorscale`이지만 실제 확장명은 `vectorscale`이다. HNSW와 비교 측정하지 않은 채 데모 범위에서 채택하지 않았다 |

**리스크 해제 (2026-08-04, 배포판 수령)**: 문서에는 pgvector 버전이 없어 최대 리스크였으나, 실제 배포 패키지의 `METADATA`에서 **`pgvector 0.8.1`**로 확정되었다.

| 요구 버전 | 판정 |
|---|---|
| HNSW 인덱스 (0.5.0+) | ✅ 사용 가능 |
| `hnsw.iterative_scan` (0.8+) | ✅ 사용 가능 — ADR-011의 조건부 적용이 해제된다 |
| `avg(vector)` 집계 (0.5.0+) | ✅ 사용 가능 — ADR-018의 전제 확정 |

**HNSW 채택을 유지한다.** `vectorscale` 0.9.0도 함께 번들되어 있으나(배포판 `METADATA` 표기는 `pgvectorscale`), 과거의 "데모 규모에서 HNSW 대비 우위가 불분명하다"는 판단은 **측정 없는 추정**이었다. #25는 필터 결합 recall에 구조적 답을 가진 유일한 번들 확장으로 계속 검토 대상으로 남겼고 비교 실측 티켓 #31도 만들었지만, 채택하지 않기로 한 뒤 #31을 **범위 밖**으로 닫았다. 데이터 규모가 실제 문제가 되는 시점은 1차 제출 이후이므로 지금 측정 비용을 쓰지 않는다. 같은 문제를 확장 없이 다루는 더 싼 수단인 `hnsw.iterative_scan`도 이미 ADR-011 보강 3에 기록돼 있다. 즉 **재 봤더니 진 것이 아니라, 재지 않고 안 쓰기로 한 것**이다.

~~인덱스 **생성 실행**은 여전히 M0에서 확인한다~~ → **실측 완료 (2026-08-05).** 실 VM에서 `CREATE INDEX ... USING hnsw (v vector_cosine_ops)`가 성공했다. 빌드 옵션 문제도 없다. **이 ADR의 미확인 리스크는 전부 해소됐다.**

### ADR-003: 임베딩은 BGE-M3 단일 프로바이더, 차원 1024 고정
**상태**: 2026-08-04 개정. 구 결정의 `OpenAIProvider` 전환 옵션은 **폐기**한다.

**결정**: 컬럼은 `vector(1024)` 고정. 임베딩 프로바이더는 sentence-transformers **`BAAI/bge-m3` 단일**로 한다. 상용 API 기반 프로바이더는 **구현하지 않는다**. 테스트용 결정론적 `FakeProvider`는 유지한다.

**이유**:
1. **대회 규정상 사용 불가.** 운영규정 [별표2]는 *"외부 API 호출을 통해서만 작동하는 API 전용 모델(Closed API) 사용 불가"*, *"로컬 환경 또는 독립 서버 환경 내 직접 구동 가능 여부 필수"*를 명시한다. 제9조 ②1.다도 같은 취지다. OpenAI `text-embedding-3-small`은 이에 해당한다.
2. **제출 서식에 적을 칸이 없다.** [붙임2] AI 모델 활용 유형은 1(외부 공개 모델 그대로)·2(파인튜닝)·3(자체 개발) 셋뿐이며, 상용 API 전용 모델을 상정하지 않는다.
3. **요청받지 않은 유연성이다.** 프로바이더 전환은 누구도 요구하지 않은 기능이며, 23일 일정에서 구현·테스트 비용만 늘린다.

**BGE-M3 규정 충족 확인**

| 확인 항목 | 판정 |
|---|---|
| 가중치 공개 | ✅ Hugging Face에 승인 절차 없이 공개 |
| 라이선스 | ✅ **MIT** — 오픈웨이트 요건을 넘어선다. 이 프로젝트도 MIT을 채택해 라이선스 계통이 일치한다 |
| 독립 구동 | ✅ `sentence-transformers`로 로컬 구동. 외부 API 호출 없음 |
| 차원 | ✅ 1024 — `vector(1024)` 컬럼과 일치 |
| 최대 시퀀스 | 8192 토큰 — 청크 1,000자 설계에 여유 |

**유지하는 것**: `EmbeddingProvider` Protocol과 `FakeProvider`는 남긴다. Protocol은 확장 지점을 드러내고, `FakeProvider`는 **모델 로딩 없이 파이프라인 전체를 CI 속도로 테스트하는 TDD의 핵심 장치**다. 둘 다 제거 대상이 아니다.

**트레이드오프**: 임베딩 품질을 BGE-M3에 전적으로 의존한다. 한국어 성능이 우수해 데모 요건에는 충분하며, 규정상 대안이 없으므로 실질적 손실이 아니다. 모델(~2GB) 첫 로딩 지연은 예열로 해결한다 (아래 보강).

**보강 (2026-08-22) — 예열의 주체는 "워커"가 아니라 "프로바이더를 만드는 프로세스"다.**

구 결정문의 *"워커 예열"*은 두 가지가 틀렸다. ① 그 예열이 **코드에 없었다** — 문서에만 있었다. ② 예열이 필요한 곳은 워커만이 아니다. `get_provider()` 호출부는 워커·API·MCP 서버 셋이고, **API도 검색 질의를 임베딩한다**. 실제로 워커를 먼저 고치고 API를 놓쳤다가 실사용 검증에서 잡았다.

| 프로세스 | 예열 | 예열이 없을 때 |
|---|---|---|
| 워커 | **한다** | 첫 업로드가 모델 로딩만큼 늦게 처리된다(백그라운드에서 흡수) |
| API | **한다** | **첫 검색 12.52초**(2026-08-21 실측, 예열 후 0.20초). 사용자가 버튼을 누르고 화면 앞에서 기다린다 |
| MCP 서버 | **하지 않는다** | 첫 `search_documents` 호출이 로딩을 떠안는다 — 한계로 받아들인다 |

**결정 1 — API와 워커는 기동 시 `app.embeddings.warm_up()`을 부른다.** 예열 함수를 프로바이더를 만드는 모듈에 둔다. 예열의 필요는 프로바이더를 만드는 데서 따라 나오므로, 둘이 떨어져 있으면 이번처럼 한쪽만 고치게 된다. 호출 위치는 둘 다 **커넥션 풀을 연 뒤**로 맞춘다 — 반대로 하면 DSN 오설정이 모델 로딩 시간만큼 늦게 드러난다.

**결정 2 — MCP 서버는 예열하지 않는다.** stdio 서버라 기동이 모델 로딩만큼 늦어지면 클라이언트의 기동 타임아웃에 걸릴 수 있고, 첫 호출을 기다리는 주체가 사람이 아니라 에이전트다. 얻는 것보다 잃을 것이 크다.

**결정 3 — 예열 실패는 삼키고 계속한다.** 예열은 최적화이지 새 실패 지점이 아니다(ADR-009의 LISTEN과 같은 원칙). 모델을 받을 수 없는 상황이라면 **기존 실패 경로가 더 나은 진단을 준다**: 워커는 `fail_job`이 `last_error`에 이유를 남겨 사용자가 화면에서 보고, API는 검색 요청이 그 자리에서 실패해 원인이 호출자에게 간다. 기동을 막으면 감독자가 되살리는 부팅 루프가 될 뿐이다.

**트레이드오프**: 기동이 모델 로딩만큼 길어진다. 가중치가 캐시된 호스트에서 12~13초이고, **캐시가 없는 첫 기동은 내려받는 시간이 더해진다** — 기동 완료를 기다리는 배포 스크립트의 헬스체크 여유가 그만큼 필요하다(`scripts/deploy_app_host.sh`). 예전에는 첫 검색이 떠안던 비용을 기동으로 옮긴 것이므로, 총량이 준 것이 아니라 **아무도 기다리지 않는 시점으로 옮겼다**.

### ADR-004: 임베딩 워커는 별도 프로세스
**결정**: 워커는 `python -m app.worker`로 API 서버와 분리된 프로세스로 실행한다.
**이유**: 장애 격리(모델 추론이 API 응답성에 영향 없음), 데모 시연성(워커만 죽이고 살리는 시연 가능), 페일오버 시 재연결 로직을 독립적으로 검증 가능.
**트레이드오프**: 실행할 프로세스가 하나 늘어난다. docker compose/README에 명시해 운영 부담을 줄인다.

### ADR-005: 마이그레이션은 번호 붙은 raw SQL + 소형 러너
**결정**: Alembic 등 마이그레이션 도구 대신 `backend/migrations/00N_*.sql` 파일을 순서대로 적용하는 소형 러너를 `db.py`에 둔다.
**이유**: 이 과제의 심사 핵심 산출물이 트리거·파셜 인덱스·HNSW 인덱스 SQL 그 자체다. 읽기 좋은 SQL 파일로 전시하는 것이 심사에 유리하고, 트리거·파셜 인덱스는 어차피 수동 SQL로 작성해야 한다.
**트레이드오프**: 자동 롤백·리비전 그래프가 없다. 그린필드 데모 프로젝트에서는 불필요하다.

### ADR-006: 애플리케이션은 OpenProxy VIP 단일 엔드포인트로 접속한다
**상태**: 2026-08-04 전면 개정. 구 결정(멀티호스트 DSN + 프록시 없음)은 **폐기**한다.

**결정**: 애플리케이션(API·워커)은 OpenProxy의 VRRP VIP에 단일 엔드포인트로 접속한다. `host=node1,node2,node3` 형태의 멀티호스트 DSN과 `target_session_attrs=read-write`는 사용하지 않는다. 백엔드 노드 목록과 역할 추적은 `openproxy.toml`의 `[pools.*.shards.*]`에 선언하고 `use_patroni = true`로 Patroni/etcd에 위임한다. DSN은 환경변수로 주입한다.

**이유**:
- OpenProxy는 OpenSQL의 **구성요소**이며, 공식 기능 목록에 "Primary 변경 감지 후 새 Primary로 재연결"이 포함된다. 멀티호스트 DSN은 이 기능을 애플리케이션에서 중복 구현하는 것이다.
- `PROJECT_CONTEXT.md` 설계 원칙 **"OpenSQL 기능을 애플리케이션에서 중복 구현하지 않는다"**, **"PostgreSQL 일반 사례보다 OpenSQL 공식 문서를 우선한다"**에 정면으로 어긋난다.
- 공식 권장 3노드 구성은 OpenProxy를 2중화하고 그 위에 VIP를 두는 형태다. 노드 직결은 이 구성을 우회한다.

**폐기된 결정의 오류**: 구 ADR-006은 openSQL을 "PostgreSQL + Patroni" 정도로 가정하고 작성됐다. 실제 OpenSQL은 OpenProxy를 포함한 4컴포넌트 제품이며, **프록시는 제거 대상이 아니라 제품의 일부다**. 조사 근거는 `docs/OPENSQL_RESEARCH.md` §1·§2·§4.

**실측 정정 (2026-08-09, #27)**

이 설치의 `openproxy.toml`에는 `use_patroni`도 `[general.etcd]`도 없고, `servers`에는 primary 하나가 하드코딩돼 있다. 즉 현재 OpenProxy는 **정적 서버 목록을 가진 순수 커넥션 풀러**다. 따라서 위 결정이 전제한 **"새 프라이머리 발견·재연결은 OpenProxy가 수행한다"는 기능은 이 설치에 구성되어 있지 않다.** 노드가 하나라 발견할 대상도 없으므로 제품 기능의 결함이 아니라 구성의 문제이며, HA 구성으로 전환할 때 Patroni·etcd 연동을 함께 설정해야 한다.

풀러로서의 동작은 별도로 실측됐다. 백엔드 축출은 헬스체크 타이머가 아니라 요청 실패에 이끌려 **278 ms**에 일어났고, `pool_mode = "session"`이라 클라이언트 연결도 함께 끊겨 애플리케이션이 `OperationalError`를 받았다. 읽기 요청은 이 예외를 ADR-023의 1회 재시도 경로로 처리한다. 재연결 역시 다음 클라이언트 요청에 이끌려 일어난다.

**트레이드오프**:
- OpenProxy 경유로 세션 상태 제약이 생긴다 (ADR-009).
- 로컬에서 OpenProxy를 재현할 수 없다 (공식 Docker 배포 없음 — ADR-007). DSN을 환경변수로 추상화해 로컬↔클러스터 전환만 가능하게 한다.
- 연결 재수립 순간의 요청은 여전히 1회 재시도가 필요하다.
- Single에서 실측된 것은 failover가 아니라 **PostgreSQL 프로세스 재기동**이다. DB 경계 5.85초(1표본), 앱이 OpenProxy 경유로 쿼리에 다시 성공하는 **서비스 경계는 13.0~22.4초**(5표본)다. 리더 선출·승격 소요는 측정하지 못했다 (ADR-020).

### ADR-007: 일상 개발은 pgvector 단일 컨테이너, OpenSQL은 별도 VM
**상태**: 2026-08-04 근거 교체 → **같은 날 배포판 수령으로 재개정**. 결론은 유지하되 이미지 태그가 `pg16` → **`pg17`**로 바뀐다.
**2026-08-10 재확인**: ADR-026이 로컬 확장 의존을 다시 점검했으며, 기본 pgvector 컨테이너와 OpenSQL VM을 나누는 이 결정은 그대로 유지된다.

**결정**: 일상 개발·테스트는 **`pgvector/pgvector:pg17`** 단일 컨테이너. OpenSQL 자체는 Rocky Linux 9.7 x86-64 가상머신에 single 모드로 설치하고, OpenSQL 고유 동작을 확인할 때만 사용한다.

**이유 (2차 개정)**: 배포판 수령으로 상황이 두 가지 바뀌었다.

1. **PostgreSQL이 17.8이다.** 문서 조사 단계에서는 16.8/14.13으로 추정해 로컬 이미지를 `pg16`으로 고정했으나, 실제 배포판은 후보에 없던 **17.8**이었다(`OPENSQL_RESEARCH.md` §0). 로컬 컨테이너의 메이저 버전을 맞춘다.
2. **설치 바이너리를 받아 VM에 직접 설치할 수 있게 됐다.** "로컬에서 OpenSQL을 돌릴 수단이 전혀 없다"는 상태는 해소됐다. Docker 이미지는 여전히 없지만(`opensql3-docker`는 빈 껍데기), VM 설치라는 경로가 생겼다.

**그래도 일상 개발을 컨테이너로 하는 이유**: OpenSQL은 **x86-64 + Rocky Linux 9.7 전용**이라 Apple Silicon에서는 QEMU 전체 에뮬레이션이 필요하고, 네이티브의 1/10~1/20 속도다. 매 테스트를 그 위에서 돌릴 수 없다. 구축 절차는 `docs/SETUP_OPENSQL.md`.

**DB만 VM에 두는 구성**: 임베딩 모델(BGE-M3, 2GB) 추론을 에뮬레이션 안에서 하면 문서 하나에 수 분이 걸린다. x86-64가 강제되는 것은 OpenSQL뿐이므로 **그것만 VM에 넣고 API·워커·프론트는 맥 네이티브로** 둔다. `ADR-006`이 DSN을 환경변수로만 주입하도록 정해두어 코드 변경이 없다.

단일 컨테이너로 커버되는 것과 안 되는 것을 명확히 구분한다:

| 영역 | 로컬 검증 | 비고 |
|---|---|---|
| 트리거·아웃박스·파셜 유니크 인덱스·CASCADE | ✅ 가능 | PG17 표준 |
| `FOR UPDATE SKIP LOCKED` 워커 경쟁 | ✅ 가능 | PG17 표준 |
| 청킹·임베딩·검색 SQL | ✅ 가능 | |
| DB 직결 `LISTEN`/`NOTIFY` | ✅ 가능 | OpenProxy 경유는 불가 |
| **OpenProxy 경유 세션 상태 제약** | ❌ 불가 | ADR-009 검증 대상 |
| **읽기/쓰기 분리·복제 지연** | ❌ 불가 | ADR-010 검증 대상 |
| **Patroni 리더 선출·프로모션** | ❌ 불가 | |

**트레이드오프**: 위 ❌ 3개가 M0의 최우선 검증 항목이 된다(`docs/OPENSQL_RESEARCH.md` §12). 이 갭을 숨기지 않고 문서에 명시하는 것이, 로컬에서 대충 흉내 내고 "검증했다"고 주장하는 것보다 정직하고 심사에도 유리하다.

**PG 메이저 버전 리스크 — 해소됨**: 문서에 16.8과 14.13이 함께 언급되어 둘 중 하나로 추정했으나, 배포판 `METADATA`에서 **17.8**로 확정되었다. 로컬 이미지를 `pgvector/pgvector:pg17`로 고정한다. **추정한 두 후보가 모두 틀렸다는 점이 이 항목을 "미확인"으로 표기해둔 값어치를 보여준다.**

### ADR-008: MCP 서버는 stdio + 검색 서비스 직접 import
**결정**: `backend/mcp_server/server.py` 단일 파일, FastMCP + stdio transport. `app/services/search.py` 등을 직접 import해 재사용하고 HTTP API를 경유하지 않는다. 툴은 `search_documents`, `get_document`, `list_documents` 3개.
**이유**: 검색 로직(하이브리드 SQL)이 한 곳에만 존재해야 REST와 MCP의 결과가 항상 일치한다. HTTP 경유는 계층 중복과 장애 지점만 늘린다. stdio는 Claude Desktop/Code 연동이 가장 단순하다.
**트레이드오프**: MCP 서버가 백엔드 코드베이스·DB 접속에 직접 의존한다. 데모 환경에서는 문제가 없고, 원격 분리가 필요해지면 그때 HTTP transport로 바꾼다.

### ADR-009: 파이프라인 기동은 폴링이 주 경로, NOTIFY는 최적화
**상태**: 2026-08-04 신규. ADR-001의 기동 방식 부분을 개정한다.

**결정**: 워커는 **주기 폴링(기본 5초)을 주 경로**로 삼아 `embedding_jobs`를 드레인한다. `LISTEN`/`NOTIFY`는 **지연 단축을 위한 최적화**로 취급하며, 동작하지 않아도 파이프라인이 정상 기동해야 한다. 트리거의 `pg_notify` 발행은 유지한다.

**이유**: OpenProxy 경유 시 `LISTEN`의 동작이 보장되지 않는다. 근거 세 가지 (`docs/OPENSQL_RESEARCH.md` §5·§7):
1. `pool_mode` 기본값이 `transaction` — 세션 상태가 유지되지 않는 모드다. `LISTEN`은 세션 상태다.
2. `server_lifetime` 기본 1시간 — 서버 커넥션이 주기적으로 강제 종료된다.
3. `idle_timeout` 기본 10분 — `LISTEN` 연결은 본질적으로 유휴 상태다.

무엇보다 **OpenSQL 공식 문서 전체에 `LISTEN`/`NOTIFY` 언급이 단 한 줄도 없다.** 지원 여부가 문서로 확인되지 않은 메커니즘을 주 경로로 두는 것은 위험하다.

**트레이드오프**: 최대 5초의 임베딩 시작 지연이 생긴다. 데모 규모에서 수용 가능하며, NOTIFY가 동작하는 환경에서는 즉시 기동한다. "DB가 워커를 깨운다"는 서사는 약해지지만, **"DB가 잡을 생성하고 정합성을 보장한다"**는 핵심 주장은 그대로다 — 트랜잭셔널 아웃박스·코얼레싱·CASCADE는 모두 DB 계층에 남는다.

**검증**: M0에서 OpenProxy 경유 `LISTEN`/`NOTIFY` 동작을 실측한다. 동작하면 폴링 주기를 늘려 부하를 낮춘다.

---

**실측 결과 (2026-08-05) — 동작한다. 그러나 결정은 유지한다.**

실 VM에서 확인했다. 다른 세션의 `NOTIFY`를 OpenProxy(6432) 경유 LISTEN 세션이 **페이로드까지 수신**했다.

```
opensql=> LISTEN ch1;
opensql=> SELECT 1;
"ch1" 비동기 통지를 받음, 부가정보: "hello from another session", 보낸 프로세스: 62653
```

**위 근거 1번이 틀렸다.** `pool_mode` 기본값이 `transaction`이라고 했으나, 설치기가 생성한 `openproxy.toml`은 **`pool_mode = "session"`**이다(`OPENSQL_RESEARCH.md` §5-1). `session` 모드는 서버 커넥션을 클라이언트 접속 동안 전용으로 유지하므로 세션 상태가 보존된다.

**그럼에도 폴링을 주 경로로 유지하는 이유:**

1. **연결이 끊긴 구간의 알림은 유실된다.** `NOTIFY`는 커밋 시 발행되며, 그 순간 수신자가 없으면 사라진다. 재연결까지의 공백에 생성된 잡은 폴링만이 회수한다
2. ~~**근거 2·3번은 그대로다.** `server_lifetime`(1시간)·`idle_timeout`(10분)은 여전히 유효하며, LISTEN 연결은 본질적으로 유휴 상태다~~ → **재실측으로 반증됨. 아래 재개정의 부수 확인 참조** (결론에는 영향 없다)
3. **이 ADR의 핵심 주장이 "기동 방식은 정합성의 일부가 아니다"이다.** 아웃박스와 `SKIP LOCKED`가 유실·중복을 막으므로, LISTEN 동작 여부와 무관하게 정합성 서사는 성립한다. 동작한다고 해서 이 구조를 뒤집을 이유가 없다

~~**바뀌는 것 — 폴링 주기를 5초 → 30초로 늘릴 수 있다.**~~ → **철회됨. 아래 재개정 참조.**

---

**재개정 (2026-08-05, M1 이후 재실측) — 폴링 주기 상향을 철회한다. 결정은 그대로다.**

위 상향의 선행 조건(유휴 LISTEN 확인)을 검증하다가 **1차 실측의 결론 자체가 틀렸음**을 발견했다.

**OpenProxy 경유로는 유휴 세션에 비동기 알림이 전달되지 않는다** (`OPENSQL_RESEARCH.md` §7-3).
알림이 유실되지는 않지만 **클라이언트가 다음에 쿼리를 보낼 때까지 지연**된다. 노드 직결(5432)에서는
즉시 도착한다.

1차 실측이 "동작한다"로 보인 이유는 **psql 대화형 세션으로 측정했기 때문**이다. 사용자가 계속
입력을 보내므로 프록시가 알림을 쥐고 있어도 즉시 도착하는 것처럼 보인다. 재현 절차에 적혀 있던
`SELECT 1; -- 알림은 다음 쿼리 실행 시 표시된다`가 바로 그 트리거였는데, 이를 psql의 출력 관례로
해석했다.

**따라서 폴링 주기는 5초를 유지한다.** LISTEN이 유휴 워커를 깨우지 못하므로 30초 폴링은 그대로
30초 지연이다.

**이 ADR의 결정은 바뀌지 않는다 — 오히려 강화된다.** "기동 방식은 정합성의 일부가 아니다"라는
설계가 정확히 이 상황을 막았다. `LISTEN`이 무효인 환경에서도 파이프라인이 정상 동작하며,
**`worker.py`는 코드 변경이 필요 없다.** `_listen_for_jobs`도 제거하지 않는다 — 노드 직결
환경(로컬 컨테이너·개발)에서는 정상 동작하고, 실패해도 무해하도록 이미 설계되어 있다.

> **부수 확인**: 유휴 세션 자체는 70분간 멀쩡했다. `idle_timeout`(10분)은 무활동 15분 구간을
> 끊지 않았고 `server_lifetime`(60분)도 백엔드를 교체하지 않았다. 근거 2·3번(연결이 주기적으로
> 끊긴다)은 **실측으로 반증됐다.** 다만 근거 1번의 오류와 달리 이것은 결론에 영향이 없다 —
> 애초에 알림이 도착하지 않기 때문이다.
>
> ⚠️ 관측은 체크포인트마다 쿼리를 보냈으므로 **무활동 최대 구간은 15분**이다. "70분 내내 건드리지
> 않은 연결"은 미검증이다.

### ADR-010: 검색 쿼리는 명시적 트랜잭션으로 Primary를 강제한다
**상태**: 2026-08-04 신규.

**결정**: 하이브리드 검색 쿼리를 **plain `BEGIN` … `COMMIT`** 블록 안에서 실행한다. `BEGIN READ ONLY` / `START TRANSACTION READ ONLY`는 **사용하지 않는다**.

**이유**: OpenProxy는 `query_parser_read_write_splitting` 활성 시 **명시적 트랜잭션 밖의 단순 `SELECT`를 Replica로 라우팅**한다. 복제 지연 인식도, read-your-writes 보장도 문서에 없다. 워커가 Primary에 청크를 커밋한 직후 검색하면 **방금 임베딩된 청크가 결과에서 누락될 수 있다.** 이는 기업이 제시한 핵심 문제인 "원본 데이터와 벡터 데이터의 정합성"과 정면으로 충돌한다.

**함정**: OpenProxy 1.1.3부터 `BEGIN READ ONLY`와 `START TRANSACTION READ ONLY`는 **의도적으로 Replica로 라우팅**된다. "읽기 전용이니 read only로 선언하는 게 맞다"는 직관을 따르면 정확히 반대 결과가 나온다. **반드시 plain `BEGIN`을 쓴다.**

**트레이드오프**: 읽기 부하 분산을 포기한다. 데모 규모에서는 무의미한 손실이며, 정합성이 이 과제의 심사 핵심이므로 정합성을 택한다. 읽기 확장이 필요해지면 그때 "재임베딩 중이 아닌 문서만 Replica 허용" 같은 정교한 정책을 검토한다.

**대안 검토**: 검색 전용 pool을 `query_parser_read_write_splitting = false`로 두는 방법도 있으나, 이는 **제공받는 클러스터의 설정 권한에 의존**한다. 애플리케이션 쪽에서 닫을 수 있는 트랜잭션 방식이 더 견고하다.

---

**근거 교체 (2026-08-04, 배포판 수령 + Single 구성 지시)**

**결정은 그대로 유지하되 근거가 바뀐다.** 사무국이 Single 구성을 지시했고, 배포판의 `openproxy.standalone.template.toml`(single 전용)을 확인한 결과:

```toml
[pools.FILL_ME]
pool_mode = "transaction"        # ← 명시되어 있다
auth_type = "scram-sha-256"

[pools.FILL_ME.shards.0]
servers = [
    ["FILL_ME", 5432, "primary"],    # primary 1개뿐
    # ["FILL_ME", 5432, "replica"],  # 주석 처리
]
```

`query_parser_enabled`·`query_parser_read_write_splitting`·`primary_reads_enabled`가 **아예 없다.** 기본값이 `false`이고 라우팅 대상 replica도 없다. 따라서 **원래 근거("트랜잭션 밖 SELECT가 Replica로 가서 복제 지연으로 누락")는 Single 구성에서 성립하지 않는다.**

**그럼에도 명시적 트랜잭션을 유지하는 이유 두 가지:**

1. **`SET LOCAL`의 필요조건이다.** 템플릿에 `pool_mode = "transaction"`이 명시되어 있고, 이 모드에서 트랜잭션 밖의 `SET`은 의도대로 동작하지 않는다(`OPENSQL_RESEARCH.md` §5). ADR-011의 `SET LOCAL hnsw.ef_search`를 안전하게 쓰려면 명시적 트랜잭션이 **반드시 필요하다**. 이제 이것이 1순위 근거다.
2. **HA 전환 대비.** 배포판에 `scripts/finalize_single_to_ha.sh`가 있다. 나중에 노드를 늘려 HA로 전환하면 원래 근거가 그대로 되살아난다. 지금 감싸두면 전환 시 검색 코드를 고칠 필요가 없다.

즉 근거가 **"Replica 라우팅 방지"에서 "세션 상태 보장 + HA 전환 대비"**로 이동했다. 트레이드오프였던 "읽기 부하 분산 포기"는 Single 구성에서 애초에 분산할 대상이 없으므로 **손실이 0이 되었다.**

**실측 확인 (2026-08-05)**: 위 근거 교체가 옳았다. 설치기가 실제로 생성한 `openproxy.toml`은 다음과 같다.

```toml
[pools.opensql]
pool_mode = "session"
default_role = "primary"
query_parser_enabled = false      # 읽기/쓰기 분리 꺼짐
[pools.opensql.shards.0]
servers = [["192.168.64.4", 5432, "primary"]]     # primary 하나뿐
```

`query_parser_enabled = false`이고 백엔드가 primary 하나라 **Replica 라우팅이 일어날 수 없다** — 원래 근거는 이 환경에서 성립하지 않는다.

다만 **`pool_mode`는 예상했던 `transaction`이 아니라 `session`이었다.** 이는 새 1순위 근거("`SET LOCAL`을 쓰려면 명시적 트랜잭션이 필요하다")를 약화시킨다 — `session` 모드에서는 트랜잭션 밖 `SET`도 세션에 남기 때문이다.

**그래도 결정을 유지한다.** `SET LOCAL`은 트랜잭션 종료 시 **자동 복원**되지만, `session` 모드에서 그냥 `SET`을 쓰면 그 값이 커넥션에 계속 남아 **다음 요청에 새어 나간다.** 풀에서 빌린 커넥션의 `hnsw.ef_search`가 이전 요청 값이면 검색 품질이 요청마다 달라진다. 명시적 트랜잭션 + `SET LOCAL`이 이 오염을 구조적으로 막는다. 근거의 표현을 "세션 상태 보장"에서 **"세션 오염 방지"**로 다듬는다.

### ADR-011: 검색 recall은 `ef_search`로, 문서 중복은 `DISTINCT ON`으로 해결한다
**상태**: 2026-08-04 신규.

**결정**: 하이브리드 검색 쿼리에서
1. 트랜잭션 안에 `SET LOCAL hnsw.ef_search = 200`을 설정한다 (기본 40).
2. 후보를 `LIMIT k * 5`로 넉넉히 뽑은 뒤 `DISTINCT ON (document_id)`으로 **문서당 최고 점수 청크 1건**만 남기고, 거리순으로 최종 `LIMIT k`를 적용한다.

**문제 1 — post-filter recall**: HNSW 인덱스는 `document_chunks`에 있는데 필터(태그·유형·권한)는 JOIN 상대인 `documents`에 있다. 벡터 인덱스가 후보를 뽑은 **뒤에** 필터가 적용되므로, 태그 필터가 조금만 좁아도 `LIMIT k`를 채우지 못한다. 하필 태그 필터는 "정형+벡터 하이브리드"를 시연하는 핵심 시나리오라 데모에서 바로 드러난다.

**문제 2 — 문서 단위 중복**: 청크 단위로 정렬하면 긴 문서 하나가 상위 k를 도배할 수 있다. 사용자가 원하는 것은 **문서 목록**이며 각 문서의 가장 잘 맞는 발췌다.

**이유**:
- `ef_search`는 **pgvector 버전에 무관하게** 동작한다. ~~`hnsw.iterative_scan`은 0.8+ 전용인데 OpenSQL의 pgvector 버전이 미확인이므로 의존할 수 없다.~~ → **아래 보강 3 참조: 0.8.1로 확인되어 사용 가능해졌다.**
- `SET LOCAL`은 트랜잭션 종료 시 자동 복원된다. ADR-010이 이미 검색을 명시적 트랜잭션으로 감쌌으므로 **추가 비용이 없다**.
- 후보를 `k*5`로 과다 조회한 뒤 중복 제거하면 **HNSW 인덱스 정렬을 그대로 활용**할 수 있다. 전체 청크에 `DISTINCT ON`을 직접 걸면 인덱스를 못 쓰고 풀스캔이 된다.

**트레이드오프**:
- `ef_search`를 키우면 검색 지연이 늘어난다. 데모 규모(수천~수만 청크)에서는 무시할 수준이다.
- `k*5` 과다 조회는 휴리스틱이다. 극단적으로 편향된 데이터(한 문서가 전체 청크의 대부분)에서는 여전히 k를 못 채울 수 있다. 실측 후 배수를 조정한다.
- 문서당 1건만 반환하므로 "같은 문서의 여러 구절"을 보고 싶은 요구는 충족하지 못한다. 상세 화면에서 청크 목록을 제공하므로 수용 가능하다.

**대안 (에스컬레이션 경로)**: 실측 결과 recall이 여전히 부족하면 `documents`의 필터 컬럼(`tags`, `content_type`, `visibility`, `owner_id`)을 `document_chunks`에 **비정규화**하고 트리거로 동기화한다. 필터와 벡터 인덱스가 같은 테이블에 있으면 pgvector의 필터링이 설계대로 동작한다. 동기화를 트리거가 맡으므로 DB 계층 자동화 서사와도 맞는다. 다만 쓰기 증폭과 스키마 복잡도가 늘어나므로 **필요가 입증되기 전에는 하지 않는다**.

**보강 1 (2026-08-04) — 이 함정은 검색 쿼리만의 것이 아니다.**

위 세 번째 근거("전체 청크에 `DISTINCT ON`을 직접 걸면 인덱스를 못 쓰고 풀스캔이 된다")는 **문서당 1건으로 줄이는 모든 벡터 쿼리에 적용된다.** 관련 문서(ADR-018)와 태그 추천(ADR-019)이 같은 구조를 가지므로, 두 ADR에도 같은 3단계 순서를 명시했다.

```
1) 벡터 정렬 + LIMIT 으로 후보 확보   ← 여기서만 인덱스를 탄다
2) DISTINCT ON (document_id) 로 문서당 1건
3) 거리순 재정렬 + 최종 LIMIT
```

2)와 3)을 합쳐 `DISTINCT ON ... ORDER BY document_id, dist LIMIT k`로 쓰면 **유사도가 아니라 `document_id`(UUID) 순으로 잘린다.** UUID 순서는 사실상 무작위이므로 결과가 조용히 망가진다. 초안 설계에서 실제로 이 실수를 했고, 그래서 근거를 여기 남긴다.

**보강 2 (2026-08-04) — RRF 도입 시 순서 조정 (조건부)**

ADR-016(키워드+벡터 RRF)을 착수하는 경우, `DISTINCT ON (document_id)`을 **RRF 융합 이후**로 옮긴다. 두 랭킹을 합치기 전에 문서당 1건으로 줄이면, 한쪽 랭킹에서만 상위인 청크가 융합 대상에서 사라져 RRF의 의미가 없어지기 때문이다. `ef_search = 200`과 `k*5` 과다 조회는 그대로 유지한다.

**ADR-016이 조건부 채택이므로 이 순서 조정도 조건부다.** RRF를 착수하지 않으면 현재 순서를 그대로 쓴다. 이 ADR은 폐기되지 않는다.

**보강 3 (2026-08-04) — `hnsw.iterative_scan`을 쓸 수 있게 됐다**

배포판 `METADATA`에서 **pgvector 0.8.1**이 확인되었다. `hnsw.iterative_scan`은 0.8+ 전용이라 "버전 미확인이므로 의존할 수 없다"고 했으나, 이제 사용 가능하다.

```sql
SET LOCAL hnsw.iterative_scan = relaxed_order;   -- pgvector 0.8+
SET LOCAL hnsw.ef_search = 200;
```

`iterative_scan`은 이 ADR이 다루는 **post-filter recall 문제의 정공법**이다. `ef_search`를 키우는 것은 후보 풀을 넓혀 확률을 높이는 완화책이지만, `iterative_scan`은 필터를 통과한 결과가 `LIMIT`에 못 미치면 **인덱스를 추가로 더 훑는다.**

**다만 지금 결정을 바꾸지는 않는다.**
- `ef_search = 200` + `k*5` 과다 조회는 그대로 둔다. 두 방법은 배타적이지 않고 함께 쓸 수 있다
- `relaxed_order`는 정확한 거리순 정렬을 보장하지 않는다. RRF(ADR-016)를 도입하면 순위가 융합 입력이 되므로 영향을 검토해야 한다
- **실측 없이 켜지 않는다.** M0에서 필터 결합 검색의 recall을 측정한 뒤, 부족하면 그때 켜고 결과를 이 ADR에 기록한다

즉 **선택지가 하나 늘었고 에스컬레이션 경로가 짧아졌다.** 비정규화(아래 대안)까지 가기 전에 시도할 수단이 생겼다.

**보강 4 (2026-08-05, 실 VM 실측; 2026-08-06 근거 교체) — `ef_search`에는 양쪽에 벽이 있다**

`SET LOCAL hnsw.ef_search = 200`이 취향이 아니라 **필수**임을, 그리고 무작정 키워서도 안 됨을
실 클러스터에서 확인했다. 현재 결정의 주 근거는 실제 BGE-M3 벡터 6000행에서 `random_page_cost=1.1`,
후보 `LIMIT 100`으로 측정한 `OPENSQL_RESEARCH.md` §12-22다.

| `ef_search` | 실제 후보 | 스캔 | 시간 |
|---|---|---|---|
| 미설정(기본 40) | **21행** | HNSW | 13.6ms |
| 40 | **21행** | HNSW | 10.7ms |
| 100 | **60행** | HNSW | 19.8ms |
| **200** | **100행** | HNSW | 29.1ms |
| 400 | 100행 | **Seq Scan** | 619.4ms |
| 600 | 100행 | **Seq Scan** | 620.5ms |
| 1000 | 100행 | **Seq Scan** | 595.8ms |

**등호에서도 모자란다.** 별도 측정에서 `ef_search=200`에 `LIMIT 200`을 요청하니 **193행**만
돌아왔다. 그래서 지켜야 할 불변식은 `LIMIT ≤ ef_search`가 아니라 **`MAX_K * 배수 < EF_SEARCH`**다.
M4 코드가 이를 지키는 방식은 호출부마다 다르다:

- **검색**(`app/services/search.py`)은 `CANDIDATE_MULTIPLIER = 5` 상수다. `20 * 5 = 100`으로
  200에서 여유가 크고, 배수를 손댈 일이 없어 상수가 읽기 쉽다.
- **관련 문서·태그 추천**(`app/services/related.py`)은 배수가 커서 벽에 가깝다. 그래서
  `CANDIDATE_MULTIPLIER = (EF_SEARCH - 1) // MAX_K`로 예산에서 역산한다.

어느 쪽이든 상수를 눈으로 지키지 않는다 — `test_search.py`와 `test_related.py`가 세 호출부의
불변식을 각각 단언하므로, `EF_SEARCH`나 `MAX_K`를 한쪽만 움직이면 테스트가 깨진다.

아래 표는 최초 근거였던 §12-14 측정 기록이다. **`random_page_cost=4` 체제·합성 벡터·`LIMIT 50`**
조건이므로, 현재 `rpc=1.1` 코드의 상한 근거로는 쓰지 않는다.

| `ef_search` | 스캔 | 시간 | 반환행 |
|---|---|---|---|
| **40 (기본)** | HNSW | 74ms | **40** ← 요청은 50인데 40행 |
| 60 / 100 / 200 / 400 | HNSW | 83 / 99 / 124 / 168ms | 50 |
| **600** | **Seq Scan** | **1177ms** | 50 |

**아래쪽 벽 — `ef_search`가 작으면 에러 없이 행이 모자란다.** 기본값 40에서는 후보 100개 요청에
21행, 100에서는 60행만 돌아왔다. 예외도 경고도 없으며, 위 등호 함정 때문에 단순히
`LIMIT ≤ ef_search`로 검사해서도 안 된다. 후보 예산은 항상 최소 1의 여유를 두고 역산한다.

**위쪽 벽 — 너무 키우면 플래너가 인덱스를 통째로 버린다.** 현재 코드와 같은 `rpc=1.1` 체제에서는
벽이 **200~400 사이**에 있고, 400부터 Seq Scan으로 떨어졌다. 이 임계는 테이블 크기에 따라
움직이므로 고정 상수로 외울 수 없다.

**결정은 그대로 `200`이다.** 후보 100개를 모두 반환하면서 HNSW를 유지한 값이고, 400은 이미 Seq
Scan으로 떨어진다. 즉 측정된 아래·위 벽 사이에서 유일하게 성립한다. 과다 조회량은 200에 닿지
않도록 예산에서 역산하며, `ef_search` 자체를 올리려면 규모마다 위쪽 벽을 다시 측정해야 한다.

> `hnsw.iterative_scan`(보강 3)은 이 아래쪽 벽을 구조적으로 없애는 수단이다. 필요가 입증되면
> 배수를 키우는 대신 그쪽을 먼저 검토한다.

**보강 5 (2026-08-05, 재실측) — `SET LOCAL random_page_cost = 1.1`을 함께 건다**

`ef_search`를 아무리 맞춰도 **플래너가 인덱스를 고르지 않으면 소용이 없다.** 데모 규모에서
실제로 그런 상태였다.

| 쿼리 (청크 6000행, `LIMIT 100`, 강제 없음) | `rpc = 4` (VM 기본) | `rpc = 1.1` |
|---|---|---|
| 관련 문서 — 필터를 `cand` 안에 | Seq Scan **624ms** | **HNSW 33.8ms** |
| 관련 문서 — 필터를 밖으로 | Seq Scan **785ms** | **HNSW 35.5ms** |
| 하이브리드 검색 (태그 필터) | Seq Scan 234ms | Seq Scan 232ms |

**왜 기본값이 안 맞나.** 힙은 3MB(약 384페이지)라 순차 스캔이 싸다. HNSW 인덱스는 47MB이고
그래프 탐색은 **전부 임의 접근**이다. `random_page_cost = 4`는 회전 디스크 기본값인데 이 VM은
맥 SSD 위에 있다. 임의 접근을 4배로 계산하니 "작은 테이블을 통째로 읽는 편이 싸다"가 나온다.
**쿼리 형태는 이 결과를 바꾸지 못한다** — 어떤 형태든 `rpc=4`에서는 Seq Scan이었다.

**전역 설정이 아니라 `SET LOCAL`로 건다.** ADR-010의 명시적 트랜잭션 안에서 `ef_search`와 나란히
둔다. 이유는 셋이다. ① 벡터 조회에만 필요하고 다른 쿼리의 계획을 바꿀 이유가 없다. ② OpenProxy가
`RESET ALL`만 하고 `DISCARD ALL`은 하지 않으므로(§5-2) 세션 GUC에 의존하지 않는 편이 안전하다.
③ 값의 근거가 쿼리 옆에 남는다.

**태그 필터가 붙은 검색은 여전히 Seq Scan이며, 그대로 둔다.** 필터가 선택적일수록(500문서 중
84개) 먼저 좁히고 정렬하는 편이 실제로 싸다 — 플래너가 옳다. 6000행에서 232ms이고, 이 경로가
느려지면 그때 재검토한다.

> **규모가 커지면 완화된다.** 순차 스캔 비용은 행 수에 선형이고 HNSW는 거의 로그다. 어느 지점부터는
> `rpc=4`에서도 플래너가 인덱스를 고른다. `rpc` 조정은 **그 지점을 앞당기는 것**이며, 데모 규모에서
> 필요한 이유가 그것이다. 교차점 자체는 측정하지 않았다.

**보강 6 (2026-08-27, 실 OpenSQL 재실측) — 그래프 순회 행에서는 청크를 고르지 않는다**

ADR-029의 관계 순회(`WITH RECURSIVE`, 깊이 2)는 순회로 도달한 행마다 `JOIN LATERAL (… ORDER BY
embedding <=> 질의 LIMIT 1)`로 대상 문서의 발췌 청크를 골라 나르고 있었다. 시연 코퍼스(문서 76건 ·
청크 415 · `document_edges` 1,704 + 위키링크, 문서당 관계 약 23개)를 실 OpenSQL VM에 넣자 검색이
**질의당 SQL 3.5~11.6초**였다. `EXPLAIN ANALYZE`: 재귀 합집합 13,330행, 그 행마다 도는 청크 정렬
**13,332회** × 0.26ms. 로컬 컨테이너는 같은 서브쿼리가 0.004ms라(65배 차이) 8/26 리허설 전까지
보이지 않았고, 8/22의 "0.20초"는 문서 1건짜리 DB에서 잰 값이었다. `k`를 3으로 줄여도 5초 — 비용은
k가 아니라 **깊이 2 × 문서당 edge 수**에서 온다.

**결정: 순회는 문서 id·거리·경로·대상 청크 번호만 나르고(`walk_ids`), 문서·대상 청크 단위로 접은
뒤(`walk_targets`, NULL은 -1로 접는다)에만 LATERAL로 청크를 고른다.** 청크 정렬 13,332회 → 204회.
같은 VM에서 질의 4개 × (관리자·익명) 8건 전부 **결과 동일**, SQL **0.35~0.81초**(이전 3.5~11.6초).
의미가 보존되는 이유: 기존 `deduplicated`가 실제 `chunk_index`로 한 번 더 접으므로, NULL 대상과
명시 대상이 같은 청크로 수렴해도 이전과 같은 행이 남는다.

**드러난 결함 하나 — 동점 규칙이 접는 단계에 없었다.** 첫 재실측에서 8건 중 1건이 `via_kind`만
달랐다(`overlaps` ↔ `refers`, 문서·청크·점수·경유 문서는 동일). 트리거가 만드는 `overlaps`는 문서
단위라 대상 청크가 NULL이고 위키링크 `refers`도 NULL이라, 같은 경유 문서에서 같은 대상에 닿으면
거리·깊이·발췌가 완전히 같은 동점이 된다. `<kind 순서>`(overlaps → related → refers → revision)는
최종 정렬에만 있었고 `deduplicated`의 `ORDER BY`에는 없어서 **어느 쪽이 남는지가 정렬 구현의 물리
행 순서에 달려 있었다** — 이전 쿼리도 같은 동점을 갖고 있었고 우연히 안정적이었을 뿐이다. 우선순위를
`walk_targets`·`deduplicated` 양쪽 접기에 넣어 결정적으로 만들었다(`VIA_KIND_PRIORITY`). 로컬
컨테이너는 행이 두세 개라 동점에서 앞 행을 남겨 이 결함이 재현되지 않는다 — 회귀 테스트
(`test_edges_converging_on_one_excerpt_keep_the_stronger_kind`)는 규칙을 고정하는 것이지 빨강을
재현한 것이 아니다. 발췌 선택 규칙 자체(NULL 대상 → 최근접 청크, 명시 대상 → 그 청크)는
`test_expanded_hit_excerpt_follows_the_edge_target_chunk`가 고정한다.

**알려진 차이 하나 (실제로는 도달 불가).** 이전 쿼리는 edge로 닿은 문서에 청크가 없으면 LATERAL에서
행이 사라져 그 문서를 **거쳐 가는** 순회도 끊겼다. 새 쿼리는 청크 없는 문서도 중계는 한다(그 문서
자체는 여전히 결과에 없다). edge는 임베딩이 끝난 문서를 향해서만 만들어지고 청크는 문서와 함께만
사라지므로(CASCADE) 그 상태는 생기지 않는다. 확인 비용(순회 행마다 `EXISTS`)을 치르지 않는다.

> **여기서 잰 것은 에뮬레이션 VM의 절대값이 아니라 구조의 배수다.** 순회 행 수는 그래프 밀도에
> 비례해 다시 커질 수 있다. 그때의 축은 청크 선택이 아니라 재귀 자체(13k행에 145ms)다.

### ADR-012: 마이그레이션을 실행하는 상시 프로세스는 API 서버 하나다
**상태**: 2026-08-04 신규. **2026-08-19 개정** — 실행 주체를 "API 서버"에서 "상시 프로세스 중
API 서버 하나"로 좁힌다. 운영자가 명시적으로 호출하는 CLI는 예외다 (ADR-039).

**결정**: 마이그레이션 러너를 `app/migrations.py`로 분리하고, **API 서버 startup에서만** 호출한다. 워커와 MCP 서버는 스키마가 이미 준비되었다고 가정하고 실행하지 않는다. `app/db.py`는 커넥션 풀만 제공하며 **import 시 부작용이 없다**.

**이유**: MCP 서버는 `app.services`를 직접 import한다(ADR-008). 마이그레이션 러너가 `db.py`에 함께 있으면 MCP 프로세스가 기동할 때마다 마이그레이션이 실행될 수 있고, 워커까지 합치면 **세 프로세스가 동시에 같은 마이그레이션을 실행**하는 경쟁이 생긴다. 실행 주체를 하나로 고정하는 것이 가장 단순한 해결이다.

**트레이드오프**: 워커나 MCP를 API보다 먼저 띄우면 스키마가 없어 실패한다. `docker compose`의 기동 순서와 README에 "API 서버를 먼저 기동"을 명시해 해결한다. 분산 락 같은 장치는 데모 규모에서 과잉이다.

**2026-08-19 개정 — `openarchive init`을 두 번째 실행 주체로 허용한다 (ADR-039)**

원 결정의 문면은 "API 서버만"이었으나, **막으려던 것은 프로세스 수가 아니라 경쟁 실행**이다.
위 이유 절이 지목한 위험은 하나뿐이다 — API·워커·MCP 셋이 각자 기동하면서 같은 마이그레이션을
동시에 적용하는 상황. 그 셋은 상시 프로세스이고 기동 시점을 서로 모른다.

`openarchive init`은 사람이 한 번 호출하는 동기 명령이고, 끝나면 종료한다. 자기 자신과
경쟁하지 않으며, 상시 프로세스와 겹치더라도 그것은 운영자가 만든 겹침이지 구조가 만든 겹침이
아니다. 따라서 원 결정의 논거는 init에 적용되지 않는다.

개정 후의 계약:

| 주체 | 마이그레이션 실행 | 근거 |
|---|---|---|
| API 서버 (상시) | 한다 — startup에서 | 원 결정 유지 |
| 워커 · MCP 서버 (상시) | **하지 않는다** | 원 결정 유지. 스키마가 준비된 것으로 가정한다 |
| `openarchive init` (일회성 CLI) | 한다 — 운영자가 명시적으로 호출할 때만 | 이 개정 (ADR-039) |

**바뀌지 않는 것**: 워커·MCP는 여전히 실행하지 않는다. `app/db.py`의 "import 시 부작용 없음"도
그대로다 — init은 `db.py`의 풀이 아니라 `migrations.py`가 직접 여는 커넥션을 쓴다.

**트레이드오프**: "마이그레이션은 API가 한다"는 한 줄로 끝나던 설명이 두 줄이 됐다. 대신 도입
경로에서 스키마 준비를 API 기동과 분리할 수 있게 됐다 — init이 확장·권한·충돌을 **적용 전에**
확인하는 자리를 얻은 것이 이 개정의 실익이다.

### ADR-013: Git Flow를 축소한 GitHub Flow를 쓴다
**상태**: 2026-08-04 신규.

**결정**: `main` 단일 기본 브랜치에 작업 브랜치를 붙이는 **GitHub Flow**를 채택한다. `develop`·`release/*`·`hotfix/*` 브랜치는 만들지 않는다.

```
브랜치 접두사:  feat/  fix/  docs/  test/  chore/
커밋 타입:      feat fix docs test refactor chore ci perf
scope:          (db) (worker) (api) (search) (mcp) (frontend) (adr)
머지 전략:      Squash merge
PR 단위:        phase 하나 = 브랜치 하나 = PR 하나
```

**이유**: `PROJECT_CONTEXT.md`의 평가 항목에 "Git Flow"가 적혀 있으나, 그대로 적용하면 1인 · 23일 프로젝트에서 순수 오버헤드가 된다.
- `release/*`는 배포 버전을 병렬 관리할 때 필요한데, 이 프로젝트는 배포 대상이 하나이고 릴리즈가 없다.
- `hotfix/*`는 운영 중인 프로덕션을 전제하는데, 그런 환경이 없다.
- `develop`은 여러 명이 통합 지점을 공유할 때 값어치가 있는데, 1인이므로 `main`과 사실상 동일해진다.

**심사 항목을 무시하는 것이 아니라 조정하는 것**이며, 근거를 이 ADR로 남긴다. 브랜치 전략·PR·리뷰·머지 이력은 그대로 남으므로 평가 대상인 "어떻게 프로젝트를 운영했는가"는 충족된다.

**브랜치 접두사를 `feat/`로 고정한 이유**: Conventional Commits의 타입 이름이 `feat`으로 고정되어 있고 변경할 수 없다. `feature/`를 쓰면 브랜치와 커밋이 같은 개념에 다른 단어를 쓰게 된다. 5개 접두사 전부를 커밋 타입과 1:1로 맞춘다.

**Squash merge를 택한 이유**: **작업 이력과 결과 이력을 각자 알맞은 곳에 둔다.**

이 프로젝트는 harness(`scripts/execute.py`)로 phase를 step 단위로 실행하므로, 작업 브랜치에는 step별 커밋과 실행·검증 산출물이 쌓인다. 이것들은 "어떻게 만들었는가"의 기록이며 **PR에서 보존된다** — 커밋 목록, step별 산출물, self-review 코멘트, 리뷰에 따른 수정 커밋이 모두 PR 페이지에 남는다.

`main`에는 **검토가 끝난 phase 단위 결과만** 남긴다. `git log`가 "이 프로젝트가 무엇을 만들었는가"를 phase 단위로 읽히게 하는 것이 목적이다. 과정과 결과를 같은 층에 섞으면 둘 다 읽기 어려워진다.

| 남는 곳 | 내용 |
|---|---|
| **PR** | step별 커밋, 실행 산출물, 검증 결과, self-review, 수정 이력 |
| **`main`** | phase 하나 = 커밋 하나. 검토를 통과한 결과 |

> **"중간 커밋이 `main`을 오염시키므로"가 아니다.** harness는 step이 `completed`일 때만 커밋하므로(`execute.py`) WIP·오타 수정 같은 커밋이 구조적으로 생기지 않는다. 정리할 쓰레기가 있어서 squash하는 것이 아니라, **두 종류의 이력을 분리해 각각 읽기 쉽게 두려는 것**이다.

**포기하는 것**: `main`의 `git log --graph`에서 머지 지점과 step 단위 작업 흐름이 보이지 않는다. 평가 항목의 "Merge History"는 PR 목록과 각 PR의 커밋 목록으로 확인할 수 있으므로 실질적 손실은 제한적이다. 다만 `git log`만 보는 사람에게는 커밋 수가 적어 보이므로, README와 결과보고서에서 PR을 함께 가리킨다.

**1인 프로젝트의 Code Review**: self-approve는 형식적이므로, PR마다 다음을 남긴다.
1. `/code-review` 실행 결과를 PR 리뷰 코멘트로 게시
2. self-review 체크리스트 (ADR 준수 / 테스트 통과 / `CLAUDE.md` CRITICAL 규칙 위반 없음)

리뷰 코멘트와 그에 따른 수정 커밋이 실제로 남는 것이 목적이다.

**트레이드오프**: 여러 버전을 동시에 유지해야 하는 상황이 오면 브랜치 전략을 다시 세워야 한다. 대회 기간 중에는 발생하지 않는다.

### ADR-014: 라이선스는 MIT, 저장소 공개는 제출 직전
**상태**: 2026-08-04 신규.

**결정 1 — 라이선스는 MIT.** 저장소 생성 시 기본 선택된 Apache-2.0을 MIT로 교체한다.

**이유**: 대회 규정 제8조 ①은 OSI 인증 라이선스를 요구하며 MIT·Apache 2.0 모두 예시로 명시한다. 둘 중 MIT를 택한 이유는 **임베딩 모델 BGE-M3가 MIT**이기 때문이다. 라이선스 계통이 일치하면 SBOM과 고지 의무(제8조 ⑥) 이행이 단순해지고, 문서 분량도 줄어든다.

**포기하는 것**: Apache-2.0의 명시적 특허 실시권 부여(§3)와 상표 조항. 이 프로젝트는 특허 대상 알고리즘을 만들지 않으므로 실질적 손실이 없다. 특허 리스크가 있는 코드를 나중에 추가한다면 재검토한다.

---

**결정 2 — 저장소는 제출 직전까지 private을 유지한다.**

**이유**: 지정과제라 참가자 전원이 같은 문제를 푼다. 개발 기간 중 공개하면 경쟁자가 설계 결정(OpenProxy 경유, LISTEN/NOTIFY 리스크 분석, 정합성 검증 쿼리)을 그대로 참고할 수 있고, 규정상 이를 막을 수단이 없다. 제18조 ②는 "무단 도용"을 금지하지만 공개된 설계를 참고하는 것까지 막지는 못한다.

규정 제10조 ②는 *"출품작은 공개 저장소에 게시해야 한다"*이지 **개발 기간 내내 공개하라는 요구가 아니다.** 커밋 히스토리·PR·이슈는 나중에 공개해도 그대로 보이므로, 제11조 ②의 "평가 시점 저장소 상태 기준" 심사에 손해가 없다.

**경위**: 저장소는 생성 시 public 상태였다. 2026-08-04 첫 push 직후 private으로 전환했으며, 공개 구간에는 `Initial commit`(LICENSE 하나)과 첫 push 후 수 분만 존재했다. star·fork 모두 0이었다.

> ⚠️ **제출 전 반드시 public으로 되돌려야 한다.** 잊으면 제10조 ② 위반으로 결격이다.
> ```bash
> gh repo edit jeongeundev/OpenArchive --visibility public --accept-visibility-change-consequences
> ```
> 수상 시에는 이후 **5년간 Public을 유지**해야 한다 (제10조 ③).

**트레이드오프**: 개발 기간 중 외부 기여나 피드백을 받을 수 없다. 23일 단독 프로젝트에서 실질적 손실이 아니다.

### ADR-015: 제품은 "AI를 위한 문서 저장소"이며, 보장 범위는 버전 일관성과 최신 수렴이다
**상태**: 2026-08-04 신규 · 2026-08-14 ADR-031이 결정 1을 확장(제품 정의를 플랫폼으로). 결정 2·3은 그대로 유효하다.

**결정 1 — 제품 정의.** OpenArchive를 *"AI에게 주는 근거가 어느 시점에도 하나의 일관된 버전이고, 최신 버전으로 수렴함을 데이터베이스가 보장하는 문서 저장소"*로 규정한다. README·PRD·결과보고서가 이 한 문장을 공유한다.

**이유**: `PROJECT_CONTEXT.md`의 core 4요건(고가용성 / DB 계층 자동화 / 정형+벡터 결합 / 의미 검색)은 각각 타당하지만, 나열해 두면 "기능 네 개"로 읽힌다. 평가 항목 중 기능 개수가 영향을 주는 것은 **혁신성 6점 하나뿐**이며, 나머지 24점은 구조·문서·운영에 붙는다. 따라서 기능을 늘리는 것보다 **넷을 하나의 주장으로 묶는 것**이 이득이 크다.

이 정의에서 각 요건은 하나의 역할을 맡는다.

| Core 요건 | 이 주장에서의 역할 |
|---|---|
| DB 계층 자동화 | 근거의 버전이 어긋난 구간을 **DB가 스스로 좁힌다** |
| 정형+벡터 결합 | 권한·태그를 지킨 채 **정확한 근거만** 인출한다 |
| 고가용성 | 그 저장소가 **장애 후 스스로 복구된다** |
| MCP | 그 근거를 **AI에게 공급한다** |

---

**결정 2 — 보장 범위는 "항상 최신"이 아니다.**

초안은 *"근거가 항상 최신임을 DB가 보장한다"*였다. **이 표현은 쓰지 않는다.** 사실이 아니기 때문이다.

- 재임베딩 중에는 **이전 버전 청크로 검색된다.** 이건 결함이 아니라 PRD가 의도한 "검색 공백 없음"이다 (`ARCHITECTURE.md` 검색 데이터 흐름 절)
- 워커 폴링 주기(기본 5초)와 임베딩 소요만큼 반영이 늦다 (ADR-009)
- Failover 구간 수십 초는 요청이 실패한다 (`OPENSQL_RESEARCH.md` §3)

대신 **실제로 보장하는 두 가지**를 명시한다.

| 보장 | 근거 |
|---|---|
| **버전 일관성** — 어느 시점에 조회해도 활성 청크는 **하나의 버전**이며, 여러 버전이 섞이지 않는다 | 청크 교체가 단일 트랜잭션이고(`DELETE` + `INSERT`), 검색은 단일 문이라 READ COMMITTED의 문 단위 스냅샷 안에서 일관된다 |
| **최신으로 수렴** — 지연은 있어도 결국 최신 버전으로 수렴하며, **어긋난 구간을 쿼리로 관측할 수 있다** | 트랜잭셔널 아웃박스 + 코얼레싱 + 커밋 직전 `content_hash` 재확인 (ADR-001, ARCHITECTURE 워커 루프) |

`PRD.md`가 이미 "무중단"을 **"짧은 중단 후 자동 복구"**로 정정한 것과 같은 태도다. 과장하지 않는 편이 심사에서도 유리하다 — **"항상 최신"은 증명할 수 없지만, "정합성 카운터가 올랐다가 0으로 돌아온다"는 화면으로 보여줄 수 있다.** 관측 가능한 주장이 검증 불가능한 주장보다 강하다.

> 사용자 대상 문구에 "항상 최신", "실시간 동기화" 같은 표현을 쓰지 않는다. `CLAUDE.md`에 규칙으로 남겼다.

---

**결정 3 — 생성 LLM을 탑재하지 않는다. MCP는 근거 제공 게이트웨이다.**

플랫폼 안에서 답변을 생성하는 LLM을 넣지 않는다. 우리의 책임은 **근거 인출까지**이며, 답변 생성은 MCP 클라이언트(Claude Desktop/Code 등)가 수행한다.

**이유**:
1. **규정 제약과 비용.** 대회 규정 [별표2]는 로컬 구동 가능한 모델만 허용한다. BGE-M3(약 2GB) 위에 생성 모델 4~8GB를 더 얹으면 개발·검증 부담이 core 4요건을 잠식한다.
2. **MCP가 규정이 권장하는 경로다.** [별표2]는 MCP를 *"적극 허용하며 권장"*한다고 명시한다. 규정이 이름을 찍어 권장하는 유일한 기술이다.
3. **제출 서식이 단순해진다.** 자체 LLM이 없으므로 [붙임2] AI 모델 활용 정보가 BGE-M3 하나로 끝난다.

**MCP를 무엇으로 부르는가**: "AI가 사내 문서만을 근거로 답하게 하는" 같은 표현은 쓰지 않는다. **클라이언트가 자기 지식으로 답하는 것을 우리가 막을 수단이 없기 때문이다.** 할루시네이션 억제는 클라이언트의 몫이다. 우리가 실제로 하는 일은 **근거를 공급하는 것**이므로, *"AI 에이전트에 사내 문서의 근거를 공급하는 게이트웨이"*로 서술한다.

**트레이드오프**: 플랫폼 단독으로는 "질문하면 답이 나오는" 데모를 보여줄 수 없다. MCP 클라이언트를 함께 띄워야 한다. 대신 검색 결과 자체가 근거(발췌 + 문서 + 기준 버전)를 갖추므로, 플랫폼 화면만으로도 가치가 드러난다.

### ADR-016: 키워드(`pg_trgm`) + 벡터 RRF 결합
**상태**: 2026-08-04 신규 · 2026-08-09 방식 변경(#29) · 2026-08-11 실측 후 미채택

**최종 결정**: 키워드와 벡터 랭킹의 RRF 융합을 **제품 검색에 채택하지 않는다.** 기존 벡터
진입점과 그 뒤의 그래프 확장을 유지한다. `pg_trgm` 확장 자체는 관계 판정 실측의 재현 근거로
남지만, 검색 SQL과 trigram 인덱스는 제품에 남기지 않는다.

**원안과 중간 결정**: 최초 안은 `content_tsv`를
`to_tsvector('simple', content)`로 만드는 `GENERATED ALWAYS AS ... STORED` 컬럼과 GIN
인덱스였다. 벡터가 약한 정확 일치를 보완하고, 서로 척도가 다른 코사인 점수와 키워드 점수를
가중합하지 않기 위해 RRF로 합칠 계획이었다. #29에서는 FTS 대신 `pg_trgm`을 쓰는 방식으로
바꾸고 m9에서 실제 규모를 측정한 뒤 채택하기로 했다. 즉 원안의 목적은 유지하되 한국어 후보
생성 방식만 먼저 정정한 상태였다.

**폐기된 FTS 설계의 한계 — 한국어에서 기대 효과가 제한적이었다**

OpenSQL 번들 확장 목록(`OPENSQL_RESEARCH.md` §1)에 한국어 형태소 분석기가 없다. 그래서 폐기된 `to_tsvector` 설계는 `simple` 파서를 쓸 수밖에 없었는데, 이는 공백·구두점 기준 토큰화만 수행하며 **조사를 분리하지 못한다.**

```
"OpenSQL의 정합성"  →  {opensql의, 정합성}     ← "opensql"로는 매치되지 않는다
```

기대 효과는 **조사가 붙지 않고 등장하는 토큰**(독립 표기된 제품명·영문 약어·숫자·에러 코드 등)에 한정된다고 예상했다. 실측에서 이 한계가 그대로 확인됐다. `simple` FTS는 `"OpenSQL"` 검색 **0건**, `"정합성"` 검색 **0건**이었고, trigram은 각각 2건·1건을 찾았다. 그래서 실제 비교 후보는 `to_tsvector`가 아니라 `pg_trgm`으로 바꿨다.

**실제 규모 비교에서 뒤집힌 것**: 이 ADR은 원래 *"기대 효과가 실측 전까지 불확실하다"*고
두었다. 실 BGE-M3 문서 63건·청크 299행에서 10개 질의를 비교했고, 융합은 채택 조건을 충족하지
못했다. `K=10·30·60·100` 중 9개 질의의 1위가 같아 상수 조정으로도 결론이 바뀌지 않았다.
중앙 실행 시간은 벡터 1.68 ms, 키워드 5.36 ms, 융합 5.93 ms로 성능이 이유는 아니다.

**⚠️ 미채택 근거는 같은 날 재측정으로 교체됐다.** 1차 측정은 키워드 순위를
`similarity(content, query)`로 매겼는데, 이 함수는 **두 문자열 전체**의 trigram 자카드라
청크가 길수록 0에 수렴한다(실측 0.013~0.065 — 전부 잡음, 사실상 청크 길이 순). 그래서
*"융합이 벡터의 정답성 높은 상위 문서를 내렸다"*는 1차 관찰은 **틀린 키워드 랭킹 위에서
나온 것이라 근거로 쓰지 않는다.**

`word_similarity(query, content)`로 바꿔 재측정하면 후보는 제대로 잡히지만 **점수가
포화한다** — `OpenSQL` 후보 125개 중 109개가 1.000 동점이고 서로 다른 점수는 4개,
`OpenProxy`는 101개 중 77개 동점에 서로 다른 점수 **2개**다. 질의어가 온전히 포함되면
무조건 1.000이므로 순위는 보조 정렬이 정한다.

**따라서 진짜 이유는 이것이다: trigram은 포함 여부를 판정하는 이진 필터이지 랭킹 함수가
아니다.** RRF는 순위를 입력으로 받으므로, 한쪽이 무작위 순서면 융합은 잡음을 섞는 일이 된다.
순위를 세우려면 빈도·길이 정규화(BM25 계열)가 필요한데 trigram으로는 만들 수 없고,
번들에 한국어 형태소 분석기가 없어 `tsvector` 경로는 위에서 이미 배제됐다. **한국어에서
키워드 랭킹을 세우려면 형태소 분석기가 먼저다** (`OPENSQL_RESEARCH.md` §14 정정 블록).

**검증한 쿼리 순서**: 실험 SQL은 벡터·키워드 후보를 각각 구한 뒤 RRF로 합치고, 그 **융합
이후에** `DISTINCT ON (document_id)`을 적용했다. ADR-011 보강 2의 조건을 실제로 지켰으므로
미채택 결과가 잘못된 문서 축소 순서에서 나온 것은 아니다. 측정 뒤 검색 SQL과
`gin (content gin_trgm_ops)` 인덱스 마이그레이션은 회수했다.

**확장 가용성**: `pg_trgm`은 OpenSQL 번들 목록에는 없지만 PostgreSQL contrib으로 존재하며,
실 VM(2026-08-05)과 로컬 `pgvector/pgvector:pg17` 컨테이너(2026-08-10) 양쪽에서 확인했다.
따라서 미채택은 환경 제약 때문이 아니다. 확장은 관계 방향 판정 실측을 재현하기 위해 남아 있으나,
그 실측에서도 `broader`는 성립하지 않아 제품 관계 종류에는 쓰이지 않는다 (ADR-029).

**트레이드오프**: 정확·부분 일치가 의미 검색을 보완할 가능성을 포기한다. 다만 포기한 것은
*보완 가능성*이지 *측정된 이득*이 아니다 — trigram으로는 순위 자체가 서지 않아 이득을 잴
수단이 없었다. **재검토 조건은 데이터 규모가 아니라 랭킹 신호다**: 한국어 형태소 분석기나
빈도·길이 정규화가 가능한 키워드 점수가 생기면 같은 3경로 비교를 다시 수행한다.

### ADR-017: 인라인 편집은 추출 텍스트의 새 논리 버전을 만든다
**상태**: 2026-08-04 신규.

**결정**: 플랫폼 안에서 문서를 편집할 수 있게 한다. 편집 대상은 **추출 텍스트**(`documents.content`)이며 **원본 파일이 아니다.** `PUT /api/documents/{id}`에 클라이언트가 읽은 `version`을 함께 보내고, 서버의 현재 버전과 다르면 **409 Conflict**를 반환한다.

**이유**: `ARCHITECTURE.md`의 정합성 검증 쿼리(`c.version <> d.version`)와 `/admin/status`의 카운터가 이 과제의 핵심 주장을 증명하는 장치인데, **그 카운터를 움직이려면 파일을 로컬에서 고쳐 재업로드해야 했다.** 화면에서 한 문장을 고치고 저장하는 것과 파일을 갈아끼우는 것은 보는 사람에게 전혀 다르게 읽힌다. 편집 → 카운터 상승 → 재임베딩 → 카운터 0 복귀를 한 화면에서 보여줄 수 있다.

**원본 파일과 추출 텍스트를 구분한다**

현재 스키마에 원본 바이너리를 담는 컬럼이 없다. PDF를 업로드하면 pypdf가 추출한 텍스트만 남고 파일은 버려진다. 따라서 편집의 의미는 다음과 같다.

| 바뀌는 것 | 바뀌지 않는 것 |
|---|---|
| `documents.content` (추출 텍스트) | 업로드된 원본 파일 — 애초에 보관하지 않는다 |
| `version` +1, `document_versions`에 새 행 | `filename`, `content_type` |
| 재임베딩된 청크 | |

**`filename = report.pdf`인데 `content`가 그 PDF에서 추출한 것과 다른 상태는 정상이다.** 결함이 아니라 설계된 동작이며, 스캔 품질이 나쁜 PDF의 오추출을 고치는 정당한 용도가 있다. 다만 명시하지 않으면 "PDF를 편집한다"로 읽히므로, UI 문구 규칙을 `UI_GUIDE.md`에 못 박았다 — 편집 영역 레이블은 "본문 편집"이 아니라 **"추출 텍스트 편집"**이다.

`document_versions`의 이력도 마찬가지로 **텍스트 버전 이력**이지 파일 버전 이력이 아니다. v1으로 되돌려도 원본 PDF가 아니라 v1 시점의 추출 텍스트가 돌아온다. 프로젝트 전체에서 **원본 파일 / 추출 텍스트 / 텍스트 버전** 세 용어를 구분해 쓴다.

**낙관적 동시성을 넣는 이유**: 두 사람이 같은 문서를 편집하면 나중에 저장한 쪽이 앞선 변경을 조용히 덮어쓴다. `version` 비교는 비교 한 줄과 409 분기로 끝나고, "정합성"을 표방하는 프로젝트에서 이 정도는 갖추는 것이 일관된다.

**신규 엔드포인트를 만들지 않는다**: 기존 `PUT /api/documents/{id}`를 재사용한다. 추가되는 코드는 백엔드의 version 비교 + 409 분기, 프론트의 편집 토글·저장·충돌 안내다. `document_versions`·`embedding_jobs`에는 여전히 애플리케이션이 직접 쓰지 않는다 — 트리거가 담당한다.

**트레이드오프**: 원본 파일을 보관하지 않으므로 "원본 다운로드" 요구를 충족할 수 없다. `PRD.md`의 MVP 제외 항목에 명시했다(2026-08-14 PRD 기준선 개편으로 「경계」 절의 제품 원칙으로 승격됨 — ADR-032). 보관이 필요해지면 오브젝트 스토리지 또는 `bytea` 컬럼을 추가하는 별도 결정이 필요하다.

### ADR-018: 관련 문서는 질의 시점 `avg(embedding)`으로 구한다
**상태**: 2026-08-04 신규 · 2026-08-11 개정 (#38, ADR-029).

**2026-08-11 개정**: `find_related`와 태그 추천의 이웃 집합을 질의 시점 `avg(embedding)`에서
ADR-029의 저장된 관계로 옮긴다. 원래 방식은 문서 대표 벡터라는 별도 동기화 대상을 만들지 않으면서
항상 현재 청크에서 계산한다는 점 때문에 옳았지만, 관계 edge를 청크 교체와 같은 트랜잭션에서 만드는
트리거를 채택하면서 그 최신성 차이가 사라졌다. 대표 벡터를 저장하지 않는 원래 판단은 여전히 옳다.
대표 벡터는 문서 하나의 요약인 반면 edge는 문서 **쌍**에서 관측한 청크 관계이며, 청크와 함께
원자적으로 교체된다. 아래 본문은 이전 결정의 근거와 측정 기록으로 보존한다.

이 개정은 벡터 검색 일반의 규칙을 폐기하지 않는다. 특히 재개정에서 확인한 **권한 필터를 벡터 정렬
서브쿼리 안에 둔다**는 규칙은 `search.py`가 계속 따르며, 필터를 밖으로 빼 private 후보가 자리를
차지하게 하지 않는다. 사라지는 것은 `find_related`의 벡터 정렬 서브쿼리뿐이다.

**결정**: 문서 상세에 "관련 문서"를 제공한다. 대상 문서의 청크 평균 벡터를 **질의 시점에 계산**하고, 그것과 가까운 다른 문서의 청크를 찾는다. **문서 대표 벡터를 컬럼으로 저장하지 않는다.**

**이유**: 대표 벡터를 `documents`에 저장하면 그 컬럼이 **새로운 동기화 대상**이 된다. 청크가 바뀔 때마다 갱신해야 하고, 갱신이 누락되면 원본과 어긋난다 — 이 프로젝트가 해결하겠다고 내세운 바로 그 문제를 하나 더 만드는 셈이다. 질의 시점 계산은 청크가 바뀌면 결과가 자동으로 따라오므로 동기화 대상이 늘지 않는다.

**쿼리 구조는 ADR-011의 3단계를 따른다** — 벡터 정렬 + LIMIT으로 후보 확보 → `DISTINCT ON`으로 문서당 1건 → 거리순 재정렬 + 최종 LIMIT. 순서를 지키지 않으면 인덱스를 못 쓰거나 결과가 `document_id` 순으로 잘린다 (ADR-011 보강 1).

**권한 필터를 반드시 포함한다**: 검색과 동일하게 `(d.visibility = 'public' OR d.owner_id = %(user)s)`를 적용한다. 빠뜨리면 private 문서가 관련 문서로 노출된다.

**점수의 정확한 의미 — 문서 간 유사도가 아니다**

```
score = 1 − distance( 대상 문서의 청크 평균 벡터 ,  후보 문서에서 가장 가까운 단일 청크 )
                     └── 문서 전체를 뭉친 값 ──┘   └──── 최댓값 하나만 ────┘
```

대상 쪽은 **평균**, 후보 쪽은 **최댓값**이라 **비대칭**이다. 의미는 *"이 문서 전반의 주제에 가장 잘 맞는 구절을 가진 문서"*이며, **A→B 점수와 B→A 점수가 다를 수 있다.** 응답 필드명을 `sim`이 아니라 `score`로 둔 것은 "유사도"로 오독되지 않게 하기 위함이다.

**이 점수를 중복 판정에 쓰지 않는다**

비대칭 지표라 두 방향으로 실패한다.

- 두 문서가 완전히 같아도, 여러 주제를 담은 문서라면 평균이 어느 개별 청크와도 멀어져 **높은 점수가 안 나올 수 있다** (거짓 음성)
- 긴 문서가 짧은 문서를 통째로 포함하면 매우 높게 나온다 — **포함이지 중복이 아니다** (거짓 양성)

그래서 두 신호를 분리한다.

| 신호 | 판정 | 근거 |
|---|---|---|
| `content_hash` 완전 일치 | **동일 텍스트** — 확정 | 이미 컬럼이 있어 비용 0 |
| `score` 상위 항목 | **내용이 유사한 문서** — 참고용 | 위 한계로 확정 판정 불가 |

자동 차단·병합·업로드 거부 같은 액션을 붙이지 않는다. 고정 임계값으로 "중복" 배지를 켜지도 않는다. UI 문구는 "중복입니다"가 아니라 **"내용이 유사한 문서가 있습니다"**이며, 판단은 사람이 한다.

**청크가 없는 문서**: `avg(embedding)`은 대상 문서의 청크가 0행이면 **NULL을 반환**한다. 그러면 `embedding <=> NULL`이 NULL이 되어 정렬이 무의미해지고, **에러 없이 무작위 문서 목록이 반환된다.** 최초 업로드 직후(`pending`)와 최초 임베딩 실패(`error`)에서 바로 발생하므로 애플리케이션이 먼저 막는다.

분기 기준은 `embedding_status`가 **아니라 청크 존재 여부**다. 재임베딩 중(`processing`)에도 이전 청크가 남아 있으므로 정상 응답해야 하며, 이는 검색이 재임베딩 중 이전 벡터로 계속 동작하는 정책과 일치한다.

**트레이드오프**: 매 호출마다 평균을 계산하므로 저장 방식보다 느리다. 데모 규모에서는 무시할 수준이다. 다만 **`avg` 결과가 플래너에서 상수로 접히지 않으면 HNSW 인덱스를 타지 못할 수 있다** — `OPENSQL_RESEARCH.md` §12의 M0 검증 항목이며, 인덱스를 못 타면 평균을 별도 쿼리로 조회해 벡터 리터럴로 넘긴다(왕복 2회).

**실측 (2026-08-05)**: `avg(vector)` **기능 자체는 동작한다.** 실 VM에서 `SELECT avg(v) FROM (SELECT '[1,2,3]'::vector AS v) s`가 정상 반환됐다. 이 ADR의 전제가 성립한다.

플래너는 벡터 정렬을 인덱스로 처리하고 `documents`를 그 뒤에 nested loop로 붙인다.

| 조건 (`enable_seqscan=off`, `ef_search=200`, `LIMIT 100`) | HNSW | 시간 |
|---|---|---|
| A. JOIN 없음 · 필터 없음 | ✅ | 29.0ms |
| B. JOIN 있음 · 필터 없음 *(1차 측정에 없던 조건)* | ✅ | 43.9ms |
| **C. JOIN 있음 · 권한 필터 (구 설계)** | **✅** | **32.7ms** |
| D. 신 설계 (후보 확보 후 밖에서 JOIN) | ✅ | 34.4ms |

**1차 측정이 왜 반대로 나왔는지는 확정할 수 없다.** 두 측정 모두 실 VM·같은 규모(6000행)였다.

한 가지 후보는 합성 벡터의 퇴화다. 재측정에서 **전 행이 같은 벡터가 되는 함정**을 두 번 밟았고,
그 상태에서는 HNSW 인덱스가 47MB → 6MB, 삽입이 8분 → 43초로 바뀌어 계획과 비용이 통째로 달라진다.
**다만 1차 측정도 이 함정을 인지하고 대응했다고 기록되어 있다**(§12 "재현 시 함정 셋" ①). 따라서
이것을 원인으로 단정할 근거는 없다. 재측정은 실제 `BAAI/bge-m3` 임베딩(고유 6000/6000, 평균 코사인
유사도 0.498)을 썼고, 난수 벡터로도 같은 결론이 나왔다 — **결론의 재현성은 확인했으나 1차와의
차이는 규명하지 못했다.**

**되돌리는 이유 — 신 설계는 이득 없이 후보를 버린다.** 필터가 뒤에 있으면 비공개 문서의 청크가
후보 자리를 차지하고 폐기된다. 후보 100개가 퍼지는 문서 수가 **54.5개 → 40.5개**로 줄었다
(비공개 20%, 문서 20건 표본, 최소 30 → 18). `k=10`에는 둘 다 여유가 있어 **지금은 무해하지만**,
얻는 것이 없는 손실이며 `k`가 크거나 비공개 비율이 높아지면 결함이 된다.

**따라서 "결과가 `k`보다 적을 수 있다"는 트레이드오프도 함께 철회된다.** 애초에 감수할 이유가
없었다. 쿼리 전문은 `ARCHITECTURE.md` "관련 문서" 절.

**진짜 변수는 `random_page_cost`였다** — ADR-011 보강 5로 분리해 기록한다. 이 ADR의 핵심 결정
(대표 벡터를 저장하지 않고 질의 시점 `avg`로 구한다)은 두 측정 모두에서 흔들리지 않았다.

### ADR-019: 태그 추천은 유사 문서의 태그 빈도로 구한다
**상태**: 2026-08-04 신규.

**결정**: 문서 상세에서 태그를 추천한다. **태그 자체를 임베딩하지 않고**, ADR-018과 같은 방식으로 유사 문서를 찾은 뒤 **그 문서들에 달린 태그를 빈도순**으로 제시한다. 이미 달린 태그는 제외한다.

**이유**:
1. **태그 임베딩은 불안정하다.** 태그는 대개 한두 단어라 문맥이 없고, BGE-M3 같은 문장 임베딩 모델의 강점이 발휘되지 않는다. "보안"과 "보안점검"의 거리가 실제 사용 맥락을 반영한다는 보장이 없다.
2. **새 테이블이 필요 없다.** 태그를 임베딩하려면 `tags` 테이블과 벡터 컬럼, 그리고 태그가 추가될 때 임베딩하는 경로가 필요하다 — 또 하나의 동기화 대상이다.
3. **하이브리드 사례가 하나 늘어난다.** `documents.tags`(정형 배열)와 벡터 이웃이 한 쿼리에서 결합된다. 이 과제의 가산점 항목을 한 번 더 시연한다.
4. **LLM이 필요 없다.** ADR-015의 "생성 LLM 미탑재" 결정과 일관된다.

**쿼리 구조**: ADR-018과 동일한 3단계로 이웃 문서를 구한 뒤 `unnest(d.tags)`로 펼쳐 빈도를 센다. `LIMIT`은 반드시 **거리순 정렬 뒤**에 온다 — `DISTINCT ON` 직후에 붙이면 이웃이 유사도가 아니라 `document_id` 순으로 뽑힌다 (ADR-011 보강 1). 권한 필터도 ADR-018과 동일하게 적용한다.

**노출 시점**: 임베딩이 끝나 청크가 있어야 계산할 수 있으므로 업로드 직후가 아니라 문서 상세에서 노출한다. 청크가 없으면 ADR-018과 같은 `not_indexed` 응답을 반환한다.

**트레이드오프**: 문서가 적을 때는 추천 품질이 낮다 — 이웃이 없으면 추천할 태그도 없다. 콜드스타트를 감수하며, 빈 결과를 자연스럽게 표시한다. 태그 체계가 정착한 뒤에 유용해지는 기능이라는 점을 인정한다.

### ADR-020: Single 구성에서 고가용성 요건을 어떻게 다룰 것인가
**상태**: 2026-08-04 신규 · 2026-08-09 개정 (#30·#27 실측 반영) · 2026-08-10 **확정** (#41 — 사무국 답변 도착, DR 미채택). 사무국의 Single 구성 지시에 대한 대응.

**배경 — 요건과 지시가 충돌한다**

`PROJECT_CONTEXT.md`의 **핵심 구현 목표 1**은 고가용성 활용이다.

> Failover 이후에도 서비스 지속 / 플랫폼이 새로운 Primary에 정상적으로 복구 / 사용자는 장애를 인지하지 않고 서비스를 이용

그런데 사무국이 배포한 안내 메일은 다음을 지시한다.

> "OpenSQL은 고가용성(HA) 구성이 아닌 **Single 구성**으로 설치해주시기 바랍니다. 여러 대의 서버를 연결하지 않고 서버 1대에 OpenSQL을 설치하시면 됩니다."

**노드가 1대이면 Primary 장애 시 승격할 replica가 없다.** 즉 실제 failover를 발생시킬 수도, 시연할 수도 없다.

### HA와 DR은 다른 것이다

**"노드가 죽어도 서비스 지속"은 노드 2대 이상이 물리적 전제다.** 노드가 1대인 구성에서 이 요건을 채울 방법은 없다. Single에서 노드 사망에 대응하는 수단은 HA가 아니라 백업·PITR로 복구하는 **DR**이다.

그 DR조차 이 설치에서는 꺼져 있다. `archive_mode = on`이지만 `archive_command = "/bin/true"`라 WAL을 보관하지 않는다 (`OPENSQL_RESEARCH.md` §0 「설치 실태」). barman은 #29에서 기각했으므로 지금 활성화하지 않고 이 한계만 기록한다.

---

**결정 1 — 지시를 따른다. Single로 설치한다.**

우회하지 않는다. **사무국의 명시적 지시**이며, 이를 어기는 것이 요건 충족보다 우선할 수 없다.

> **2026-08-09 개정 각주**: "노드를 늘리려면 라이선스가 추가로 필요하다"는 문장을 삭제했다. 라이선스가 hostname을 검사한다는 사실만으로 다중 노드의 라이선스 조건을 알 수 없고, Patroni 노드 이름은 hostname과 별도로 설정할 수 있어 확인되지 않은 추정이었다. Single을 선택하는 근거는 사무국의 명시적 지시 하나이며 그것으로 충분하다.

**결정 2 — HA 설계는 그대로 유지한다. 축소하지 않는다.**

실제 failover를 시연할 수 없다고 해서 설계에서 HA를 걷어내지 않는다. 다음은 전부 유지한다.

| 유지하는 것 | 근거 |
|---|---|
| OpenProxy VIP 단일 엔드포인트 접속 | ADR-006 |
| 검색의 명시적 트랜잭션 | ADR-010 (근거는 교체됨) |
| 폴링 주 경로 + NOTIFY 최적화 | ADR-009 |
| 연결 끊김 재시도, 좀비 잡 회수 | ARCHITECTURE |
| `embedding_jobs`의 WAL 내구성 | ARCHITECTURE |

**이유**: 배포판에 `scripts/finalize_single_to_ha.sh`가 있다. **Single → HA 전환이 제품이 지원하는 경로**이며, 설계를 HA 전제로 두면 노드를 늘리는 것만으로 요건이 충족된다. 지금 HA를 걷어내면 나중에 되돌릴 수 없다.

**결정 3 — 시연 가능한 것과 불가능한 것을 문서에 명시한다.**

**OpenSQL 계층**

| | Single 구성에서 | 근거 |
|---|---|---|
| ✅ **PG 프로세스 장애 자동 복구** | 시연 가능 | Patroni 감지 **0.05~8.5초**(`loop_wait=10`) · redo **3 ms** · **서비스 재개 13.0~22.4초** (6표본, `OPENSQL_RESEARCH.md` §3 재측정) |
| ✅ **DCS 장애를 `failsafe_mode`가 흡수** | 시연 가능 | etcd 99초 부재에도 primary 유지 |
| ✅ **OpenProxy 백엔드 축출·재연결** | 시연 가능 | 축출 **278 ms**, 재연결은 요청 구동 |
| ⛔ **리더 선출·승격·`timeline` 증가** | **불가능** | 승격 대상 replica 없음 (`patronictl history`가 `[]`) |
| ⛔ **OpenProxy의 새 프라이머리 발견** | **불가능** | 기능 이전에 설정 자체가 없음 (ADR-006 실측 정정) |
| ⛔ **watchdog 펜싱** | **불가능** | `/dev/watchdog` 권한 부재 |
| ⛔ **노드 사망으로부터의 복구** | **불가능** | 노드 2대 이상이 물리적 전제. **DR을 켜도 이 칸은 채워지지 않는다** — 축이 다르다 (결정 6) |

**애플리케이션 계층**

| | Single 구성에서 | 근거 |
|---|---|---|
| ✅ **연결 끊김 후 자동 복구** | 시연 가능 | API·워커가 연결을 재수립하고 읽기 요청은 ADR-023에 따라 1회 재시도 |
| ✅ **잡 큐 무손실** | 시연 가능 | 워커 중단 중에도 `embedding_jobs`가 남고 재기동 후 처리 재개 |
| ✅ **좀비 잡 회수** | 시연 가능 | `processing` 잡을 스윕해 `pending`으로 복귀 |
| ✅ **원본-벡터 정합성 유지** | 시연 가능 | 장애 전후 정합성 카운터가 0으로 수렴 |

Single에서 증명한 것은 OpenSQL의 **DB 프로세스 장애 자동 복구**와 애플리케이션의 재연결·잡 재개·정합성 수렴이다. 리더 선출이나 노드 장애 복구를 증명한 것은 아니다.

증명하지 못한 **"새 Primary로의 승격"은 애초에 OpenSQL(Patroni)의 책임이지 우리 애플리케이션의 책임이 아니다** — 계층별 주체는 `ARCHITECTURE.md` 「책임 분리」 표가 정하며, 그 표의 OpenProxy 행 주석도 위 ⛔ 두 줄과 같은 실측을 근거로 한다.

**결정 4 — 표현을 정확히 쓴다.**

문서·데모·결과보고서에서 다음을 지킨다.

- "Failover를 시연했다"고 쓰지 않는다. **하지 않았다.**
- "Single 구성이라 HA를 포기했다"고도 쓰지 않는다. **설계는 유지했다.**
- 정확한 표현: **"DB 프로세스 장애 자동 복구를 검증했다. 노드 사망은 복구되지 않으며, 이는 사무국 지시에 따른 Single 구성의 제약이다. HA 설계는 유지하되 노드 승격은 검증하지 못했고, 애플리케이션 측 재연결·잡 재개·정합성 수렴을 함께 검증했다."**

`PRD.md`가 "무중단"을 "짧은 중단 후 자동 복구"로 정정하고, `ADR-015`가 "항상 최신"을 쓰지 않기로 한 것과 같은 태도다. **하지 않은 것을 했다고 쓰지 않는다.**

**트레이드오프**: 평가에서 "고가용성 활용"이 부분적으로만 드러난다. 이는 사무국 지시에 따른 결과이므로 그 사실과 함께 제시한다. 지시를 어기고 3노드를 구성하는 것보다, 지시를 따르고 **한계를 정확히 밝히는 편**이 낫다고 판단했다.

**결정 5 — HA는 세 통로로만 드러낸다.**

HA 설계와 검증 범위는 **코드 · 시연 영상 · 결과보고서**에서만 제시한다. `/admin/status`에는 Patroni 상태나 `timeline`을 추가하지 않는다. Patroni REST 응답을 받아 구현 가능성까지 확인했지만, 플랫폼 사용자가 인프라 내부 값을 볼 이유가 없고 사용자 화면과 운영 증거를 분리한다는 UI 원칙에도 맞지 않는다.

**결정 6 — DR(백업·PITR)을 켜지 않는다.** [2026-08-10 확정, #41]

`archive_command = "/bin/true"`를 그대로 두고 barman도 세우지 않는다. 위 표의 ⛔ 네 줄은 제출 시점까지 ⛔로 남는다.

**DR은 비어 있는 칸을 채우지 않는다.** 이것이 첫 번째이자 가장 큰 이유다.

| | failover | PITR |
|---|---|---|
| 답하는 질문 | 노드가 죽어도 **서비스가 계속되는가** | 데이터가 손상돼도 **되돌릴 수 있는가** |
| 성질 | 가용성 | 내구성 |
| 복구 | 수십 초, 무인 | 분~시간, 사람이 개시 |

`⛔ 노드 사망으로부터의 복구`는 **서비스 지속**을 묻는 칸이다. DR을 켜도 그 칸은 ⛔로 남고, 표에 *다른 축의 행*이 하나 생길 뿐이다. "PITR로 고가용성을 대신 보여줬다"고 쓰면 **결정 4를 정면으로 어긴다.**

나머지 근거 넷:

1. **증명할 사고가 요구사항에 없다.** 데이터 손상·오삭제 복구는 지정과제 어디에도 나오지 않는다. 프로세스 장애 자동 복구는 출제자가 1순위로 적었기에 데모의 자리가 있었지만, DR은 그 자리가 없어 영상에 넣을 컷이 없다.
2. **barman은 설치돼 있지도 않다** — 배포판 tarball에 풀려만 있고 바이너리가 없으며 `opensql-installer/` 전체에 barman 언급이 **0건**이다(실측). #25가 판정한 *"채택 비용이 구조적으로 0"*은 **코드 비용**을 말한 것이고, 설치·SSH 키·서버 등록·스케줄은 그대로 남아 있다. Single이라 백업 호스트를 분리할 수도 없어 "DB가 죽으면 백업도 같이 죽는" 구성이 된다.
3. **실증은 클러스터를 한 번 부수는 일이다.** WAL 보관(1층)만으로는 기준점이 없어 복구가 성립하지 않고, 기준 백업(2층)까지 가도 *해본 적 없는 상태*다. 실제로 복구해 보려면 Patroni를 내리고 데이터 디렉터리를 갈아끼우고 etcd 상태와 맞춰야 하는데, **그 클러스터가 `demo_recovery.sh`의 유일한 무대다.**
4. **기회비용.** 코드 프리즈 2026-08-20까지 m7~m9가 남아 있고, 프로젝트의 차별점(관계 저장·그래프 검색)과 미측정 위험이 전부 m7에 몰려 있다 (#32).

**하지 않은 것을 안 했다고 쓰는 것까지가 이 결정이다.** 결과보고서에는 "백업·PITR은 구성하지 않았다. `archive_command`가 비활성이며, 이는 Single 구성에서 노드 사망 복구가 불가능하다는 위 한계와 별개의 축이다"로 적는다. **"안 했지만 할 수 있다"는 여지를 붙이지 않는다.**

**트레이드오프**: 데이터가 손상되면 되돌릴 수 없다. 대상이 시연용 데이터이고 DB 크기가 8.4 MB(실측)이라 수용한다. 운영 배포로 간다면 이 결정이 가장 먼저 뒤집혀야 한다.

**재검토 조건**: ~~사무국 답변이 HA 허용이면~~ **2026-08-10 사무국 답변으로 Single이 확정되어 이 갈래는 닫혔다.** 문의에 충돌을 명시했고 *"기업 측에 확인한 결과, 설치 안내를 기준으로 single 구성으로 과제를 진행"*이라는 답을 받았다 — 출제자가 충돌을 알고도 Single을 지시했다는 뜻이므로, 위 결정들은 잠정이 아니라 **확정**이다. 남아 있던 뒷 절반(DR)은 결정 6이 닫았다. 이 ADR이 다시 열리는 조건은 **본선에서 노드 수 제약이 풀리거나, 이 플랫폼을 실제 운영에 올리는 경우**뿐이다.

### ADR-021: 라이선스 만료(2026-09-10)를 일정 제약으로 관리한다
**상태**: 2026-08-04 신규.

**결정**: 발급받은 trial 라이선스의 만료일을 **개발 일정의 명시적 제약**으로 다룬다. 만료 이후 OpenSQL이 필요한 작업(M0 검증, OpenProxy 경유 테스트, 최종 데모 리허설)을 배치하지 않는다.

```xml
<issue_date>2026/08/04</issue_date>
<end_date>2026/09/10</end_date>     <!-- 38일 -->
<type>trial</type>
<identified_by_host>opensql-dev</identified_by_host>
```

**이유**: `patroni.yml`의 `shared_preload_libraries`에 `opensql_license`가 포함되어 있어, **라이선스가 만료되면 PostgreSQL이 기동하지 않는다.** 검색·임베딩 파이프라인 전체가 멈춘다. 만료를 인지하지 못한 채 제출 직전 리허설을 계획하면 그 시점에 아무것도 실행할 수 없다.

**일정 대조 (2026-08-04 확인)**

```
2026-08-04   오늘 · 라이선스 발급
2026-08-27   1차 제출          ← 만료 14일 전. 여유 있음
2026-09-10   라이선스 만료
2026-??-??   2차(본선) 일정     ← 미확인. 만료 이후일 가능성이 높다
```

**1차 제출까지는 안전하다.** 23일 일정이 만료일 안에 들어간다. 문제는 그 다음이다 — **1차를 통과하면 본선 준비 기간에 DB를 띄울 수 없을 수 있다.**

**대응**:
1. OpenSQL 의존 작업(M0 검증, ADR-009·010 실측)을 **만료 전에 끝낸다**
2. 일상 개발은 `pgvector/pgvector:pg17` 컨테이너로 하므로 만료의 영향을 받지 않는다 (ADR-007)
3. **2차 일정을 확인하고, 만료 이후라면 1차 제출 직후에 연장을 요청한다.** 마감에 임박해 요청하면 처리 시간이 없다
4. 실측 결과는 문서에 기록해, 라이선스가 만료되어도 **증거가 저장소에 남도록** 한다

**트레이드오프**: 만료 후에는 OpenSQL 고유 동작을 재확인할 수 없다. 그래서 M0 검증 결과를 `OPENSQL_RESEARCH.md`에 수치와 함께 남기는 것이 4번 대응의 핵심이다 — 나중에 다시 돌려볼 수 없기 때문이다. 심사는 저장소 상태를 기준으로 하므로(규정 제11조 ②), 기록이 남아 있으면 라이선스 만료가 평가에 직접 영향을 주지는 않는다.

### ADR-022: 임시 테이블을 쓰지 않는다 — 중간 결과는 CTE로 처리한다
**상태**: 2026-08-05 신규.

**결정**: 애플리케이션 쿼리에서 `CREATE TEMP TABLE`을 쓰지 않는다. 여러 단계를 거치는 조회의 중간 결과는 **CTE(`WITH`)로 처리**한다.

**이유**: **OpenProxy는 풀 백엔드를 다음 클라이언트에게 넘길 때 `RESET ALL`만 하고 `DISCARD ALL`은 하지 않는다.** 실측으로 확인했다 (`OPENSQL_RESEARCH.md` §5-2).

| 세션 상태 | 다음 클라이언트로 |
|---|---|
| GUC (`SET statement_timeout`) | 초기화됨 ✅ |
| `LISTEN` 등록 | **누수** ❌ |
| 임시 테이블 | **누수** ❌ |

세션1이 만든 임시 테이블이 세션2에게 그대로 보인다. 그래서 다음 두 가지가 **에러 없이** 일어난다.

1. **이름 충돌** — 같은 이름으로 `CREATE TEMP TABLE`을 하면 이미 존재한다는 에러가 나거나, `IF NOT EXISTS`를 쓴 경우 **이전 클라이언트의 데이터가 남은 테이블을 그대로 쓴다**
2. **데이터 누수** — 다른 사용자의 중간 결과를 읽는다. 권한 필터를 아무리 정확히 걸어도 그 앞단에서 새는 경로다

무증상이라는 점이 위험하다. 실패가 예외로 드러나지 않고 **조용히 잘못된 결과**로 나타난다.

**CTE로 충분한가**: 그렇다. 이 프로젝트에서 다단계가 필요한 조회는 검색·관련 문서·태그 추천 세 가지이며, 셋 다 이미 CTE 구조다 (`ARCHITECTURE.md`). 임시 테이블이 필요한 케이스가 현재 설계에 없다.

**같은 뿌리의 결정들**: `SET LOCAL`을 쓰기로 한 ADR-010·011이 이 실측으로 정당화된다. GUC는 `RESET ALL`이 되돌려주지만 그것에 의존하지 않고 트랜잭션 스코프로 못 박아두는 편이 안전하다. 누수되는 축(`LISTEN`·임시 테이블)에 대해서는 **아예 쓰지 않는 것**이 대응이다.

**`LISTEN` 누수는 왜 금지하지 않나**: 워커의 `LISTEN`은 전용 커넥션에서 걸고, 폴링이 주 경로라 오작동해도 정합성에 영향이 없다 (ADR-009). 임시 테이블과 달리 **잘못된 데이터를 만들지 않는다** — 불필요한 깨우기가 생길 뿐이다.

**트레이드오프**: CTE는 실행 계획이 쿼리 전체와 함께 잡히므로, 임시 테이블처럼 중간 결과에 인덱스를 걸거나 통계를 갱신할 수 없다. 데모 규모에서는 문제되지 않으나, 후보 집합이 커져 중간 결과 재사용이 병목이 되면 이 결정을 재검토해야 한다. 그때의 대안은 임시 테이블이 아니라 **명시적 이름 격리(세션 ID 접두사) 또는 실제 테이블 + 정리 잡**이다 — 누수 자체는 OpenProxy의 동작이라 사라지지 않는다.

### ADR-023: `OperationalError` 재시도는 읽기 요청에만 적용한다
**상태**: 2026-08-05 신규. `ARCHITECTURE.md`의 "요청 핸들러는 `OperationalError` 1회 재시도"를 좁힌다.

**결정**: 끊긴 연결로 실패한 요청을 한 번 다시 태우되, 대상은 **읽기 전용 요청**(`GET`·`HEAD`와 `POST /api/search`)으로 제한한다. 업로드·편집·삭제·재임베딩 요청은 재시도하지 않고 그대로 실패시킨다.

**이유**: 재시도가 안전한 조건은 "첫 시도가 아무것도 커밋하지 않았음이 확실할 때"인데, 쓰기 요청에서는 그것을 알 수 없다. `COMMIT`이 서버에 닿기 전에 끊긴 경우와, 닿아서 커밋된 뒤 응답만 잃은 경우가 클라이언트 쪽에서 구별되지 않는다. 후자를 재시도하면 **같은 문서가 두 건 생긴다** — 원본-벡터 정합성을 DB가 보장한다는 이 과제의 전제를 애플리케이션이 앞단에서 깨는 셈이다.

읽기에는 이 위험이 없고, 재시도의 실익은 오히려 읽기 쪽에 있다. 페일오버가 나도 사용자는 "업로드·검색이 계속 성공하는 것만 본다"는 것이 UI 원칙이고(`ARCHITECTURE.md` 프론트엔드 절), 그 화면을 그리는 요청이 전부 읽기다. `POST /api/search`를 포함시킨 것은 메서드만 `POST`일 뿐 읽기이기 때문이다.

**구현 위치가 미들웨어인 이유**: 핸들러 안에서 다시 시도해봐야 소용이 없다. 이미 주입된 커넥션이 죽은 그 커넥션이기 때문이다. 요청 전체를 다시 태워야 의존성이 새로 풀리고, 풀이 `check=check_connection`으로 검사한 새 커넥션을 빌려준다.

`BaseHTTPMiddleware`는 쓰지 않는다. 그쪽 `call_next`를 두 번 부르면 앱은 다시 돌지만 **첫 시도에 저장해 둔 예외를 그대로 다시 던진다**(Starlette 1.3.1 실측). 순수 ASGI 미들웨어로 요청 본문 버퍼링과 응답 송신 시점을 직접 통제한다. 응답이 이미 나가기 시작했다면 되돌릴 수 없으므로 재시도하지 않는다.

**트레이드오프**: 페일오버 중 쓰기 요청은 사용자에게 실패로 보인다. 사용자는 다시 시도해야 하고, 그 판단을 사람이 한다 — 중복 생성을 조용히 만드는 것보다 낫다는 판단이다. 쓰기까지 안전하게 재시도하려면 요청마다 멱등 키를 받아 DB에 유니크 제약으로 걸어야 하는데, 데모 범위에서 그만한 값을 하지 않는다.

### ADR-024: 태그 편집은 별도 엔드포인트이며 낙관적 잠금을 두지 않는다
**상태**: 2026-08-06 신규.

**결정**: 태그는 `PUT /api/documents/{id}/tags`에 `{tags: string[]}`를 보내 전체 교체한다. 추출 텍스트를 편집하는 `PUT /api/documents/{id}`와 분리하며, 낙관적 잠금을 두지 않는다.

**이유**:
1. 태그 UPDATE는 `UPDATE OF content_hash` 트리거를 발화시키지 않아 **재임베딩이나 버전 증가가 일어나지 않는다.** 추출 텍스트 편집과 부작용이 근본적으로 다르므로 같은 엔드포인트로 묶지 않는다.
2. `document_versions`는 추출 텍스트의 이력이며 태그는 그 대상이 아니다 (ADR-017).
3. 태그 변경은 문서 `version`을 올리지 않는다. 따라서 version 기반 잠금은 태그 변경끼리의 충돌을 감지하지 못하며, 감지하지 못하는 잠금은 보호받는다는 착각만 준다.

**트레이드오프**: 태그 편집은 last-write-wins다. 동시 편집이 드문 데모 규모에서 수용하며, 필요해지면 태그 전용 리비전 컬럼을 도입한다.

### ADR-025: MCP 서버의 사용자 컨텍스트는 환경변수이며 기본값은 익명이다
**상태**: 2026-08-06 신규 · 2026-08-15 쓰기 경계 개정 (ADR-036)

**결정**: MCP 사용자 컨텍스트는 `MCP_USER_ID` 환경변수로 주입한다. 미설정 시 `user_id=None`으로 실행해 public 문서만 조회하며, 사용자 ID를 툴 인자로 받지 않는다.

**이유**: 사용자 ID를 툴 인자로 받으면 MCP 클라이언트가 임의의 사용자를 사칭해 private 문서를 읽을 수 있다. stdio 서버는 사용자 한 명이 자기 자격으로 기동하는 프로세스이므로, 프로세스 단위 주입이 신뢰 경계와 맞는다.

**트레이드오프**: 여러 사용자가 MCP 서버 하나를 공유할 수 없다. 데모 구성에서는 문제가 없고, 다중 사용자가 필요해지면 HTTP transport와 인증을 함께 도입한다. 이는 원격 분리가 필요할 때 HTTP transport를 검토한다는 ADR-008의 트레이드오프와 같은 방향이다.

**2026-08-15 개정**: MCP 도구는 읽기 3개(`search_documents`·`get_document`·`list_documents`)와
쓰기 1개(`create_document`)가 됐다. 원 결정의 주체 경계는 그대로이며 쓰기에서 더 엄격하다.
`MCP_USER_ID`가 없으면 trusted local context로 public 문서를 읽을 수 있지만, 주체 없는 문서의
소유자를 확정할 수 없으므로 쓰기는 거부한다. 주체를 툴 인자로 받지 않는 결정도 유지한다.
구체적인 공급 계약과 범위는 ADR-036이 정한다.

### ADR-026: 로컬 개발 컨테이너는 기본 pgvector 이미지를 유지한다
**상태**: 2026-08-09 채택(#28) · 2026-08-10 결론 변경 — 커스텀 이미지를 만들지 않는다(#29 반영)

**결정**: `docker-compose.yml`의 `pgvector/pgvector:pg17`을 그대로 두고 커스텀 Dockerfile을 만들지 않는다.

**#28의 검증 결과는 유지한다.** 커스텀 Dockerfile 3줄로 `pg_cron 1.6.7`과 `vectorscale 0.9.0`을 설치해 OpenSQL 배포판과 버전을 정확히 맞출 수 있었고, 빌드는 4초, 이미지 증가는 5MB였다. 따라서 **"로컬에서 못 돌린다"는 이유로 번들 확장을 기각할 필요는 없다**는 결론은 여전히 유효하다.

**결론이 바뀐 이유**: #29가 `pg_cron`은 사용자 화면에 보이지 않는다는 이유로, `vectorscale`은 데모 규모에서 우위가 불분명하고 비교 실측 #31도 범위 밖이라는 이유로 모두 기각했다. 남은 확장 의존은 `pg_trgm` 하나이며, contrib이라 기본 이미지에 이미 존재함을 `OPENSQL_RESEARCH.md` §11에서 실측했다. 따라서 커스텀 이미지를 만들 이유가 사라졌다.

**유지되는 원칙**: 확장 없는 PostgreSQL에서도 프로젝트가 온전히 돌아야 한다(ADR-009의 폴링 우선 패턴과 같은 방향). 이를 위한 새 폴백 코드는 만들지 않으며 **현재 코드 그대로**가 그 경로다.

**재검토 조건**: 번들 확장을 실제로 채택하면 #28이 검증한 Dockerfile 경로가 그대로 살아 있다. 그때 이 ADR을 되돌린다. 이 결정은 ADR-007의 2단 개발 환경을 바꾸지 않고 오히려 재확인한다.

### ADR-027: 관계 그래프의 권한 규칙 — 볼 수 없는 문서는 존재하지 않는 것처럼 보인다
**상태**: 2026-08-09 신규 (#35) · 2026-08-14 경계 위치 개정 (#63)

**전제 — 권한은 전부 조회 시점 규칙이다.** 관계 edge를 만드는 워커에는 사용자 컨텍스트가 없다. 따라서 edge는 권한과 무관하게 전부 만들고, 사용자별 열람 범위는 조회 시점에만 적용한다. 이는 부작용이 아니라 이점이다. `visibility`를 바꾸면 다음 조회부터 그래프에 자동 반영되며, 저장 시점에 권한을 굳혀 토글마다 그래프를 다시 만들 필요가 없다.

**결정 — 볼 수 없는 문서는 존재하지 않는 것처럼 보인다.** 이 원칙은 다음 다섯 가지를 뜻한다.

| # | 규칙 | 무엇을 막는가 |
|---|---|---|
| 1 | **순회가 통과하지 못한다** | private 노드에서 멈춘다. 결과 목록에서만 빼면 경유 과정에서 이웃 관계가 샌다 |
| 2 | **자리도 남기지 않는다** | Confluence식 `🔒` 표시를 기각한다. 표시 자체가 존재와 개수를 알린다 |
| 3 | **집계에 세어지지 않는다** | 고아 문서·깨진 링크·덩어리 크기를 모두 사용자의 열람 범위 안에서 센다 |
| 4 | **다른 문서의 관계 종류에 영향을 주지 않는다** | 전역 집계가 다른 사용자의 문서에 표시되는 `kind`를 바꾸지 못하게 한다 |
| 5 | **링크가 닿지 않는다** | 위키링크를 조회 시점의 열람 범위 안에서 resolve하며, private 대상은 없는 문서와 똑같이 깨진 링크로 보인다 |

1번은 **결과에서 숨기는 것만으로 충분하지 않다.** 탐색이 볼 수 없는 노드를 경유하면 그 너머의 도달 가능성과 이웃 관계가 드러나므로, 순회 자체가 해당 노드에서 멈춰야 한다.

2번에서 `🔒` 자리표시자를 기각한다. 이 프로젝트에는 권한 요청 흐름이 없어 사용자가 그 자리를 보고 취할 수 있는 행동이 없고, 표시 자체가 문서의 존재와 개수를 알리는 정보다.

3번에서 *사용자마다 고아 수가 다른 것*은 부작용이 아니라 옳은 동작이다. 전체 그래프를 기준으로 세면 사용자가 볼 수 있는 문서에 표시된 *고아가 아니다*라는 사실이 곧 *내가 못 보는 이웃이 있다*는 뜻이 되어 정의상 누출이다. 깨진 링크 수와 덩어리 크기도 같은 이유로 열람 범위 안에서만 집계한다.

5번은 깨진 링크와 권한 없음을 의도적으로 구분하지 않는다. **둘이 구분 불가능한 것이 정확히 목적이다.** resolve 결과나 오류 종류가 다르면 private 대상의 존재를 확인하는 통로가 된다.

**4번의 핵심 근거는 누출이 아니라 정합성이다.** `포괄↔상세` 관계 판정에서 허브성 같은 전역 집계 축을 제거한다. 권한 필터는 행을 거를 수 있을 뿐, 이미 `kind` 값 안에 접힌 정보는 거를 수 없다. 그러나 그 누출은 간접적인 1비트라 그것만으로는 설계를 기각할 충분히 강한 이유가 아니다.

진짜 이유는 **새로운 동기화 대상이 생긴다**는 점이다. 허브성 기반 `kind`는 A와 B가 전혀 바뀌지 않아도 무관한 문서 D가 추가되는 순간 낡는다. 이는 ADR-018이 문서 대표 벡터를 저장하지 않음으로써 피한 함정의 재판이며, 더 나쁘다. 대표 벡터는 자기 청크가 바뀔 때만 낡지만 허브성은 남의 문서가 늘 때 낡아 해당 edge의 트리거로도 잡을 수 없다.

대신 `pg_trgm`의 비대칭 함수인 **`word_similarity` 단독으로 `포괄↔상세`를 판정**하고, 판정하지 못하면 `related`로 폴백한다. 관계 종류가 두 문서 자체의 값에만 의존하므로 둘이 바뀌지 않는 한 결과도 낡지 않는다.

**기각한 대안 — public만 센다.** 전역 집계를 유지하되 public 문서만 허브성에 포함하는 방식은 쓰지 않는다. 원칙 하나로 누르려는 설계에 별도 예외 규칙을 더하며, 소유자조차 자기 private 문서끼리의 방향을 볼 수 없게 만든다.

**강제 방법 — grep이 아니라 행동 테스트.** 권한 술어는 SQL 조각 상수 하나로 두고 모든 조회 쿼리가 재사용한다. 각 쿼리에는 private 문서를 넣은 뒤 익명·타인·소유자 결과를 각각 단언하는 행동 테스트를 둔다. 문자열 `grep`은 검사 범위에 테스트나 규칙 문서가 섞이면 문자열을 쪼개 우회할 수 있고, M5 결함 3건이 이 방식에서 생겼으므로 강제 수단으로 쓰지 않는다.

기존 세 곳인 `SEARCH_SQL`·`_NEIGHBOR_CTE`·`IDENTICAL_SQL`에도 이 상수와 행동 테스트를 소급한다. **이 ADR에서는 대상만 지정하며, 실행은 m7에서 관계 그래프 쿼리와 함께 한다.**

**2026-08-14 개정 — 주체 문서의 열람 검증을 서비스 계층으로 내린다.** 위 결정의 열람
의미론과 `VISIBLE_TO_USER`는 바꾸지 않았다. 달라진 것은 관련 문서·태그 추천·링크·백링크가
조회할 **주체 문서**에도 같은 술어를 적용하는 자리다. `services/documents.py`의
`ensure_visible`이 이를 검증하고, 볼 수 없으면 `DocumentNotFound`를 던진다.

원래는 HTTP 읽기 엔드포인트의 선행 문서 조회가 주체 문서를 검사했다. 그러나 이 구조에서는
서비스를 직접 호출하는 인터페이스가 같은 선행 검사를 각자 협조해서 넣어야만 계약이 성립한다.
PRD §4의 경계 규칙대로 Web UI 밖의 공급·소비 인터페이스가 늘어날 예정이므로, 네 서비스 함수
`find_related`·`suggest_tags`·`resolve_links`·`find_backlinks`가 스스로 `ensure_visible`을
호출하도록 경계를 옮겼다. 이에 따라 문서 라우터의 중복 선행 가드 4개를 제거했으며,
`DocumentNotFound`의 공통 예외 매핑 때문에 REST 응답은 이전과 같이 404다.

원 결정이 지키려던 두 가지도 유지된다. 첫째, `VISIBLE_TO_USER`는 한 글자도 바뀌지 않았고 그
동일한 술어의 적용 범위만 주체 문서로 넓어졌다. 둘째, `MCP_USER_ID`가 없는 설치의 MCP는 public
문서를 계속 볼 수 있어 통째로 눈이 멀지 않는다. 달라지는 것은 비공개 문서를 주체로 지정한
경우뿐이며, 이 경우 MCP의 `get_document`는 이미 `DocumentNotFound`를 반환하고 있었다. 이번
개정으로 네 서비스 함수도 같은 동작을 한다.

**RLS는 기각이 아니라 후속 후보이다.** RLS는 DB 계층에서 원칙을 강제하고, ADR-011 때문에 사용자 컨텍스트를 `SET LOCAL`로 둘 트랜잭션 경계도 이미 있다. 컨텍스트가 미설정되면 public만 보여 안전한 방향으로 실패한다는 장점도 있다. 다만 워커가 전체 edge를 만들려면 RLS 우회용 역할 분리가 필요하고, 정책 술어가 HNSW 실행 계획에 미치는 영향도 측정된 적이 없어 지금 도입하지 않는다. 애플리케이션 쿼리 수가 늘어 SQL 조각과 행동 테스트만으로 누락 위험을 관리하기 어려워지면, 전용 워커 역할을 분리하고 실제 데이터에서 HNSW 계획을 측정한 뒤 재검토한다.

### ADR-028: 최소 로그인 — 한 설치 = 한 조직
**상태**: 2026-08-11 신규 (#37) · 2026-08-14 시스템 상태 인증 개정 (#63)

**맥락 — 공개 URL이 권한 모델의 전제를 바꿨다.** 기존 MVP는 `X-User-Id` 헤더를 데모 사용자
식별자로 썼다. 공개 URL에서는 헤더 위조만 문제가 아니었다. 문서의 기본 `visibility`가 `public`이고
익명이 이를 읽을 수 있어, 위조조차 하지 않고 모든 public 문서를 볼 수 있었다. 따라서 공개 배포 전에
실제 로그인 경계가 필요해졌다.

**경계 — 한 설치를 한 조직으로 본다.** `public`은 이 설치에 로그인한 사용자 전체, `private`은
소유자만 볼 수 있으며 **익명은 아무 문서도 보지 못한다.** 혼자 쓰는 설치에서는 public과 private의
실질적 독자가 같은 한 사람이 되어 별도 모드 분기 없이 개인 지식 관리소가 된다. 이 모델은 설치 규모에
중립적이다.

**DB 안 워크스페이스는 기각한다.** 근거는 둘이다.

1. 요구사항에 테넌시는 한 번도 없다. 권한은 정형 데이터의 예시이고, 요구 범위는 권한 컬럼과 벡터
   검색을 한 SQL에서 결합하는 데까지이며 기존 열람 술어 네 곳이 이미 충족한다.
2. `workspace_id`는 매우 선택적인 필터가 되어 `MAX_K * 배수 < EF_SEARCH` 계산이 전제하지 않은
   recall 손실을 만든다.

**형태 — 새 우회 경로 없이 최소 구성으로 닫는다.**

| 선택 | 근거 |
|---|---|
| `hashlib.scrypt` · `secrets` | 새 의존성이 0개라 SBOM이 바뀌지 않는다 |
| 서버 측 세션 | 세션 행 삭제로 로그아웃이 실제 토큰 무효화가 된다 |
| HttpOnly 쿠키 | localStorage 토큰은 XSS 한 번에 노출된다. Next.js rewrite로 same-origin이라 CORS 설정도 필요 없다 |
| `X-User-Id` 제거 | 남겨두면 `curl -H` 한 줄로 우회되어 로그인이 장식이 된다 |
| 관리자 발급 계정 | 실무 ECM의 계정 발급 방식에 맞춘다. 초대 코드는 SaaS 협업 도구의 가입 방식이라 쓰지 않는다 |
| 관리자 = 계정 관리 전용 | 열람 권한까지 주면 ADR-027과 충돌한다. 관리 기능으로 한정해 기존 열람 술어를 바꾸지 않는다 |
| 소유 문서가 있는 계정은 삭제 거부 | 문서를 고아로 만들거나 소유자를 조용히 옮기면 `owner_id`에 걸린 열람 술어의 의미가 사라진다. 삭제하려면 문서를 먼저 지우게 해 판단을 사람에게 남긴다 (`409`) |

**경계를 거는 자리는 HTTP 계층이다.** 열람 술어(`VISIBLE_TO_USER`)는 그대로 두고 읽기
엔드포인트가 `require_user_id`를 요구한다 — 검색·문서 목록·문서 상세·관련 문서·태그 추천·주제
덩어리·문서 진단 전부다. 술어를 "익명이면 아무것도"로 고치지 않은 이유는 두 가지다. 첫째,
이 표의 마지막 줄이 약속한 "기존 열람 술어를 바꾸지 않는다"를 지킨다. 둘째, MCP는 HTTP를 타지
않으므로 술어를 고치면 `MCP_USER_ID`가 없는 설치에서 MCP가 통째로 눈이 먼다 — 로컬 신뢰 프로세스에
공개 URL의 경계를 적용하는 셈이다.

**2026-08-14 개정 — 시스템 상태도 로그인 경계 안에 둔다.** `/api/system/status`는 노드
주소·포트, 임베딩 잡 카운터, 원본 버전과 청크 버전의 어긋남 수, 임베딩 프로바이더 이름을
반환하므로 읽기 엔드포인트 인증 목록에 추가했다. 반면 `/api/health`는 문서·토폴로지 정보를
반환하지 않고 프로세스 기동 여부만 알리므로 무인증으로 남긴다. `demo_recovery.sh`도 로그인
세션을 만들기 전의 API 기동 대기를 `/api/system/status`에서 `/api/health`로 옮겼다. 인증이
필요한 status를 로그인 전에 폴링하는 순서 의존성을 다시 만들지 않기 위한 분리다.

**영향 범위는 작았다.** MCP는 서비스 계층을 직접 import하고 HTTP를 거치지 않아 변경이 0줄이다.
열람 술어와 관계 그래프도 바꾸지 않았다. 프론트에서는 `userHeaders()` 한 곳을 제거했고, 테스트는
`conftest.py` 헬퍼와 15개 호출부를 실제 쿠키 세션으로 바꿨다.

**2026-08-15 후속**: 프로그램용 비대화형 자격증명은 ADR-034의 위임 API 토큰으로 추가했다.
`X-User-Id`를 제거한 이 결정은 유지되며, 식별자가 아니라 서버가 검증하는 자격증명만 받는다.

**업로드 제한도 함께 닫는다.** 파일은 10MB, 추출 텍스트는 500KB를 상수로 제한한다. 성능 실측값이
아니라 시연 데이터에서 가장 큰 문서인 90KB의 5배 이상을 허용하는 경계다.

**남은 한계와 확장 경로.** 이 권한 모델은 실무 ECM 기준 최소형이다. 실무 문서관리에는 공간·폴더
단위 권한, 그룹 기반 권한, 역할 구분, 상속과 예외가 필요하지만 현재 구현은 문서 단위 `public`과
`private` 두 값뿐이다. 요구사항은 충족하므로 현재 범위의 결함은 아니지만, 이 기능들은 부족하다.
발전 경로는 LDAP·사내 디렉터리 연동, 그룹 권한, 공간 단위 권한 순이다. 또한 `Secure` 쿠키는
HTTPS를 전제로 하므로 상시 배포 전에 HTTPS를 구성하고 `SESSION_COOKIE_SECURE=true`로 켜야 한다.

### ADR-029: 관계를 저장 시점에 만든다 — 청크 사이의 지형을 DB 안에 남긴다
**상태**: 2026-08-11 신규 (#38)

**맥락 — RAG를 한 단계 더 간다.** 일반 RAG는 청크를 저장하고 끝나므로 청크 사이의 지형은
남지 않고, 검색은 비슷한 것을 나열하는 데서 멈춘다. GraphRAG가 LLM으로 하는 인덱싱을 벡터와
SQL만으로 대신한다. 그래프 순회는 SQL의 일이고 거리 계산은 벡터의 일이며, 둘이 같은 DB 계층에
있으므로 한 쿼리로 결합할 수 있다. 이것은 *"외부 벡터 DB를 붙였다면 못 했을 일인가"*라는 이
과제의 판단 기준에 직접 답한다. 상용 API를 금지한 ADR-003과도 맞는다. LLM이 답을 생성하지 않아도
문서 사이의 관계 구조 자체가 탐색의 답이 된다.

**결정 1 — 노드는 문서이고, 청크는 관계의 부가 정보다.** 관계 테이블은 하나로 두고 `src`와
`dst` 모두 문서를 가리킨다. 특정 대목의 만남처럼 위치가 의미 있는 관계만
`src_chunk_index`·`dst_chunk_index`를 채운다.

- **청크 쌍·문서 쌍 두 테이블**은 기각한다. 순회가 두 테이블을 오가면서 재귀 CTE가 `UNION`으로
  커지고, 같은 권한 규칙을 두 경로에 중복 적용해야 한다.
- **청크 쌍 단일 테이블**도 기각한다. 문서 관계를 대표 청크(index 0)에 매다는 순간 ADR-018이
  대표 벡터를 저장하지 않음으로써 피한 것과 같은 임의의 대표 지점이 생긴다.

실물 스키마상 `document_chunks.id`는 `bigserial`이고, 워커는 재임베딩 때 기존 청크를 전량
`DELETE`한 뒤 다시 `INSERT`한다(`worker.py:132`). 문서를 한 글자만 고쳐도 청크 id가 전부 바뀌므로
이를 관계 FK로 걸 수 없다. 문서 FK와 재계산 가능한 `chunk_index`를 사용한다.

**결정 2 — 계산이 비싼 관계만 저장한다.** §14 실측 결과를 반영해 저장 kind는 처음 계획한
3종이 아니라 **`overlaps`·`related` 2종**이다. `broader` 판정은 성립하지 않았고, 초기 계획의
`points_to` 후보도 최종적으로 `related`로 표현한다.

| 저장한다 | 저장하지 않는다 — 조회 시점에 계산한다 |
|---|---|
| `overlaps` · `related` | 이어짐 · 선후 · 분류 · 개정 |

- **이어짐**은 `chunk_index ± 1`이 곧 답이다.
- **선후**는 `created_at` 정렬이 곧 답이며, 저장하면 새 문서 하나마다 기존 끝 edge가 낡는다.
- **분류**는 `tags &&`가 곧 답이다. 게다가 `003_triggers.sql:65`의 트리거는
  `UPDATE OF content_hash`에만 발화하므로 태그만 고친 UPDATE를 잡을 갱신 주체가 없어 조용히 낡는다.
- **개정**은 문서 쌍이 아니며 `document_versions`가 이미 갖고 있다.

분류와 선후를 순회 edge로 넣으면 태그 하나가 겹치는 문서 전부가 이웃이 되어 깊이 2에서 사실상
전체 문서가 된다. 싸게 계산할 수 있을 뿐 아니라 그래프의 분별력도 해치므로 저장하지 않는다.

위키링크(`refers`)도 이 테이블에 넣지 않는다. 대상은 문서 id가 아니라 제목 문자열이고 ADR-027은
이를 저장 시점에 특정 문서로 고정하지 못하게 한다. 저장 위치는 m9가 결정한다. 따라서 이 테이블의
`dst_document_id`는 `NOT NULL`을 유지한다.

**결정 3 — `embedding_status`가 `ready`가 될 때 AFTER 트리거가 순수 SQL로 만든다.** 모든 청크가
들어간 뒤 문서당 한 번만 발화하며 워커 코드는 한 줄도 바꾸지 않는다. 임베딩 잡 생성에서 시작한
*"원본-벡터 정합성이 DB 안에서 보장된다"*는 주장을 관계까지 연장한다. 애플리케이션이 계산해
넣으면 관계 테이블은 DB가 보장하는 파생 데이터가 아니라 앱이 채운 캐시가 된다.

대가는 `finalize_job` 트랜잭션이 관계 판정만큼 길어지고, 판정이 실패하면 같은 트랜잭션의 임베딩도
롤백된다는 것이다. §14의 60문서·262청크 실측에서 중앙값에 가까운 4청크 문서 한 건은 **2.92 ms**,
전체 262청크 계산은 **176.1 ms**였다. 최대 29청크도 단순 비례로는 1초 미만이라 1초 문턱은
걸리지 않았다. 그러나 지정한 상관 `LATERAL`은 HNSW를 전혀 타지 않고 청크마다 Seq Scan했으므로,
이 수치는 현재 코퍼스의 비용일 뿐 규모 확장이나 해당 쿼리 형태 채택의 근거가 아니다. 구현은
청크별 상수 프로브처럼 HNSW가 가능한 순수 SQL 형태를 써야 하며 실제 트리거 비용을 다시 검증한다.

**`edge_jobs` 별도 아웃박스**는 지금 기각한다. 실패 격리는 낫지만 테이블과 워커 루프가 하나씩
늘고, 임베딩 완료 뒤 관계가 늦게 붙는 구간도 생긴다. 실제 트리거 비용이 임베딩 완료 지연이나
롤백 빈도를 유의미하게 늘리면 관계 계산을 `edge_jobs`로 옮겨 재검토한다.

**양방향은 한 번 계산해 두 행으로 저장한다.** 새 문서 C가 들어와도 기존 A는 재임베딩되지 않아
A가 C를 발견할 기회가 없다. C 기준 조회 한 번으로 `(C→A)`와 `(A→C)`를 함께 넣는다. 이것은
**근사**다. kNN은 비대칭이라 A 기준 이웃과 C 기준 이웃은 실제로 다를 수 있지만, 정확한 역방향은
전체 문서를 다시 계산해 비용이 문서 수에 비례한다. §14에서 `broader`가 제거됐으므로 방향 자체가
kind의 의미인 예외도 현재는 없다. 트리거는 `src = NEW.id OR dst = NEW.id`를 지우고, 대칭 저장된
두 행을 한 번의 재임베딩으로 다시 만든다. 문서 수가 커져 근사의 누락이 눈에 띄면 정확한 역방향
계산을 별도 잡으로 분리한다.

**결정 4 — 컷오프는 순위이고 kind는 비율이다.** 절대 거리 임계를 두지 않는다. 청크당 상위
`NEIGHBOR_N = 10`을 가져오는 HNSW `LIMIT`이 컷오프이며 N² 후보 폭증도 같은 장치로 막는다.
절대 임계는 임베딩 거리 분포에 의존하므로 서로 관련성이 높은 저장소 문서에 맞춘 값이 심사위원의
문서에서는 그래프를 비우거나 헤어볼로 만들 수 있다.

매칭 청크 비율 `OVERLAP_RATIO = 0.8` 이상**이면서 매칭 청크가 2개 이상**이면 `overlaps`,
나머지는 `related`로 가른다. 비율은 데이터 규모와 무관하지만 분모가 자기 청크 수여서 1청크
문서는 한 번 매칭되어도 1.0이 된다. **초판은 이를 한계로 남겼으나 실측에서 편향이 지배적이었다**
— 청크 1개 문서 19개가 각각 평균 9.6건의 `overlaps`를 만들었고, 전체 502건의 60%가 청크 3개
이하 문서에서 나왔다. 요리 레시피 한 편(1청크)이 OpenSQL 설치 문서와 비율 1.000으로 붙는다.
화면 문구가 *"전반적으로 같은 내용"*이라 단정이 그대로 틀리는 자리이므로, 절대 수 하한 2로
**"두 대목 이상에서 만난다"**를 요구한다. 하한을 거리 임계가 아니라 개수로 둔 것은 결정 4의
첫 문단과 같은 이유다 — 개수는 임베딩 거리 분포에 의존하지 않는다.

> ⚠️ **정정 (m8 step 6 화면 검증, 2026-08-11).** 위 실측은 `FakeProvider` 벡터였고, 하한 2는
> 1청크 문서만 막는다. **실 BGE-M3 재측정에서 편향이 짧은 문서에 국한되지 않음이 드러났다** —
> `PRD`↔`UI 디자인 가이드`(4·8청크), `ADR-020`↔`고가용성(HA) 전략`(8·8청크)이 모두 비율
> 1.00이다. 분모가 자기 청크 수인데 이웃 판정이 **순위 기반**이라 코퍼스 안에 최근접은 항상
> 존재하고, 주제가 가까우면 자기 대목 전부가 상대에서 최근접을 찾기 때문이다. 청크 수 하한을
> 어디에 걸어도 걸러지지 않는다(§14 재측정).
>
> 따라서 `overlaps`는 "거의 같은 내용"이 아니라 **"여러 대목에서 서로 가장 가깝다"**로 읽어야
> 한다. 임계는 그대로 두고 **화면 어휘를 신호에 맞췄다** — `UI_GUIDE.md` 관계 어휘표를
> *"여러 대목에서 만난다"*로, 진단 화면 점수를 *"닿은 대목 N%"*로 바꿨다. 확정 중복은
> `content_hash` 일치(`identical`)뿐이다. 절대 거리 임계 도입은 #38의 순위 컷오프 결정을
> 되돌리는 일이라 **미해결 항목으로 남긴다** — "한계로 남긴다"로 닫지 않는다.

`BROADER_MARGIN = 0.10`은 §14의 진단값으로만 보존한다. 정답 포괄↔상세 쌍도 차가 0.005~0.023에
그쳤고 전체 쌍의 97.5%가 0.10 미만이어서 방향 판정에는 쓰지 않는다. 즉 판정 실패 후보는
`related`로 폴백하여 방향만 사라지고 관계 자체는 사라지지 않는다. 설계 변경점 (a)의 1초 문턱과
(b)의 겹침비 구분은 걸리지 않았고, (c)의 broader만 걸려 제거했다.

**결정 5 — 관련 문서와 태그 추천을 저장된 관계 위로 옮긴다.** ADR-018의 `avg(embedding)`을
유지한 근거는 조회 시점 계산이라 현재 청크를 따른다는 것이었다. edge를 청크와 같은 트랜잭션에서
만드는 트리거를 선택했으므로 관계의 지연은 0이고 그 근거가 사라졌다.

edge 방식은 관련성이 옅으면 0건이 될 수 있다. `RelatedResult.reason`에 `no_edges`를 추가해
*"관련 문서 없음"*을 정직하게 표시한다. `find_related`에는 벡터 정렬 서브쿼리가 없어지므로
`CANDIDATE_MULTIPLIER = (EF_SEARCH - 1) // MAX_K` 불변식과 `test_related.py`의 해당 단언도
사라진다. `search.py`의 후보 제한과 불변식은 그대로 남는다.

**권한은 ADR-027을 그대로 따른다.** 워커에는 사용자 컨텍스트가 없으므로 edge는 권한과 무관하게
전부 만들고 조회 시점에만 거른다. 볼 수 없는 노드는 결과에서만 숨기는 것이 아니라 순회가 그
노드에서 멈춰 경유하지도 못한다. `kind`에 전역 집계를 접지 않는다. 결정 4의 매칭 비율은 두 문서
사이의 값일 뿐 전역 집계가 아니므로 ADR-027과 모순되지 않는다.

**m7~m9 구현 대조 결과**: 설계 변경점 (a)의 1초 문턱과 (b)의 겹침비 구분은 걸리지 않았고,
(c)의 `broader`만 성립하지 않아 저장 관계는 `overlaps`·`related` 2종으로 확정됐다. 트리거는
상관 `LATERAL` 대신 청크별 상수 HNSW 프로브로 구현했고, 임베딩 완료 지연이나 롤백 증가가
관측되지 않아 `edge_jobs` 재검토 조건은 발동하지 않았다. 재귀항은 인덱스를 사용해 깊이 2에서
2.65 ms였으므로 깊이를 1로 줄이지 않았다. 즉 이 세 항목에는 확인 후 남긴 침묵 상태가 없다.

### ADR-030: 위키링크는 제목을 가리킨다 — 해석은 조회 시점에
**상태**: 2026-08-11 신규 (#38)

**결정**: 추출 텍스트의 `[[제목]]`을 위키링크로 저장한다. 링크 행에는 대상 문서 id가 아니라
`target_title`을 저장하고, 사용자의 열람 범위 안에서 조회할 때 대상 문서를 해석한다. 채택의
값어치는 ADR-027을 화면에서 증명하는 데 있다 — private 문서를 가리키는 링크가 다른 계정에게
없는 문서와 똑같이 보인다.

**대상 id를 저장하지 않는 이유**: 링크 생성 트리거에는 사용자 컨텍스트가 없다. 같은 제목의
public·private 문서가 있을 때 저장 시점에 private id를 고르면, 사용자가 볼 수 있는 public 문서가
있는데도 링크가 깨진 것처럼 보인다. 제목만 저장하면 조회 사용자가 볼 수 있는 동명 문서를 각각
해석할 수 있고, visibility 변경도 링크 재생성 없이 다음 조회부터 반영된다.

**제목에 유일성(`UNIQUE`)을 걸지 않는다**: 사용자가 볼 수 없는 private 문서와도 제목이 충돌한다.
그 충돌 에러 자체가 같은 제목의 문서가 존재한다는 사실을 알려 ADR-027을 위반한다. 열람 가능한
동명이 여럿이면 하나를 임의로 고르지 않고 **전부 대상**으로 반환한다. 정보 손실과 임의 기준을
피하는 대신 그래프 순회의 `refers`가 1:N으로 퍼지는 것은 의도한 결과다.

**깨진 링크를 허용한다**: 위키에서는 아직 만들지 않은 문서로 향하는 링크도 정상적인 작성
도구다. 더 중요하게는 ADR-027 결정 5에 따라 없는 대상과 볼 수 없는 대상이 구분되지 않아야 한다.
둘 다 같은 깨진 링크 표현과 진단 결과를 사용하며, 이유를 따로 노출하지 않는다.

**`document_edges`와 분리한다**: 벡터 관계는 문서 id 쌍이고 임베딩 완료 시 만들어진다.
위키링크의 대상은 제목 문자열이며 벡터가 필요 없으므로 본문 변경 트리거에서 즉시 만든다. 한
테이블에 넣으면 `dst_document_id NOT NULL` 모델을 깨고 링크가 불필요하게 임베딩을 기다린다.
따라서 `document_links`는 출발 문서 id와 대상 제목을 가지는 별도 테이블이다.

**순회 채택과 실측**: 조회 시점에 해석된 링크를 `refers` edge로 그래프 검색의 깊이 2 순회에
포함했다. 문서 63건·저장 edge 1,252행·링크 128행에서 저장 edge만 순회한 중앙값은 0.952 ms,
제목 resolve를 합친 순회는 **1.220 ms**로 0.268 ms 늘었다. 제목 결합은 작은 입력에서 Hash Join을
썼고 전체가 2 ms 아래여서 제외할 근거가 없었다. 이 값은 현재 seed의 계획 검증이며, 문서 수가
커지면 제목 인덱스 필요성을 다시 측정한다 (`OPENSQL_RESEARCH.md` §14).

**동점 타이브레이커에서 `refers`를 `revision` 앞에 둔다**: `search.py`의 `CASE via_kind`가
`overlaps`(0) · `related`(1) · `refers`(2) · `revision`(3) 순이며, `refers`가 들어오면서
`revision`이 2에서 3으로 밀렸다. 거리가 같을 때만 작동하는 순서이고, 사람이 본문에 직접 쓴
링크가 **같은 문서의 과거 판본**보다 새 정보를 줄 가능성이 크다는 판단이다. 화면 어휘도 같은
이유로 갈린다 — `refers`만 자동 판정이 아니므로 「본문에서 가리킨다」로 단정한다
(`UI_GUIDE.md` 관계 종류 어휘).

### ADR-031: 제품 정의를 플랫폼으로 확장한다 — Web UI는 여러 소비 인터페이스 중 하나
**상태**: 2026-08-14 신규

**결정 1 — 제품 정의의 확장.** OpenArchive를 *"다양한 문서 소스에서 수집한 문서를 AI가 쓸 수
있는 형태로 변환·동기화·공급하는, OpenSQL 기반 AI 문서 데이터 플랫폼"*으로 규정한다. ADR-015
결정 1의 한 문장("AI에게 주는 근거가 어느 시점에도 하나의 일관된 버전이고, 최신 버전으로
수렴함을 데이터베이스가 보장한다")은 폐기가 아니라 **이 플랫폼의 코어가 보장하는 계약**으로
그대로 유지된다. 확장되는 것은 그 계약을 소비하는 주체의 범위다 — 사람의 화면만이 아니라 API
클라이언트·MCP 클라이언트·수집기가 같은 계약 위에서 동작한다. 이 확장은 README 태그라인과
PRD 목표 절(2026-08-14 PRD 기준선 개편 후 「정의와 가치」 절 — ADR-032)에 반영한다. 용어는 과제 정의와 어긋나지 않는다 — `PROJECT_CONTEXT.md`의
지정과제명이 이미 "OpenSQL 기반 **AI 문서관리 플랫폼**"이다. 여기에 "데이터"를 넣은 것은
관리 대상이 원본 파일이 아니라 AI가 소비하는 문서 데이터(추출 텍스트와 벡터)임을 드러내기
위해서다 (ADR-017).

**이유 — 구조가 이미 그렇다.** 이 재정의는 희망 사항이 아니라 현재 코드의 실측이다.

- 문서를 만드는 코드 경로는 `services/documents.py:create_document` 하나이고, 호출자는
  INSERT만 한다. 임베딩 잡·버전 이력·관계 그래프·위키링크는 전부 DB 트리거가 만든다
  (ADR-001, ADR-029, ADR-030). 즉 **수집기는 `documents`에 INSERT하는 클라이언트일 뿐**이며
  (`ROADMAP.md`), 공급 주체가 늘어도 파이프라인 코드는 변하지 않는다.
- services 계층은 HTTP를 모른다 — FastAPI import 0건, 모든 조회 함수가 `user_id`를 명시
  인자로 받는다. 로그인 도입(ADR-028)에서 MCP 서버 수정이 0줄이었다는 기록이 이 경계의
  실측 증거다.
- MCP 도구 세 개는 REST와 같은 services 함수를 호출하며(`mcp_server/server.py`의 import),
  그중 **검색**은 REST 응답과 실제로 비교하는 테스트가 동등성을 강제한다
  (`tests/test_mcp_server.py`). 나머지 두 도구는 같은 함수를 부른다는 사실이 근거이고,
  응답 대조 테스트는 아직 없다.

**결정 2 — 계층 구분은 conceptual model이다.** 현재 구조를 설명할 때 Ingestion(수집) →
Processing(변환·임베딩) → Storage(저장·정합성) → Retrieval(검색·관계) → Interface(소비)의
다섯 구분을 쓸 수 있다. 이것은 **설명용 개념 모델이지 공식 용어가 아니다** — 커밋 스코프
(`db`/`worker`/`api`/`search`/`mcp`/`frontend`)·디렉토리·"DB 계층" 같은 기존 어휘를 대체하지
않으며, 코드나 문서에 이 명칭의 사용을 강제하지 않는다. 명칭을 지금 고정하지 않는 이유:
다섯 구분의 경계는 커넥터·큐레이션이 실제로 생길 때 옮겨질 수 있다. 설명에 필요한 만큼만
쓰고, 강한 용어 고정은 그 필요가 확인된 뒤에 한다.

**결정 3 — Web UI는 여러 소비 인터페이스 중 하나다.** Web UI·REST API·MCP는 같은 services
계층을 소비하는 대등한 인터페이스이며, Web UI가 플랫폼의 본체가 아니다.
`PROJECT_CONTEXT.md`의 목표 파이프라인은 MCP를 "(선택)"으로 표기하지만 — 그 문서는 외부
불변 참조라 고치지 않는다 — 우리는 MCP를 선택이 아니라 **1급 인터페이스로 승격**해 구현했다:
별도 프로세스(ADR-008), 전용 사용자 컨텍스트(ADR-025), REST와의 검색 응답 동등성 테스트. 문서에서
"플랫폼 안에서"가 Web UI를 가리키는 용법은 더 쓰지 않는다 — 화면을 가리킬 때는 "Web UI에서"로
쓴다 (기존 ADR 본문은 결정 당시의 기록이므로 소급 수정하지 않는다).

**결정 4 — 발전 경로는 ROADMAP의 단계를 기준으로 삼는다.** 기능 후보를 개별로 저울질하지
않고, `ROADMAP.md`의 단계적 발전 경로(신뢰 가능한 파이프라인 → 프로그래매틱 플랫폼 → 외부
소스 연결 → 지식 큐레이션 → Living LLM Wiki)에 비추어 채택 여부와 순서를 정한다. 각 단계의
착수 조건과 선행 ADR은 ROADMAP에 있다. 큐레이션·위키 단계는 ADR-015 결정 3(생성 LLM
미탑재)과 긴장이 있으며, 그 재검토는 해당 단계 착수 시점의 별도 ADR로 한다 — 지금 결정 3은
유효하다.

**트레이드오프**: 정의가 넓어지면 "무엇이든 된다"로 흐를 위험이 있다. 경계는 ROADMAP의
"하지 않는 것" 절이 계속 지키고, 1차 범위(PRD 핵심 기능)는 이 ADR로 재편하지 않는다. 대회
산출물의 서사도 그대로다 — 심사에 보여줄 것은 여전히 코어 계약(정합성·복구·검색)이며, 이
ADR은 그 계약의 소비 주체를 넓히는 문서다.

### ADR-032: PRD 기준선을 제품 정의에서 재도출한다 — 1차 소비자·핵심 능력·Identity 요구사항
**상태**: 2026-08-14 신규. ADR-031의 다음 단계이며, ADR-031 트레이드오프가 미뤄 둔 PRD 재편("1차 범위는 이 ADR로 재편하지 않는다")을 수행한다.

**맥락**: 기존 PRD는 제품을 웹서비스 관점에서 설계하던 시기의 산물이다. ADR-031이 제품 정의를 플랫폼으로 확장했지만 PRD 본문은 재편하지 않았다. 사용자 지시로 **기존 구현을 정당화하지 않고** 문제 → 사용자 → 가치 → 경계 → 핵심 능력 → 하지 않는 것 → 발전 경로 순서로 제품을 다시 도출해 PRD를 전면 교체했다. 기존 결정과 일치하는 항목은 "이미 있어서"가 아니라 문제에서 같은 결론이 다시 나왔기 때문에 유지된 것이다. 결정의 전문은 PRD 본문이 담고, 이 ADR은 목록과 근거만 기록한다.

**결정 1 — AI 에이전트·프로그램을 1차 소비자로 명시한다.** Web UI는 축소되지 않는다 — 완전한 검색·소비 인터페이스이며, 큐레이션과 계약 가시화가 고유 역할이다. 심사위원은 사용자 목록에서 제외한다 — 대회는 제약 조건과 배포 마일스톤이지 사용자 니즈가 아니다.

**결정 2 — 기능 목록 대신 핵심 능력 C1~C5로 정의한다.** 기존 핵심 기능 1~7의 내용(정직성 조항 포함)은 능력 아래로 재배치해 보존한다. 프로그래매틱 공급은 C4의 일부로 승격하되 **미착수 상태를 명기**한다 — 정의가 구현을 앞서는 유일한 항목이며, 착수 시기·조건은 ROADMAP 1단계가 정하고 1차 제출 범위는 바뀌지 않는다. 정합성 관측 가능성은 계약의 부속 설명이 아니라 독립된 제품 표면(C2)이다 — "지금 인덱스가 원본과 맞는가"에 쿼리로 답하는 능력이 차별점의 증명 수단이다.

**결정 3 — 원본 비보관을 제품 원칙으로 승격한다.** MVP 제외 항목이 아니라 경계 절의 원칙이다. 단, 원본의 authoritative source가 어디인지는 입력 방식에 따라 달라질 수 있으며 외부 소스 연동 시 별도 정책으로 정한다 — 지금 확정하지 않는다.

**결정 4 — Identity·인증·권한 요구사항을 PRD에 신설한다.** Authorization은 코어(열람 술어 하나, 전 경로 공유), Identity는 코어의 어휘(인터페이스 중립 주체), Authentication은 인터페이스별 구현이다. R1~R6과 IA-1~3의 전문은 PRD §6이 정본이다. 제품 수준에서 확정하지 않는 것: 프로그램 주체 모델(위임 토큰 vs 서비스 주체) · 자격증명 scope 체계 · 원격 MCP transport — 전부 착수 시점의 ADR로 미룬다. 미인증의 두 형태는 **untrusted anonymous / trusted local context**로 구분해 부른다(ADR-025·028이 이미 구현한 2단 구조의 명명).

**결정 5 — 제품 경계의 정본을 PRD 「하지 않는 것」 절로 옮긴다.** 종전 `CLAUDE.md`는 "제품 경계와 발전 경로의 기준은 ROADMAP.md"로 규정했으나, 새 기준선에서 하지 않는 것은 제품 정의의 일부다. **발전 경로의 정본은 계속 ROADMAP이다.** ROADMAP 「하지 않는 것」 절은 확장 후보 판단에 직접 걸리는 항목의 요약으로 남기고 정본 표시를 단다. 이유: 두 문서가 각자 완전한 목록을 유지하면 드리프트가 반복된다 — 이 기준선 리뷰에서 실제로 PRD 8항 vs ROADMAP 3항의 어긋남이 발견됐다.

**트레이드오프**: PRD가 미구현 능력(C4의 공급 절반)을 정의에 포함하므로, 상태 표기를 소홀히 하면 과장이 된다. C4의 미착수 명기와 능력 표의 상태 열이 그 방지 장치이며, C5는 ADR-020 결정 4의 표현("DB 프로세스 장애 복구 검증 · 노드 승격 미검증")을 그대로 따른다. ADR 과거 본문은 소급 수정하지 않되, 이 개편으로 가리키는 대상이 이동한 두 곳(ADR-017 트레이드오프, ADR-031 결정 1)에는 이동처를 알리는 주석만 단다.

### ADR-033: ZIP은 브라우저에서 풀어 기존 단건 업로드로 투입한다
**상태**: 2026-08-15 신규 (M10)

**결정**: ZIP은 브라우저에서 JSZip **3.10.1**(MIT)으로 풀고, 나온 지원 문서를 기존 단건
`POST /api/documents`로 순차 투입한다. 서버 API와 스키마는 바꾸지 않는다. 중첩 ZIP은 풀지
않는다 — `.zip`은 지원 문서 확장자가 아니므로 내부 ZIP은 미지원 항목으로 건너뛴다. 재귀 해제의
깊이 제한이나 순환 판단은 도입하지 않는다.

**필터 규칙**: 지원 확장자(`pdf`·`docx`·`txt`·`md`)가 아닌 일반 항목은 업로드 목록에
**「건너뜀」으로 보여준다.** 반면 경로에 `__MACOSX`가 있거나 경로 구성요소가 `.`으로 시작하는
숨김 파일은 목록에서 아예 뺀다. 전자는 사용자가 넣은 파일이 처리되지 않은 이유라 알려야 하지만,
후자는 운영체제·압축 도구가 만든 항목이다. 사용자가 만든 적 없는 항목이 건너뜀 목록을 채우면
실제 미지원 이유가 묻힌다.

**이유**: ADR-017의 원본 파일 비보관 결정에서 따라온다. 원본 파일을 보관하지 않는 제품이
아카이브 자체를 서버로 받으면 zip bomb·경로 탈출(`../`)·파일명 인코딩 처리를 서버가 떠안는다.
브라우저에서 해제하면 서버로 나가는 것은 기존과 똑같은 개별 문서뿐이고, 각 문서는 이미 있는
업로드 경계와 DB 트리거 파생 계약을 그대로 지난다. ADR-031의 플랫폼 경계에서도 이는 새 코어
진입점이 아니라 Web UI 공급 인터페이스의 입력 편의다.

**트레이드오프**: 해제가 사용자 브라우저 메모리에서 일어나므로 아주 큰 아카이브는 탭의 자원
한계에 걸린다. 서버에는 배치 개념이 없어 일부 파일이 실패해도 앞서 성공한 파일은 배치 단위로
롤백되지 않으며, 업로드 목록의 파일별 상태 행이 성공·실패·건너뜀을 대신 보여준다.

### ADR-034: 프로그램 인증은 사람이 발급하는 위임 API 토큰으로 한다
**상태**: 2026-08-15 신규 (M11-c)

**결정 1 — 서비스 주체를 만들지 않고 사람 계정의 위임 토큰을 쓴다.** 사용자가 발급한 API
토큰은 그 사용자의 주체와 열람 범위로 해석된다. `users` 스키마는 바꾸지 않는다. 이는 PRD §6
IA-1의 비인간 주체 확장 가능성을 닫지 않으면서, 사람임을 전제하는 필드나 정책을 지금 추가하지
않는 최소 구현이다. 자체 계정을 가진 서비스 주체는 외부 소스와 provenance가 들어오는 ROADMAP
2단계에서 다시 판단한다.

**결정 2 — 원문은 발급 응답에 한 번만 반환하고 DB에는 salt 없는 SHA-256 해시를 저장한다.**
토큰은 `secrets.token_urlsafe(32)`로 만든 256비트 고엔트로피 비밀이라 사람 비밀번호처럼 사전
공격을 막기 위한 salt·비용 KDF가 필요하지 않다. 오히려 salt를 두면 인증할 때 토큰 해시를
인덱스로 찾지 못하고 전 행을 읽어 KDF를 수행해야 한다. `sessions.token`이 원문을 저장하는 것과
갈라지는 이유는 노출 창이다. API 토큰은 장기간 CI·스크립트 설정에 남지만 세션은 브라우저의
단기 HttpOnly 쿠키다. DB 덤프만으로 장수명 자격증명을 사용할 수 없게 하는 쪽을 택했다.

**결정 3 — scope는 `read`와 `read_write` 두 단계이며 기본값은 `read`다.** 읽기 전용 자동화가
쓰기 권한을 받을 필요가 없게 해 IA-2의 최소 권한을 가장 작은 체계로 충족한다. 문서·태그 같은
리소스별 scope 세분화는 현재 사용 사례가 없어 명시적으로 하지 않는다.

**결정 4 — 만료는 두지 않고 행 삭제로 독립 폐기한다.** IA-2가 요구하는 것은 각 자격증명의
독립 폐기이며 자동 만료가 아니다. 고정 만료는 정상 커넥터를 어느 날 조용히 멈추게 한다. 사용자는
토큰 목록에서 하나의 행만 삭제할 수 있고, 사용자 삭제 시 FK `ON DELETE CASCADE`가 전부 폐기한다.

**결정 5 — Authorization Bearer를 쿠키보다 먼저 해석하며, Bearer가 있으면 실패해도 쿠키로
폴백하지 않는다.** 폴백하면 폐기된 토큰을 보낸 요청이 로그인 쿠키로 성공해 폐기 효력이 보이지
않고, `read` 토큰도 쿠키 세션의 `read_write` 권한으로 조용히 승격된다. Bearer가 없는 요청만 기존
세션 쿠키를 사용한다. **`Basic` 같은 다른 스킴은 쿠키 판정으로 넘어간다** — 그 근거 두 가지는
토큰이 실제로 제시됐을 때만 성립하고(폐기할 토큰도 좁힌 scope도 없다), Authorization을 덧붙이는
프록시 뒤에서 브라우저 세션이 조용히 끊기는 편이 더 나쁘다.

**결정 6 — 토큰 발급·목록·폐기와 `/api/admin/*`는 세션 전용이다.** 토큰으로 새 토큰을 발급할
수 있으면 기존 토큰을 폐기해도 스스로 자격증명을 재생하는 체인이 생긴다. 문서 공급용 토큰에
계정 관리 권한까지 주는 것도 IA-2의 최소 권한과 맞지 않는다. 따라서 관리자 계정이 발급한
`read_write` 토큰도 이 경계를 넘지 못한다.

**ADR-028과 R4의 정합 — 식별자와 자격증명은 다르다.** ADR-028이 제거한
`X-User-Id: alice`는 검증 절차 없는 **주체 주장**이라 누구나 쓸 수 있었다. Bearer도 헤더로
전달되지만, 값은 서버가 발급하고 해시로 보관한 **비밀의 소유 증명**이다. 서버는 검증에 성공한
뒤에야 연결된 사용자 행에서 주체를 해석한다. 따라서 PRD §6 R4의 “주체 식별자를 요청 데이터로
받지 않는다”는 그대로 지켜진다. `test_token_access.py`는 사용자명·임의 문자열·폐기된 토큰·
변조 토큰·저장된 해시 문자열로는 인증되지 않고, 유효한 원문 토큰만 발급자 주체가 되는 것을
양방향으로 고정한다.

**기각한 대안**:

- **서비스 주체의 자체 계정**은 provenance·조직 소유 정책 없이 도입하면 `users`와 권한 모델만
  넓힌다. ROADMAP 2단계에서 다시 본다.
- **원문 저장**은 조회가 단순하지만 DB 덤프가 곧 장수명 자격증명 유출이 된다.
- **scope 세분화**는 현재 클라이언트가 요구하지 않는 정책과 테스트 조합을 만든다.
- **만료 강제**는 독립 폐기보다 안전성을 더 증명하지 않으면서 무인 커넥터를 예고 없이 멈춘다.

**영향 범위 실측**: `git diff --stat main -- backend/mcp_server frontend/src` 결과는 출력이 없었다.
즉 MCP 서버와 프론트엔드는 각각 **변경 0줄**이다. 인증은 HTTP 경계와 공통 인증 서비스에만
추가됐고, stdio MCP의 `MCP_USER_ID` 계약(ADR-025)과 Web UI의 세션 흐름은 바뀌지 않았다.

**남은 한계**:

1. 문서 소유권은 `owner_id`의 username 텍스트인데 인증 주체는 `users.id` UUID라 어휘 이중화가
   남아 있다. 이번에는 건드리지 않았으며 서비스 주체 도입 전의 선행 정리 대상이다.
2. 위임 토큰으로 커넥터가 넣는 문서는 발급자 개인 계정에 귀속된다. 조직 소유·시스템 소유
   문서라는 개념은 아직 없다.
3. 만료와 사용 이력이 없다. 유출된 토큰은 사람이 폐기할 때까지 유효하며 마지막 사용 시점도
   알 수 없다. 감사는 이번 범위의 non-goal이었다.

### ADR-035: 텍스트 공급 API는 코어에 텍스트 우선 진입점을 만든다 — 원본 파일 없는 문서
**상태**: 2026-08-15 신규 (M11-b)

**결정 1 — 코어에 텍스트 우선 진입점을 둔다.** 라우터가 가짜 파일명을 만들어 기존 파일
진입점을 재사용하지 않는다. `services/documents.py`에 `create_text_document`를 두고,
`create_document`는 파일 형식 판별·파싱 뒤 같은 `_insert_document`로 넘기는 어댑터로 축소한다.
`git diff --stat main -- backend/app/services/`의 실제 변경량은
**1 file changed, 62 insertions(+), 6 deletions(-)**다.

이 수치는 인터페이스를 하나 추가하는 데 코어가 필요해서 바뀐 양이 아니라, 코어의 입력 어휘를
파일에서 문서 텍스트로 바로잡은 초기 비용이다. 따라서 PRD §4 판별 기준 3의 "인터페이스 추가 시
코어 변경 0줄"을 충족했다는 증거도, 깨뜨렸다는 증거도 아니다. 이 진입점 위에 별도 코어 변경 없이
MCP 쓰기 도구(M11-d)를 얹을 때 그 기준을 처음 실측한다.

라우터에서 텍스트를 임의 파일명과 바이트로 encode해 `create_document`에 넣는 대안은 기각했다.
그 방식의 코어 변경 0줄은 경계가 깊어서가 아니라 새 인터페이스가 파일 중심 코어 어휘에 자신을
구겨 넣어서 나온 숫자다. `scripts/seed_demo.py`가 쓰던 가짜 파일명 우회를 공식 API 표면으로
승격시키며, 실제로 존재하지 않는 원본 파일을 데이터에 남긴다.

**결정 2 — 귀속과 출처를 분리한다.** 직접 공급 문서의 `filename`은 `NULL`이다. 요청은
`filename`과 `owner_id`를 받지 않는다. 소유자는 세션에서만 해석해 PRD §6 R4의 사칭 불가를
지키고, 출처(provenance)는 R6에 따라 외부 소스 연결 시점의 별도 스키마로 미룬다. 이번 API는
존재하지 않는 출처 값을 꾸며내지 않는다.

**결정 3 — 문서 텍스트가 상위 개념이다.** `documents.content`의 정본 명칭은 **문서 텍스트**다.
그중 파일 업로드 경로에서 만들어지고 `filename IS NOT NULL`인 값이 **추출 텍스트**다. ADR-017의
원본 파일 / 추출 텍스트 / 텍스트 버전 구분은 폐기하지 않고, 상위 개념 하나를 얻는다. 원본 파일이
없는 문서의 Web UI 편집 레이블은 "문서 텍스트"로 표시한다.

직접 공급 텍스트도 "추출 텍스트"라 부르고 추출을 항등 변환으로 해석하는 대안은 택하지 않았다.
실제로 추출한 대상이 없는데 기존 단어를 유지하면, 구분을 지키려다 "추출"의 의미를 비워 버린다.

**결정 4 — 텍스트 공급 형식은 `txt`·`md`다.** PDF·DOCX의 base64 JSON 공급은 도입하지 않는다.
바이너리 입력은 기존 multipart 업로드가 담당하고, 텍스트 API는 공급자가 이미 가진 텍스트만 받는다.

**결정 5 — CORS를 열지 않는다.** 비브라우저 소비자인 curl·서버 간 클라이언트·MCP에는 CORS가
적용되지 않는다. 현재 HTTP 인증은 세션 쿠키뿐이므로 브라우저 서드파티 origin을 허용하면
비대화형 인증 없이 쿠키 기반 쓰기 요청의 CSRF 표면만 넓어진다. 브라우저 서드파티 소비는 이번에
열지 않으며, M11-c의 비대화형 자격증명 이후 origin과 자격증명 전달 정책을 함께 재검토한다.

**결정 6 — 요청 본문 크기 가드를 라우터에 장식으로 두지 않는다.** 설치된 FastAPI의
`fastapi/routing.py` 요청 핸들러를 직접 확인하면 `body_bytes = await request.body()`가 먼저
실행되고 그 뒤 `solve_dependencies(...)`가 호출된다. 따라서 라우터나 의존성의
`Content-Length` 검사는 JSON 본문이 이미 메모리에 올라온 뒤 실행되어 전송 계층 상한이 되지 못한다.
실효 애플리케이션 경계는 서비스의 `MAX_EXTRACTED_TEXT_LENGTH = 500_000`자이며, 초과 요청은
400으로 거부하고 테스트가 문서 미저장까지 단언한다. 전송 계층 상한은 리버스 프록시나 본문을
읽기 전 차단하는 미들웨어의 책임이며 이번 범위에는 추가하지 않는다.

**이유**: 파일 업로드와 JSON 텍스트 공급이 서로 다른 입력 어댑터를 쓰면서도 한 INSERT 헬퍼와
DB 트리거 계약을 공유한다. 실제 테스트는 두 경로 모두에서 임베딩 잡·텍스트 버전·관계 edge·
위키링크 파생이 같은 DB 경로로 생성됨을 확인한다. 독립 예제는 `backend` 패키지를 import하지 않고
표준 라이브러리만 사용하며, 로그인·텍스트 공급·상태 폴링의 HTTP 경로를 코드로 보여준다.

**트레이드오프**:

1. `examples/ingest_text.py`가 실제 서버에 접속해 완주하는지는 CI가 확인하지 않는다. pytest가
   지키는 것은 의존성 독립, 문법 유효성, 예제가 쓰는 세 경로와 등록 라우트의 대조뿐이다. 실행
   확인에는 API·워커·DB를 함께 기동해야 한다.
2. 인증은 여전히 세션 쿠키뿐이라 프로그램 주체는 없다. 예제도 사람의 username/password로
   로그인해 쿠키를 얻는다. PRD §6의 프로그램(REST)용 비대화형 자격증명은 계속 미구현이며,
   M11-c와 예약된 ADR-034의 몫이다.
3. **전송 계층 상한이 두 입력 경로에서 비대칭이다.** multipart 업로드에는
   `MAX_UPLOAD_BYTES`(10MB)가 걸리지만, JSON 텍스트 공급은 결정 6에 따라 본문을 전부
   메모리에 읽은 뒤 500,000자 검사로만 거른다. 즉 500KB짜리 거부 응답을 받기까지 그보다
   훨씬 큰 본문이 버퍼링될 수 있다. 이는 결정 6의 의도적 귀결이며, 실효 방어는 리버스
   프록시나 본문을 읽기 전 차단하는 미들웨어가 들어올 때 생긴다.

**2026-08-15 후속**: 트레이드오프 2의 인증 공백은 ADR-034의 위임 API 토큰으로 해소됐다.
예제는 이제 `--token`으로 세션 쿠키 없이 공급할 수 있다. 트레이드오프 1의 실서버 완주 미검증과
트레이드오프 3의 전송 계층 상한은 그대로다.

**2026-08-15 후속 (M11-d)**: 위 결정 1이 예약한 판별 기준 3의 첫 실측을 ADR-036에서 수행했다.
MCP `create_document`는 기존 `create_text_document`를 재사용했고, 해당 인터페이스 추가 커밋의
`backend/app/`·`backend/migrations/` 변경은 **0줄**이었다. 원 문단은 이 실측이 예약된 맥락으로
보존한다.

### ADR-036: MCP 쓰기는 로컬 사용자 컨텍스트로 문서 텍스트를 공급한다
**상태**: 2026-08-15 신규 (M11-d)

**결정 1 — `MCP_USER_ID`가 공급 주체이자 `owner_id`다.** `create_document`는 프로세스에
주입된 `MCP_USER_ID`를 소유자로 사용하며, 미설정이면 쓰기를 거부한다. ADR-025의 trusted local
context가 주체 없이 허용하는 범위는 public **읽기**까지다. 주체 없는 공급은 삽입 시점에 소유자와
공개범위를 확정하라는 PRD §6 R5를 만족할 수 없다.

**결정 2 — 도구 인자는 문서 속성만 받는다.** 실제 인자는 `title`·`content`·`content_type`
(`txt`·`md`, 기본 `md`)·`tags`·`visibility`(기본 `public`)다. `owner_id`나 다른 주체 식별자는
받지 않으며, 공개범위도 `public`·`private` 밖의 값을 받지 않는다. 이는 REST에서
`X-User-Id`를 제거한 ADR-028과 같은 R4 사칭 방지 결정이다. `visibility` 기본값은 REST와 같은
`public`이다. 같은 서비스 함수의 기본 계약을 인터페이스마다 달리하면 C4의 “하나의 계약 위에서
공급”이 성립하지 않으므로, 차이를 만들지 않고 도구 설명문에 기본값을 명시한다.

**결정 3 — 텍스트 의미론은 ADR-035를 그대로 재사용한다.** MCP가 새로 결정하는 입력 의미론은
없다. 형식은 `txt`·`md`이고, 원본 파일이 없으므로 `filename IS NULL`이며, 저장되는 값은
“문서 텍스트”이지 “추출 텍스트”가 아니다. 도구는 `services/documents.py:create_text_document`를
직접 호출하므로 REST 텍스트 공급과 같은 INSERT·DB 트리거·파생 계약을 따른다.

**결정 4 — 최소형은 생성 도구 하나다.** update/delete는 동시성·파괴적 호출 승인 의미론을
각각 결정해야 하므로 넣지 않는다. 원격 transport는 인증과 다중 사용자 격리를 함께 설계해야 하므로
stdio 단일 사용자 경계를 유지한다. PDF·DOCX는 바이너리·파일명 의미론이 필요한 기존 multipart
업로드의 몫이며, 텍스트 도구에 base64 공급을 추가하지 않는다.

**결정 5 — 공개범위 계약은 코어 INSERT 경계가 스스로 지킨다.** `VISIBILITY_VALUES`와 검증을
두 생성 경로가 공유하는 `_insert_document` 한 곳에 두어, REST를 거치지 않는 MCP도 같은 계약을
적용받는다. REST 라우터는 Pydantic `Literal`이 먼저 막아 잘못된 값이 서비스까지 도달하지 않으므로
고치지 않았다. 이 보강은 MCP 인터페이스 비용에 섞지 않고 선행 step으로 분리했다.

**판별 기준 3 실측**: 선행 코어 보강(step 0)은 `backend/app/`에서
**2 files changed, 9 insertions(+), 1 deletion(-)**였다. 이후 MCP 인터페이스 추가(step 1)는
`backend/mcp_server/`·`backend/tests/`에서 **3 files changed, 198 insertions(+), 2 deletions(-)**였고,
같은 커밋의 `backend/app/`·`backend/migrations/` 변경은 **0줄**이었다. 즉 ADR-035가 만든 텍스트
우선 진입점 위에 두 번째 공급 인터페이스를 얹을 때 코어 변경 0줄이라는 PRD §4 판별 기준 3을
처음 실측했다. step 0의 9삽입·1삭제는 이 수치를 만들기 위한 인터페이스 비용이 아니라, 기존 파일·
REST 경로에서는 라우터 검증에 가려져 있던 코어 공개범위 계약의 비대칭을 메운 별건이다. 참고로
`origin/main..HEAD` phase 전체의 `backend/mcp_server/`·`backend/tests/` 통계는 step 0의 서비스
직접 호출 테스트 45줄까지 포함해 **4 files changed, 243 insertions(+), 2 deletions(-)**다. 이를
step 1 비용으로 유리하게 재분류하지 않고 커밋 경계로 분리했다.

**이유**: MCP 클라이언트도 Web UI·REST와 같은 문서 텍스트 진입점과 DB 파생 계약을 사용한다.
주체와 공개범위를 호출 경계에서 위장할 수 없게 하고, 서비스의 기존 의미론을 재사용해야 AI
에이전트가 공급자가 되어도 정합성·귀속·열람 계약이 약해지지 않는다.

**트레이드오프**:

1. ADR-025의 stdio 단일 사용자 한계가 그대로다. 여러 사용자가 서버 하나를 공유할 수 없다.
2. MCP 클라이언트가 도구 호출을 사용자에게 승인받는 신뢰 모델에 이제 읽기뿐 아니라 문서 공급
   권한도 얹힌다. 잘못 승인한 호출은 해당 `MCP_USER_ID` 소유의 실제 문서를 만든다.
3. 공개범위의 DB `CHECK` 제약은 이번에 추가하지 않았다. 모든 현재 생성 경로는 코어 가드를
   통과하지만, 향후 서비스 밖에서 `documents`에 직접 INSERT하는 코드나 운영 SQL은 잘못된 값을
   저장할 수 있다. DB 계층까지 강제하려면 별도 마이그레이션과 DB 행동 테스트가 필요하며 이번
   문서·MCP 범위에는 포함하지 않았다.
4. **`owner_id`가 실존하는 사용자인지는 검증하지 않는다.** `documents.owner_id`는 `text NOT NULL`
   뿐이고 `users` FK가 없다. `MCP_USER_ID`에 오타가 있으면 문서는 저장되지만 그 계정으로 로그인한
   사람에게는 보이지 않는다 — 비공개로 만들었다면 아무에게도 보이지 않는다. Web UI는 세션이,
   REST는 세션 또는 위임 토큰이 실존 사용자를 보장하므로 MCP가 검증되지 않은 `owner_id`로 INSERT
   하는 유일한 경로다. 막으려면 `users` 조회나 FK가 필요하고, 둘 다 이번 범위 밖의 DB·서비스
   결정이다.

**2026-08-15 후속 (코드 리뷰)**: 결정 1의 "미설정이면 거부"를 빈 값·공백까지로 좁혔다.
`MCP_USER_ID=""`는 `None`이 아니라 빈 문자열로 들어와 `if user_id is None` 검사를 통과했고,
위 트레이드오프 4처럼 `owner_id`에 제약이 없어 **소유자가 빈 문자열인 문서가 조용히 저장될 수
있었다.** `not user_id or not user_id.strip()`로 좁히고 세 형태(미설정·빈 값·공백)를 파라미터
테스트로 고정했다. 이 대응은 `backend/app/`을 건드리지 않았으므로 위에 기록한 판별 기준 3의
실측(코어 변경 0줄)은 그대로다.

### ADR-037: 과거 텍스트 버전을 조회하고, 복원은 새 버전으로 만든다
**상태**: 2026-08-18 신규.

**배경 — 이력은 쌓이는데 꺼낼 수단이 없었다**

ADR-017이 인라인 편집을 도입하면서 `document_versions`에 이력이 쌓이기 시작했다. 그 이력의
용도는 정합성 검증 쿼리(`c.version <> d.version`)와 `/admin/status` 카운터를 움직이는 것이었고,
화면에는 버전 번호와 시각만 보였다. 과거 버전의 본문을 읽거나 되돌리는 경로는 만들지 않았다.

지정과제 원문의 기능 목록은 **"메타데이터/버전 관리"**를 명시한다. 이력 축적만으로 이 항목에
답하는 것은 얇다 — 사용자가 버전 목록을 보면서 그 내용을 볼 수 없고 되돌릴 수도 없으면, 그것은
관리라기보다 기록이다. 조회·복원을 채택한다.

**결정 1 — 과거 버전의 본문을 조회한다.** `GET /api/documents/{id}/versions/{version}`.
열람 범위는 문서 본체와 같은 술어(`VISIBLE_TO_USER`)를 쓴다. 볼 수 없는 문서의 버전은 존재하지
않는 것처럼 404다 — 버전 번호의 존재 자체도 누출하지 않는다 (ADR-027).

**결정 2 — 복원은 되감기가 아니라 새 버전 생성이다.**
`POST /api/documents/{id}/versions/{version}/restore`는 그 버전의 본문을 현재 내용으로 삼아
**새 버전을 만든다.** `version`을 감소시키거나 이력 행을 삭제하지 않는다. 되감기는 그 사이 버전에서
만들어진 청크·관계가 무엇을 기준으로 하는지 답할 수 없게 만들고, 이력이 append-only가 아니게
되는 순간 정합성 검증 쿼리의 기준이 흔들린다.

구현은 `services/documents.py:update_extracted_text`를 **그대로 호출한다.** 별도 UPDATE 경로를
만들지 않는다 — 낙관적 잠금·길이 검증·`content_hash` 갱신·트리거 발화가 편집과 완전히 같아야
하고, 두 경로로 나뉘면 한쪽만 고쳐지는 자리가 생긴다.

**결정 3 — 복원도 호출자가 읽어온 현재 버전을 함께 받는다.** 편집과 같은 409 규칙이다. 다른
탭이나 다른 클라이언트가 먼저 편집했다면 복원은 실패해야 한다. 복원은 파괴적으로 보이지 않지만
현재 내용을 밀어내므로 편집과 같은 무게다. 요청 필드는 `current_version`으로 두어 경로의
`{version}`(되돌릴 과거 버전)과 이름이 겹치지 않게 한다 — 편집의 `version`을 그대로 쓰면 한
요청 안에 뜻이 다른 `version`이 둘 생긴다.

**결정 4 — 현재와 같은 내용으로 복원해도 막지 않는다.** `content_hash`가 현재와 같아도 SET 절에
컬럼이 언급되므로 트리거는 발화하고, 새 버전이 생기며 재임베딩이 돈다. 이를 "변화 없음"으로
판정해 거절하지 않는다. 사용자가 명시적으로 요청한 행위이고 결과가 정확하며, 예외 분기를 두면
"언제 새 텍스트 버전이 생기는가"의 규칙이 하나 늘어난다.

**범위 밖**

- **논리 삭제(휴지통)** — 열람 범위·그래프 순회·검색·집계 전 경로에 `deleted_at` 조건이 번지므로
  별개 결정이다. 하드 삭제를 유지한다.
- **MCP 복원 도구** — ADR-036 결정 4가 MCP 쓰기를 생성 하나로 한정했고, 그 근거(파괴적 호출의
  승인 의미론을 따로 결정해야 한다)가 복원에도 그대로 적용된다.
- **버전 간 차이(diff) 표시** — 조회·복원과 독립이며 UI 결정이 따로 필요하다.

**트레이드오프**: 복원 한 번마다 재임베딩이 한 번 돈다. 되감기였다면 이미 있는 청크를 재사용할 수
있었겠지만, 그 대가로 이력의 append-only 성질과 정합성 기준을 잃는다. 임베딩 비용은 워커가
비동기로 흡수하고 그 사이 검색은 이전 벡터로 계속되므로 (ADR-015), 사용자가 보는 지연은 배지
상태뿐이다.

### ADR-038: 워커 프로세스는 감독자가 되살리고, 재시도 예산은 크래시 경로에도 적용한다
**상태**: 2026-08-19 신규.

**배경 — 관측은 되는데 복구가 안 되는 구간이 있었다**

ADR-020이 검증한 것은 **DB 프로세스** 장애 복구다. Patroni가 PostgreSQL을 재기동하고
(감지 0.05~8.5초 · 서비스 재개 13.0~22.4초), API·워커는 끊긴 연결을 재수립하며(ADR-023), 큐가 DB 안에
있어 미처리 잡이 유실 없이 재개된다. 그런데 **워커 프로세스 자신이 죽는 경우**는 이 그림에
없었다. 배포는 `nohup` 맨 프로세스이고 감독자가 없어, 워커가 SIGKILL·OOM으로 사라지면
아무것도 되살리지 않는다.

결과는 특정 문서 하나의 실패가 아니라 **임베딩 파이프라인 전면 정지**다. API는 살아 있어
업로드를 계속 받으므로 `embedding_jobs`에 `pending`이 무한히 쌓이고, 새 문서는 영원히
검색되지 않으며 수정된 문서는 옛 벡터로 검색된다. 다행히 조용히 죽지는 않는다 —
`/admin/status`의 `pending`이 계속 오르고 `recovery_pending`·정합성 카운터가 0으로 돌아오지
않아 **정지 사실은 관측된다.** (`recovery_pending`은 임계를 넘긴 `processing` 건수라 크래시
시점의 값에서 멈춘다 — 계속 오르는 것은 `pending`이다.) ADR-015가 약속한 "어긋난 구간의 관측"은 정확히 작동했고,
빠진 것은 복구뿐이었다.

호스트 OOM은 가정이 아니다. t3.large 8GB에 BGE-M3가 워커(2233MB)·API(2006MB) 두 벌로
상주하고 swap이 없다 (`SETUP_OPENSQL.md` 측정값). 워커는 OOM killer의 1순위 표적이다.

**결정 1 — 감독은 systemd 유닛으로 하되, 재부팅 생존은 도입하지 않는다.**

기존 결정이 systemd를 배제한 근거는 *"OpenSQL 자신이 nohup 맨 프로세스로 도는 설치라 앱만
systemd로 감싸도 DB가 없어 의미가 없다"*였다. 이 논거는 **재부팅에 대한 것이지 crash에 대한
것이 아니다.** 두 시나리오는 DB의 생사가 다르다.

| 시나리오 | DB | 워커 재기동의 의미 |
|---|---|---|
| 호스트 재부팅 | Patroni·PostgreSQL·OpenProxy 전부 정지 | 없음 — 기존 논거 유효 |
| 워커만 crash | **살아 있음** | 있음 — 기존 논거가 다루지 않던 칸 |

그래서 기존 결정을 뒤집지 않고 빈 칸만 채운다. `scripts/openarchive-worker.service`는
`Restart=always`를 갖되 **`[Install]` 섹션을 두지 않는다** — `systemctl --user enable`이
거부되고 `is-enabled`가 `static`으로 남아, 부팅 자동 기동이 실수로 켜지는 것을 파일 구조가
막는다. 인스턴스를 켤 때마다 `deploy_app_host.sh`를 돌리는 절차는 그대로다.

`StartLimitIntervalSec=300` · `StartLimitBurst=5`로 재기동을 제한한다. 메모리 압박으로 죽었다면
즉시 되살려도 또 죽고, 무한 재기동은 같은 호스트의 API까지 끌어내린다. 포기해도 상태 카운터가
정지 사실을 계속 노출한다.

**system 유닛이 아니라 user 유닛이다 — SELinux 때문이다.** 처음에는 `/etc/systemd/system/`에
`User=rocky`로 두었으나 EC2 실측에서 `203/EXEC Permission denied`로 기동하지 못했다. Rocky 9는
SELinux Enforcing이 기본이고 venv가 홈 아래(`user_home_t`)에 있어, system 유닛의 도메인(`init_t`)이
실행 파일을 **찾는 단계**에서 막힌다. `SELinuxContext=`로 exec 도메인만 바꿔도 경로 탐색에서
그대로 걸렸다. `~/.config/systemd/user/`의 user 유닛은 사용자 세션 매니저가 실행하므로 nohup으로
돌리던 때와 같은 도메인이며 **보안 수준이 낮아지지 않는다.** 세션이 끊겨도 유지되도록
`loginctl enable-linger`가 필요하고, 배포에서 sudo를 쓰는 곳은 그 한 줄뿐이다. 로그는
`journalctl --user -u openarchive-worker`로 sudo 없이 읽는다.

> 대안이던 "앱을 `/opt`로 옮긴다"는 채택하지 않았다. SELinux 관점에서는 정석이지만 rsync 대상과
> 배포 절차 전체가 바뀌고, user 유닛으로 같은 목적이 달성된다.

**적용 범위는 워커 하나로 좁힌다.** API·프론트는 죽으면 사용자가 즉시 알아차리지만, 워커는
화면이 멀쩡한 채로 파이프라인만 멈춘다 — 감독이 필요한 비대칭이 여기에 있다.

**결정 2 — 재시도 예산을 좀비 회수 경로에도 적용한다.**

감독자를 붙이면 잠복해 있던 결함이 발현된다. `MAX_ATTEMPTS`는 `fail_job`(예외로 잡히는 실패)
에서만 검사되고, `claim_job`의 WHERE에는 `attempts` 조건이 없으며, `sweep_zombies`는 `status`만
되돌린다. 그래서 **워커를 반복적으로 죽이는 잡은 회수 → 재선점 → 재크래시를 무한 반복**하고,
`attempts`는 4, 5, 6으로 올라가지만 아무도 보지 않는다. 감독자가 없을 때는 워커가 한 번 죽고
끝이라 이 루프가 성립하지 않았다 — 결정 1이 발현 조건을 만든다.

`sweep_zombies`가 임계를 넘긴 잡 중 예산을 소진한 것을 `pending`으로 되돌리지 않고 job `error`
+ `documents.embedding_status='error'`로 격리한다. `fail_job`의 소진 처리와 결과가 같아야
`/admin/status`의 `error` 카운터와 UI 배지가 두 경로를 구분 없이 보여준다.

판정 순서는 `fail_job`과 동일하다: **새 `pending` 잡 확인 → 예산 소진 확인 → 회수.** 문서가 이미
수정됐다면 그 잡은 실패한 것이 아니라 수명이 끝난 것이므로 `done`으로 마감하고 `error` 배지를
달지 않는다. 순서를 뒤집으면 새 잡이 곧 `ready`로 되돌릴 문서에 거짓 `error`가 뜬다.

격리해도 청크는 지우지 않는다 — 검색은 이전 버전으로 계속되고 정합성 카운터는 어긋난 채
남는다. **격리했다고 어긋남을 숨기면 계약이 거짓말이 된다.** 재개 수단은 문서 재수정이며,
본문을 바꾸지 않고 다시 태우려면 `UPDATE documents SET content_hash = content_hash`를 쓴다.

**결정 3 — 정상 종료는 선점을 반납하고 `attempts`를 원복한다.**

`systemctl stop`이 보내는 SIGTERM에 워커가 처리 중인 잡을 마치고 멈춘다. 임베딩을 시작하기
전이었다면 `pending`으로 반납하며, 이때 **`attempts`를 되돌린다.** 배포로 워커를 세우는 것은
잡의 실패가 아니므로 예산을 소비하면 안 된다 — 원복하지 않으면 배포를 세 번 반복하는 것만으로
멀쩡한 문서가 결정 2의 소진 판정에 걸려 `error`가 된다. 결정 2와 결정 3은 짝이며, 한쪽만
도입하면 정상 문서를 격리하는 회귀가 생긴다.

반납은 부수적으로 배포마다 발생하던 5분 좀비 대기도 없앤다. 반납하지 못하고 죽어도(SIGKILL)
정합성은 깨지지 않는다 — 좀비로 남아 임계 후 회수될 뿐이다.

**결정 4 — 크래시 복구는 기존 시간 기반 판정을 유지한다 (즉시 회수를 도입하지 않는다).**

재기동한 워커가 좀비를 즉시 회수하는 방법을 검토했다. 워커는 자기 기동 시각을 알므로
"내가 기동하기 전에 `started_at`이 찍힌 `processing` 잡"은 확실히 죽은 워커의 것이고, 그러면
복구가 5분에서 재기동 시간(10초)으로 줄어든다. **채택하지 않는다** — 이 판정은 워커가 하나라는
전제 위에서만 참이고, 그 전제를 correctness 로직과 설정에 심는 비용이 5분을 줄이는 이득보다
크다. 멀티 워커로 확장할 때 반드시 걷어내야 하는 종류의 가정이다.

`pg_try_advisory_lock`으로 세션 종료를 즉시 감지하는 방안도 검토했으나 **기각한다.** OpenProxy는
풀 백엔드를 넘길 때 `RESET ALL`만 하고 `DISCARD ALL`은 하지 않아 advisory lock이 다음
클라이언트로 누수된다 — 임시 테이블과 같은 경로이며 ADR-022가 이미 실측한 함정이다.

그래서 복구 흐름은 이렇게 확정된다.

```
워커 crash → systemd 자동 재기동 → 정상 pending 잡 처리 지속
          → 기존 processing 좀비는 임계(5분) 후 회수
          → 재시도 예산 확인 → 재시도 또는 error 격리
```

**임계를 기다리는 동안에도 파이프라인은 멈추지 않는다.** 좀비는 `processing`이라 `claim_job`의
대상이 아니고, 워커는 남은 `pending` 잡을 그대로 집어간다 — 크래시의 영향은 그 잡 하나로
격리된다. 이 동작은 `test_pipeline_keeps_draining_while_a_zombie_waits_for_its_timeout`이
단언한다. 진술이 아니라 테스트가 지키는 계약이다.

**트레이드오프**

1. **크래시 복구가 최대 5분 늦다.** 결정 4의 대가다. poison job의 격리는 최대
   3 × (5분 + 재기동 10초) ≒ 15분 30초가 걸리고, 그동안 워커는 5분 주기로 죽는다. 그 사이
   다른 잡은 계속 처리되므로 처리량 손실에 그친다.
2. **배포 호스트에 systemd와 lingering이 필요해졌다.** user 유닛이라 sudo는
   `loginctl enable-linger` 한 줄에만 쓴다. 로컬 개발(`python -m app.worker`)과
   `demo_recovery.sh`(자체 워커를 띄우고 `kill -STOP`으로 세운다 — 프로세스가 죽지 않으므로
   감독자가 개입하지 않는다)는 영향을 받지 않는다.
3. **재부팅 생존은 여전히 없다.** 결정 1이 의도적으로 남긴 구멍이며, OpenSQL 자체가 그렇게
   도는 설치라 여기만 메워도 관통되지 않는다.
4. **감독자가 포기한 뒤에는 자동 복구가 없다.** `StartLimitBurst` 초과 시 유닛은 failed로
   남고 사람이 개입해야 한다(`systemctl --user reset-failed`). 관측은 `/admin/status`와
   `systemctl --user status` 양쪽에서 된다.
5. **`MemoryMax` cgroup 상한은 도입하지 않았다.** 호스트 전체 OOM 대신 워커만 정확히 죽게
   만들 수 있으나 임계값 실측이 선행되어야 한다. 미채택으로 남긴다.

**실측 (2026-08-19, EC2 t3.large · Rocky 9.7 · SELinux Enforcing · systemd 252)**

| 확인 | 결과 |
|---|---|
| 유닛 기동 | `active`. `.env`를 읽어 `provider=BAAI/bge-m3` — `WorkingDirectory`가 유효하다 |
| `kill -9` → 자동 재기동 | **PID 2855 → 2901**, 15초 내 `active` 복귀 |
| `systemctl --user stop` | 12초 후에도 `inactive` — 감독자가 개입하지 않는다. 워커 로그에 "종료 신호 — 처리 중인 잡을 마치고 멈춘다" |
| `systemctl --user enable` | 거부, `is-enabled=static` — 결정 1의 부팅 자동 기동 차단이 강제된다 |
| `StartLimitBurst` | 실제로 발동해 `Start request repeated too quickly`로 포기. 재개에 `reset-failed`가 필요했다 |
| 문서 INSERT → 임베딩 | 36초에 `ready`, 청크 2개 (BGE-M3 첫 로드 포함) |
| 좀비 회수 (attempts=1) | `pending` 회수 → 재선점(attempts=2) → `ready`. 로그 "좀비 잡 1건을 pending으로 회수" |
| 좀비 격리 (attempts=3) | `job=error` · `embedding_status=error` · `last_error=WorkerCrashLoop: …` · 청크 0 |
| 배포 사전 검사 (DB 다운) | OpenProxy만 정지한 상태에서 **실패**. 같은 상태에서 옛 `patronictl \| grep -q running`은 매치 1건으로 **통과했을 것** |
| 배포 사전 검사 (DB 정상) | "쓰기 가능 확인" 후 전체 관통 |

좀비 두 건은 `started_at`을 임계 너머로 밀어 재현했다 — 5분을 기다리지 않기 위한 조작이며
`test_worker.py`가 쓰는 방식과 같다. 회수 건수 반환값이 격리분을 세지 않는다는 계약도 로그에서
확인됐다(2건 중 1건만 "회수"로 집계).

**곁가지로 배포 사전 검사의 거짓 통과도 이 실측에서 닫았다.** 인스턴스를 켠 직후는
Patroni·PostgreSQL·OpenProxy가 전부 죽고 etcd만 살아 있는 상태인데, `patronictl list`가
DCS에 남은 마지막 기록으로 `Leader | running`을 보여주어 검사가 통과했다. 판정을 **앱이 쓸
DSN으로 `select pg_is_in_recovery()`를 던지는 것**으로 바꿨다 — 쿼리 한 번이 프로세스 생존·
네트워크·자격증명과 풀 이름·쓰기 가능 여부를 함께 확인한다. 포트 리스닝만 보는 방식은
채택하지 않았다: OpenProxy는 풀러라 백엔드가 죽어도 리스닝하고, 연결이 서더라도 Replica로
라우팅되면 마이그레이션이 read-only로 죽는다.

### ADR-039: 설치 준비는 `openarchive init` CLI가 담당한다
**상태**: 2026-08-19 신규. 초안은 038로 썼으나 같은 날 먼저 열린 PR #74(워커 감독)가 그 번호를
쓰고 있어 039로 옮겼다. **2026-08-26 결정 2 부분 철회 — 기동을 `openarchive serve`가 맡는다.**

**배경 — 첫 실행 경로가 문서에만 있었다**

도입하는 사람이 밟아야 하는 순서(연결 정보 확정 → 스키마 준비 → 준비 상태 확인)가 README의
산문으로만 존재했다. 실패는 늦게, 그리고 엉뚱한 자리에서 드러난다. 확장이 없으면
`001_extensions.sql`에서, 권한이 없으면 `002_tables.sql`에서 깨지고, 사용자는 마이그레이션
스택트레이스를 읽으며 원인을 역추적해야 한다. **무엇이 왜 필요한지는 적용 전에 알 수 있는
정보**인데 그것을 확인하는 코드가 없었다.

**결정 1 — CLI를 인터페이스 계층에 추가한다.** `backend/app/cli.py`에 `openarchive` 명령을 두고
`[project.scripts]`로 등록한다. Web UI·REST·MCP와 같은 자리이며, 로직을 새로 쓰지 않고 코어를
재사용한다 (ADR-031 결정 1). 마이그레이션 적용은 `run_migrations`, 준비 상태 판정은
`services/system.py:get_system_status`가 그대로 한다. 선례는 `scripts/create_admin.py`이며,
그것이 `services/auth.py:create_user`를 재사용한 것과 같은 관계다.

**결정 2 — 첫 버전의 범위는 "DB를 준비된 상태로 만드는 것"까지다.**

| 한다 | 하지 않는다 |
|---|---|
| 연결 정보 입력(대화형 1회 또는 `--dsn`) | API·워커·프론트 기동 |
| 연결 확인과 서버 정보 표시 | DB 자동 탐색·설치 |
| capability 확인 — PG 버전·`vector`·`pg_trgm`·CREATE 권한 | 문서 공급(ingest) |
| 기존 스키마 충돌 확인 | 관리자 계정 생성(`create_admin.py`가 한다) |
| 마이그레이션 적용과 준비 상태 보고 | 원격 실행·오케스트레이션 |
| `backend/.env`의 `DATABASE_URL` 기록 | |

프로세스 기동을 삼키지 않는 이유는 ADR-007이다 — 앱을 컨테이너로 감싸지 않고 네이티브로 두는
구성에서, CLI가 프로세스 수명주기를 관리하기 시작하면 프로세스 매니저를 새로 만드는 별개 문제가
된다. init은 다음 단계를 **출력만** 한다.

**결정 2 개정 (2026-08-26) — 기동은 `openarchive serve`가 맡는다.**

위 표의 "하지 않는다: API·워커·프론트 기동"을 **부분 철회한다.** `init`의 범위는 그대로 DB
준비까지이고, 기동은 별도 서브커맨드가 맡는다.

철회하는 이유는 원래 근거가 겨눈 대상이 달랐기 때문이다. "프로세스 매니저를 새로 만드는
별개 문제"가 말하는 것은 **감독**(죽으면 되살리기·부팅 시 자동 기동)이며, 그 자리는
ADR-038의 systemd가 이미 채웠다. 남은 것은 **첫 실행에서 두 프로세스를 켜는 일**이고
이것은 프로세스 매니저가 아니다.

이 자리를 비워둔 대가는 실사용에서 드러난다 — 워커를 켜지 않으면 **업로드는 성공하는데
검색에 잡히지 않는다.** 에러가 나지 않으므로 사용자는 원인을 짐작할 수 없다. init이 DB
연결을 한 줄로 끝내놓고 그다음에 터미널 셋을 요구하면, "복잡한 설정 없이 시작한다"는 이
CLI의 목적이 마지막 한 걸음에서 무너진다.

| `serve`가 한다 | 하지 않는다 |
|---|---|
| API(uvicorn)와 워커를 자식 프로세스로 기동 | **죽은 프로세스 재시작** — systemd의 일이다 (ADR-038) |
| Ctrl-C·SIGTERM에 둘 다 종료 | 부팅 시 자동 기동 |
| 한쪽이 멈추면 나머지도 내리고 0이 아닌 코드로 종료 | 프론트(Node) 기동 — 별도 런타임이라 빌드 산출물 동봉이 먼저다 |

- **한쪽이 멈추면 함께 내리는 이유**는 반쪽 생존이 조용한 실패이기 때문이다. API가 죽고
  워커만 남으면 화면은 안 뜨는데 프로세스는 살아 있어 "돌고 있으니 괜찮다"로 오해된다.
- **Ctrl-C 경로에서 신호를 겹쳐 보내지 않는다.** SIGINT는 프로세스 그룹 전체에 가므로 자식은
  이미 받았다. 곧바로 SIGTERM을 겹치면 워커가 "처리 중인 잡을 마치고 멈춘다"는 ADR-004의
  계약을 지키지 못한다. 유예가 지난 뒤에만 SIGTERM을, 그래도 남으면 SIGKILL을 보낸다.
- **부모만 받은 SIGTERM에도 자식을 내린다** (2026-08-27 보강). `kill <pid>`·컨테이너 진입점·
  감독자의 stop은 그룹이 아니라 부모 하나에만 신호를 보낸다. 그것을 무시하면 부모만 죽고
  uvicorn과 워커가 고아로 남아 포트를 쥔 채 잡을 계속 집어간다(실측). 핸들러는 예외를 던지지
  않고 **플래그만 세운다** — 자식을 띄우는 중이나 내리는 중에 신호가 오면 끊는 쪽이 오히려
  고아를 만들기 때문이다(방금 뜬 자식을 놓치거나, 정리를 하다 만다). 이 경로에서는 Ctrl-C와
  달리 유예 없이 곧바로 SIGTERM을 보낸다. 부모만 받은 경우 자식은 신호를 받지 않아 기다림이
  헛되고, 그룹째 온 경우라도 uvicorn과 워커 둘 다 두 번째 신호를 종료 요청의 반복으로 다뤄
  잡을 잃지 않는다. 두 창 모두 테스트가 고정한다(`tests/test_serve.py`).
- **stdout을 줄 단위 버퍼링으로 바꾼다.** 자식과 같은 stdout을 쓰는데 파이프로 나갈 때 블록
  버퍼링이 걸려 안내가 통째로 맨 끝으로 밀리는 것을 실측했다. 맨 끝에 나오는 안내는 안내가
  아니다. 회귀는 로그의 출현 순서로 고정한다(`tests/test_serve.py`).

**개발자의 기존 경로는 그대로 둔다.** `uvicorn --reload`가 필요한 작업에 `serve`는 맞지
않으므로 `--reload` 옵션을 넣지 않고, README가 두 경로를 모두 남긴다. 옵션을 하나 더
얹는 대신 용도를 나눈 것이다 — `serve`는 "그냥 켜기"이고, 개발 중 재시작은 uvicorn 자신이
더 잘한다.

**결정 3 — 남의 데이터베이스에는 스키마를 얹지 않는다.**

`schema_migrations`가 없는데 OpenArchive가 쓰는 테이블 이름이 이미 존재하면 **아무것도 바꾸지
않고 중단**한다. 이것이 "기존 데이터에 영향을 주지 않는다"의 실제 장치다 — 마이그레이션에는
`ALTER TABLE documents`(009)와 `DELETE FROM document_links`(012)가 있어, 같은 이름의 남의
테이블 위에서 돌면 그 데이터를 손상시킨다. `CREATE TABLE`이 실패해 멈추는 것에 기대면 늦다.

판정 기준이 되는 이름 목록은 마이그레이션 파일에서 정규식으로 추출한다. 손으로 적어두면 새
테이블이 추가될 때 조용히 낡고, 낡은 목록은 보호에 구멍을 뚫는다. 추출 결과는 테스트가 9개
이름으로 고정한다(`tests/test_cli.py`).

**결정 3-2 — capability 판정의 세 자리는 실측으로 정했다.**

- **CREATE 권한은 스키마 단위로 본다.** `has_database_privilege(user, db, 'CREATE')`는 "DB 안에
  **스키마를** 만들 권한"이지 테이블을 만들 권한이 아니다. 컨테이너 실측에서 `public`에만
  CREATE를 받은 롤이 이 함수로 `false`가 나오면서 `CREATE TABLE`은 성공했다 — 그대로 두면
  멀쩡한 DB를 거부한다. `has_schema_privilege(user, 'public', 'CREATE')`를 쓴다.
- **확장은 "설치 가능"만이 아니라 "이미 설치됨"도 본다.** `005_trgm_extensions.sql`은 ADR-005
  관례에 따라 `IF NOT EXISTS` 없이 `CREATE EXTENSION pg_trgm`을 실행한다. DBA가 미리 깔아둔
  DB에서는 001~004가 적용된 뒤 005가 `duplicate_object`로 죽어 **부분 적용 스키마가 남는다.**
  미적용 마이그레이션이 가드 없이 만드는 확장이 이미 있으면 적용 전에 멈춘다.
- **확장을 만들 권한은 데이터베이스 단위로 본다.** (2026-08-26 보강 — 도입 경로 실측에서
  드러난 결함) `pg_available_extensions`는 **배포판에 그 확장이 있는지**만 말한다. 실제로
  만들 수 있는지는 `CREATE EXTENSION`의 권한 규칙이 정하며, 로컬 컨테이너 실측은 이렇다.

  | 롤 | `pg_trgm` (trusted) | `vector` (untrusted) |
  |---|---|---|
  | 비슈퍼유저 · DB CREATE 없음 | ⛔ | ⛔ |
  | 비슈퍼유저 · DB CREATE 있음 | ✅ | ⛔ |
  | 슈퍼유저 | ✅ | ✅ |

  판정식은 `슈퍼유저 or (trusted and has_database_privilege(current_user, current_database(),
  'CREATE'))`다. 앞 항목이 바로 그 함수를 테이블 판정에서 물리쳤는데 여기서 다시 쓰는 것이
  모순처럼 보이지만 **대상이 다르다** — 테이블을 만들 권한은 스키마가, 확장을 만들 권한은
  데이터베이스가 정한다. `trusted` 컬럼(`pg_available_extension_versions`)은 PostgreSQL 13에서
  생겼고 그 아래 버전은 어차피 거부되므로, 버전 미달이면 확장 조회 자체를 하지 않는다.

  이 자리가 비어 있던 이유는 검증이 전부 설치기가 만든 `postgres` 슈퍼유저로 이뤄졌기
  때문이다. DBA가 앱 전용 롤을 내주는 실제 도입 형태에서는 점검이 `vector`를 "사용 가능"으로
  통과시킨 뒤 001이 `InsufficientPrivilege`로 죽어 `schema_migrations`만 남았다 — **"확인이
  적용보다 먼저"라는 이 ADR의 계약이 정확히 그 경로에서 깨졌다.** 회귀는 비슈퍼유저 롤을
  실제로 만들어 고정한다(`tests/test_cli.py`).

  **이미 설치된 확장에는 이 판정을 걸지 않는다.** 001은 `IF NOT EXISTS`라 권한 없이
  통과하고, 005처럼 가드 없는 파일은 앞 항목이 따로 막는다. 권한만 보고 일괄 거부하면
  "DBA가 `vector`만 미리 깔아준 DB"라는 정상 도입 경로까지 막힌다.

**결정 4 — DSN을 `backend/.env`에 기록한다.** `DATABASE_URL` 줄만 갈아 끼우고 나머지 설정은
보존한다. 기록하지 않으면 "준비 완료"가 다음 프로세스로 이어지지 않는다 — 앱이 기본값(로컬
컨테이너)을 보게 되어, 방금 준비한 DB와 다른 곳에 붙는다. 위치가 `backend/`인 것은 `config.py`가
그 한 곳만 절대경로로 읽기 때문이다.

**트레이드오프**

- **마이그레이션 실행 주체가 둘이 된다.** ADR-012를 이에 맞게 개정했다(아래).
- **대화형 입력은 DSN 한 줄**이라 항목별 안내가 없다. OpenProxy 경유에서 데이터베이스 자리가
  pool 이름이라는 점은 프롬프트 문구로만 알린다. 항목별 질문은 입력 횟수를 늘리는 대가로 얻는
  것이 안내뿐이라 채택하지 않았다.
- **`--dsn`은 셸 기록에 비밀번호를 남긴다.** 대화형 입력에는 남지 않는다. 비대화형 경로가 필요한
  이유(CI·스크립트·테스트)가 그 대가보다 크다고 보았다.
- **CLAUDE.md의 "DSN은 환경변수로만 주입한다"(ADR-006)에 대한 예외는 이 명령에 한한다.** 그 규칙이
  막으려는 것은 애플리케이션이 접속 대상을 스스로 정하는 것(멀티호스트 DSN·`target_session_attrs`)
  이다. init은 **도입 시점에 그 환경변수의 값을 확정해 파일에 남기는** 도구이며, 확정 이후 API·워커·
  MCP는 여전히 `DATABASE_URL` 하나만 읽는다. 런타임 접속 경로는 늘지 않는다.
- **`schema_migrations`라는 이름을 다른 용도로 쓰는 DB는 충돌 검사를 건너뛴다.** 그 테이블의 존재가
  "우리 설치"의 판정 기준이기 때문이다. 다만 뒤이은 `filename` 컬럼 조회가 실패해 중단되므로 스키마가
  손상되지는 않는다. 이 자리를 더 좁히려면 이력 테이블의 형태까지 대조해야 하는데, 얻는 것에 비해
  판정이 복잡해진다고 보아 그대로 둔다.
- **conflict 판정이 이름 기준이라 보수적이다.** OpenArchive와 무관한 `users` 테이블을 가진 DB에는
  설치를 거부한다. 오탐의 대가는 "빈 DB를 새로 만들라"는 안내이고, 미탐의 대가는 남의 데이터
  손상이다. 비대칭이 명확하다.

### ADR-040: 세션으로만 할 수 있는 일에는 웹 입구를 만들고, 잊은 비밀번호는 CLI가 푼다
**상태**: 2026-08-21 신규

**배경 — 설계가 세션 전용으로 못박은 두 가지에 화면이 없었다**

ADR-034가 토큰 발급·목록·폐기를 세션 전용으로 봉인했다. 토큰이 토큰을 발급하면 폐기 뒤에도
자격증명을 스스로 재생산하기 때문이다. 그런데 세션 쿠키를 가진 클라이언트는 Web UI 하나뿐인데
**그 화면이 없었다** — 프론트엔드 소스 전체에 "토큰" 문자열이 0건이었다. 정상 경로가 닫혀 있어
`curl`로 로그인해 쿠키를 얻고 직접 POST하는 것이 유일한 발급 방법이었다.

같은 누락이 비밀번호에도 있었다. 자체 가입이 없고(ADR-028), 관리 화면은 계정 생성·삭제뿐이며,
`create_admin.py`는 기존 계정을 거절하고, 소유 문서가 있는 사용자는 삭제도 안 된다. **문서를 가진
사용자가 비밀번호를 잊으면 DB를 직접 만지는 것 외에 방법이 없었다.**

둘은 우연이 아니라 한 가지 누락이다 — **"세션이 있어야만 할 수 있는 일"을 웹이 다 받지 않았다.**
문서·이슈·`check.sh`가 모두 초록인 채로 남아 있었고, 실제로 화면을 열어 써 본 검증(2026-08-21)에서야
드러났다.

**결정 1 — 세션 전용 동작의 입구를 `/settings` 한 화면에 모은다.** 헤더의 사용자명이 진입점이다.
토큰 발급·목록·폐기는 백엔드를 한 줄도 바꾸지 않는다 — API는 이미 완성돼 있었고 없던 것은 화면뿐이다.

**결정 2 — 비밀번호 변경은 세션 전용이며 자기 것만 바꾼다.** `PUT /api/auth/password`는
`require_session_user`로 봉인한다. 토큰이 비밀번호를 바꿀 수 있으면 위임 자격증명이 계정 자체를
장악하게 되어 ADR-034의 경계가 무너진다.

틀린 현재 비밀번호에는 **401이 아니라 403**을 준다. 세션 자체는 유효하므로, 401이면 클라이언트가
"세션 만료"로 읽고 로그인 화면으로 튕긴다. 401은 세션 부재, 403은 이 동작의 거부로 나눈다.

400·422도 후보였다. 422는 이 앱에서 Pydantic이 **모양이 틀린 요청**에 쓰는 코드이므로(빈 새 비밀번호가
그렇다), 모양은 맞고 대조에 실패한 경우에 같은 코드를 주면 두 실패가 섞인다. 400은 "거부"를 표현하지
못한다. 대신 **403이 두 가지 뜻을 갖는 대가**를 진다 — 세션 전용 경계 거부(`로그인 세션이 필요합니다.`)와
현재 비밀번호 불일치(`현재 비밀번호가 올바르지 않습니다.`)다. 상태 코드만으로는 갈리지 않으므로
**두 경우의 `detail`을 테스트가 단언해** 경계 검증이 엉뚱한 이유로 통과하지 않게 고정했다
(`test_auth_api.py`).

**결정 3 — 비밀번호를 바꾸면 그 계정의 세션을 전부 무효화한다.** 현재 세션도 포함한다. 비밀번호
변경의 통상 의도가 "탈취 의심"이고, 다른 기기의 세션을 남기면 그 의도가 절반만 이뤄진다. 현재
세션만 살려두는 선택지도 있었으나 "현재 세션"이라는 개념을 서비스 계층으로 끌어와야 해서,
바꾼 본인이 한 번 더 로그인하는 대가와 바꾸지 않았다.

**결정 4 — API 토큰은 비밀번호를 바꿔도 살아남는다.** ADR-034에서 토큰은 비밀번호와 독립한 위임
자격증명이고, 폐기 수단이 같은 화면의 목록에 개별로 있다. 함께 폐기하면 비밀번호 하나를 바꾸느라
운영 중인 공급 스크립트가 전부 멈춘다. 화면과 CLI 출력 양쪽에서 이 사실을 밝힌다.

**결정 5 — 잊은 비밀번호는 웹이 아니라 운영자 CLI가 푼다.** `openarchive reset-password <username>`이
현재 비밀번호 없이 갈아끼운다. 결정 2는 로그인할 수 있는 사람만 쓸 수 있어 분실 사례를 풀지 못한다.

관리 화면에 "남의 비밀번호 재설정"을 두는 안을 기각한 이유는 권한 경계다. 관리자가 남의 계정을
탈취하면 그 사람의 private 문서를 읽게 되고, 이는 `is_admin`이 **계정 관리 권한만 뜻한다**는
경계(`009_auth_tables.sql`·ADR-027·ADR-028)를 무너뜨린다. 반면 서버 셸 접근자는 이미 DB를 직접
만질 수 있으므로 CLI는 권한을 늘리지 않는다 — **없던 능력을 만드는 것이 아니라, 있는 능력에
안전한 손잡이를 붙이는 것이다.** CLI는 이미 인터페이스 계층의 한 자리다(ADR-039 결정 1).

**트레이드오프**

- **분실 복구에 서버 접근이 필요하다.** 셀프서비스 재설정(메일 링크)은 메일 발송 인프라를 요구하고,
  ADR-028의 "한 설치 = 한 조직" 전제에서 얻는 것보다 늘리는 것이 많다. 도입자가 운영자를 겸하는
  규모에서는 CLI 한 줄이 더 짧은 경로다.
- **관리자도 잠기면 CLI가 필요하다.** 관리자 계정을 관리자가 스스로 못 푼다. 이 대칭을 깨려면
  결정 5가 기각한 권한 확대를 다시 열어야 한다.
- **비밀번호 재설정은 `--dsn`을 셸 기록에 남길 수 있다.** ADR-039의 같은 트레이드오프이며, 생략하면
  `DATABASE_URL`을 쓴다. 비밀번호 자체는 `getpass`로만 받아 인자·화면 어디에도 남지 않는다.
- **확인 재입력을 두지 않았다.** 오타로 다시 잠길 수 있으나 같은 명령을 한 번 더 실행하면 풀린다.
  `create_admin.py`의 단일 프롬프트와 형태를 맞췄다.
- **새 비밀번호에 정책이 없다.** 길이 1 이상만 본다. 현재 비밀번호와 같아도 통과한다. 계정 생성
  경로(`create_user`)에도 정책이 없어 한쪽에만 걸면 두 경로가 갈린다 — 정책은 두 자리에 함께
  도입해야 하고, 그것은 ADR-028의 "최소 로그인" 범위를 다시 여는 별개 판단이다.
- **화면이 하나 늘었다.** UI_GUIDE의 사용자 화면은 6개에서 7개가 된다. 관리 화면이 아닌 이유는
  이 화면의 모든 동작이 **자기 자신에게만** 미치기 때문이다.

### ADR-041: 빌드된 프론트를 백엔드 패키지에 동봉해 같은 오리진에서 서빙한다
**상태**: 2026-08-26 신규. ADR-039 결정 2 개정(`openarchive serve`)의 다음 걸음이다.

**배경 — 마지막에 남은 런타임 하나**

`init`이 DB 연결을, `serve`가 API·워커 기동을 한 줄로 만든 뒤에도 프론트엔드가 남았다.
사용자는 여전히 Node.js를 설치하고 `npm install`로 **521MB**(실측)의 `node_modules`를
받은 뒤 세 번째 프로세스를 띄워야 했다.

그런데 이 앱의 프론트가 Node에서 하는 일은 셋뿐이었다 — 정적 파일 서빙, `/api/*`
프록시(`next.config`의 rewrites), `documents/[id]` 한 페이지의 서버 렌더링. 셋 다
없앨 수 있다. 확인해 보니 서버 전용 코드(`use server`·Route Handler·`cookies()`)는
한 줄도 없었다. 이미 순수 클라이언트 앱이었다.

**결정 1 — 정적 export를 백엔드 패키지에 담는다.** `STATIC_EXPORT=1 npm run build:static`이
`out/`을 만들고 `backend/app/static/`으로 복사한다. FastAPI가 그것을 서빙하므로 Node는
개발자 쪽에만 남는다. 산출물은 **1.5MB · 86파일**이라 저장소에 커밋한다 — 커밋하지 않으면
clean clone에서 다시 Node가 필요해져 이 ADR의 목적이 사라진다.

**결정 2 — 문서 상세는 껍데기 한 장으로 받는다.** 정적 export는 빌드 시점에 아는 경로만
만드는데(Next 16 static-exports 문서: `dynamicParams: true`인 동적 라우트는 미지원)
문서 ID는 실행 중에 생긴다. `generateStaticParams`가 `__id__` 하나만 내놓고, 서버가 모든
문서 ID 요청에 그 파일을 내려준다. 실제 ID는 컴포넌트가 `usePathname()`으로 URL에서 읽는다.

`page.tsx`가 서버 컴포넌트로 남고 화면은 `DocumentDetailView.tsx`로 갈라진 것은 이 때문이다
— `generateStaticParams`는 클라이언트 컴포넌트 파일에서 export할 수 없다.

**결정 3 — fallback은 두 번째 세그먼트를 치환해 찾고, 확장자를 남긴다.**

| 요청 | 내려주는 파일 |
|---|---|
| `/search` | `search.html` |
| `/documents/<uuid>` | `documents/__id__.html` |
| `/documents/<uuid>.txt` | `documents/__id__.txt` |
| `/documents/<uuid>/__next._tree.txt` | `documents/__id__/__next._tree.txt` |

확장자를 남기는 이유는 `<Link>` 이동이 HTML이 아니라 **RSC 페이로드**를 받아 가기 때문이다.
확장자를 잃고 `.html`로 떨어지면 라우터가 페이로드 대신 HTML을 읽어 클라이언트 이동이 깨진다.

어느 라우트가 동적인지는 **적어 두지 않는다.** 치환한 경로가 실제로 존재할 때만 쓰이므로
목록이 필요 없고, 손으로 적은 목록은 라우트가 늘 때 조용히 낡는다(ADR-039 결정 3의 같은 원칙).

**결정 4 — catch-all은 API 라우트를 전부 등록한 뒤에 붙인다.** 먼저 붙이면 `/api/*`까지
삼킨다. `mount_frontend(app)` 호출이 `main.py` 맨 끝에 있는 이유이며, 테스트가 이 순서를
`/api/health` 응답으로 고정한다.

**실측에서 잡은 것 둘**

- **HEAD를 함께 받아야 한다.** Next의 `<Link>` 프리페치가 HEAD로 온다. GET만 받으면 화면은
  멀쩡히 동작하는데 콘솔이 405로 뒤덮인다(브라우저로 열기 전까지 드러나지 않았다 —
  페이지 하나 여는 데 31건). 회귀는 테스트로 고정한다.
- **경로 조작 방어는 정규화 뒤에 판정한다.** 문자열만 검사하면 인코딩된 형태를 놓친다.
  `resolve()` 후 `is_relative_to(static_dir)`로 본다.

**트레이드오프**

- **빌드 산출물이 저장소에 들어온다.** 소스와 어긋날 위험이 있어 `scripts/check.sh`의 프론트
  빌드를 `build:static`으로 바꿨다 — 검증을 돌리면 산출물이 갱신되고 차이는 `git diff`에
  그대로 드러난다. 검증 스크립트가 워킹트리를 건드리는 것은 부작용이지만, 조용히 어긋난
  산출물을 배포하는 것보다 낫다.

  **다만 그러려면 빌드가 재현 가능해야 한다.** 이 결정을 처음 넣었을 때 놓쳤고, 머지 직후
  브랜치를 옮기려다 드러났다 — Next는 빌드마다 새 build ID를 만들고, 그것이 산출물 경로
  (`_next/static/<buildId>/`)와 각 페이지의 참조에 들어간다. 소스를 한 줄도 고치지 않고
  `check.sh`를 한 번 돌리는 것만으로 **파일 55개가 "수정됨"이 되었다.** 매번 무의미한 diff를
  보게 되면 사람은 그것을 읽지 않게 되고, 그러면 위에서 얻으려던 "차이가 눈에 드러난다"가
  통째로 무효가 된다. `generateBuildId`를 고정값으로 두어 해결했다(3회 연속 빌드가 동일
  해시임을 확인). 캐시 무효화는 콘텐츠 해시가 붙은 청크 파일명이 이미 하고 있으므로 잃는 것이 없다.
- **`next.config`의 rewrites가 정적 export에서 빠진다.** 동봉하면 API가 같은 오리진이라
  프록시가 필요 없고, Next 16은 export 모드에서 rewrites를 무시한다(빌드 경고). 개발
  서버는 여전히 프록시가 필요하므로 `STATIC_EXPORT` 환경변수로 갈라 둔다.
- **개발 경험은 바뀌지 않는다.** `npm run dev`는 그대로다. 동봉 산출물은 배포·심사 경로를
  위한 것이고, 프론트를 고치는 사람은 기존 방식을 쓴다.

### ADR-042: 주제 덩어리는 조회 시점에 관계 그래프의 Louvain 군집으로 만든다
**상태**: 2026-08-26 신규 (#85)

**맥락 — 태그 분류는 자동 정리의 축이 아니었다.** 태그로 묶던 덩어리는 태그 없는 문서를 전부
미분류로 두었다. 문서를 올리기만 해도 정리되는 것이 아니라 사람이 먼저 태그를 붙여야 했고,
정리의 핵심 축이 사람 손에 남았다. 한편 ADR-029의 `document_edges`에는 이미 문서 관계 그래프가
있다. LLM 없이 kNN edge를 Louvain으로 나누고 키워드로 이름 붙이는 공개 구현인 txtai Semantic
Graph에서 **방법**을 가져오되, OpenArchive의 저장·권한 계약 안에서 다시 구성한다.

**결정 1 — 군집은 조회 시점에 계산하고 저장하지 않는다.** 요청자가 볼 수 있는 문서와 그 사이의
edge만 읽어 부분 그래프를 만든 뒤 군집화한다. 전 문서로 계산한 결과를 저장하면 내가 볼 수 있는
두 문서가 내가 볼 수 없는 문서 때문에 같은 덩어리에 묶일 수 있다. 집계를 열람 범위 안에서만
계산하고 다른 문서가 관계 종류에 영향을 주지 못하게 한 ADR-027 규칙 3·4를 군집에도 그대로
적용한다. 개발 DB 66문서에서 요청마다 계산해도 **서비스 경계(열람 범위 SQL 왕복 + 군집 계산)
16~24ms**였다. 군집 계산 자체는 6ms 안팎이다.

**결정 2 — NetworkX Louvain을 `resolution=1.0`, seed 42로 실행하고 입력을 정렬한다.** 문서와
edge를 정렬한 뒤 `networkx.algorithms.community.louvain_communities`에
`LOUVAIN_RESOLUTION = 1.0`, `LOUVAIN_SEED = 42`를 넘긴다. 같은 입력의 응답을 재현할 수 있게
하기 위한 선택이다. `networkx`는 이전에 torch가 간접으로 끌고 오던 의존성이었지만, 군집 기능은
`[local]` 없이도 동작해야 하므로 기본 의존성으로 승격한다. 순수 Python이며 BSD 라이선스다.

**결정 3 — edge는 무가중으로 쓴다.** ADR-029 결정 4의 `overlaps`와 `related`는 `score` 척도가
서로 다르므로 한 가중치 축에 섞을 수 없다. 구현으로 다시 잰 문서쌍 일치율은 **0.84**다 — 무가중
3군집(27·20·19)과 `score` 가중 4군집(23·20·16·7)이 큰 갈래에서 같은 분할을 만들었다. 척도를
억지로 합치지 않아도 잃는 것이 크지 않다.

**결정 4 — 이름은 최다 태그, 태그가 없으면 연결이 많은 문서 제목을 쓴다.** 군집 안 태그의
최빈값을 이름으로 쓰고 동률은 사전순으로 정한다. 태그가 하나도 없으면 차수가 가장 큰 문서의
제목을 쓰며, 다시 동률이면 제목과 문서 id로 정한다. **이때 차수는 그 군집 안에서만 센다** —
군집 밖으로 뻗은 edge까지 세면 다른 덩어리와 이어졌다는 이유만으로 대표 문서가 바뀐다. 같은
이름이 겹치면 큰 덩어리부터 기본 이름을 쓰고 뒤에는 번호를 붙인다. 태그든 제목이든 예약 버킷
이름(`미분류`·`기타`)과 겹치면 출처를 밝혀 `미분류 (태그)`·`미분류 (문서)`로 쓴다 — 화면이
덩어리 이름을 원과 선의 식별자로 쓰기 때문에 같은 이름이 둘이면 원이 겹쳐 그려진다. 한국어
토크나이저 없이 저장된 메타데이터와 그래프만으로 재현 가능한 이름을 만든다.

**결정 5 — 화면은 군집을 확정된 주제나 분류로 단정하지 않는다.** Louvain 결과는 그럴듯한 분할
중 하나다. 무가중 seed 42와 7의 문서쌍 일치율은 0.92, 42와 2026은 0.88이었다. 정렬과 seed 고정은
결정론을 확보하지만 유일한 정답을 만들지는 않는다. 따라서 화면은 관계 기반 추천 묶음으로 설명하고,
`미분류`는 태그 없음이 아니라 관계가 없는 문서를 뜻한다. 순위 기반 `overlaps`를 "같은 내용"이라
부르지 않기로 정정한 ADR-029와 같은 원칙으로, 측정한 신호보다 강한 어휘를 쓰지 않는다.

**트레이드오프**

1. 요청마다 그래프를 만들고 군집화한다. 문서 수천 규모까지는 sub-second로 수용하고, 그 이상에서
   병목이 확인되면 캐시나 저장을 재검토한다. 그때는 ADR-027의 열람 범위와 다른 문서의 영향 규칙을
   다시 만족시켜야 한다.
2. 문서와 관계가 늘면 덩어리 경계가 바뀔 수 있다. 저장하지 않으므로 "예전 덩어리"라는 개념과
   안정적인 군집 id는 제공하지 않는다.
3. SBOM에 `networkx` 한 줄이 늘어난다.

**기각한 대안**

- **배치 계산 후 `document_communities`에 저장**: 전역 결과가 볼 수 없는 문서의 영향을 접어 넣어
  ADR-027 규칙 4를 위반한다. 재계산 시점과 군집 id 안정성 문제도 함께 생긴다.
- **kind·score 가중**: 관계 종류마다 점수 척도가 달라 하나의 가중치로 비교할 수 없다.
- **c-TF-IDF 키워드 라벨**: 어절 단위 실측에서는 `'없다'`, `'않는다'`, `'id'` 같은 잡음이 상위에
  올랐다. 한국어 형태소 분석기가 필요하므로 별도 결정으로 미룬다.
- **txtai 채택**: 방법은 참고할 수 있지만 그래프와 군집 계산을 애플리케이션 메모리의 별도
  파이프라인에 맡기면 OpenSQL 안의 관계를 코어 계약으로 삼은 현재 경계가 깨진다.

**실측 (2026-08-26, 개발 DB · 실 BGE-M3)**: 문서 66건, 무방향 문서쌍 646개에서
`resolution=1.0`은 **3군집(27·20·19)**, `resolution=1.5`는 **8군집**을 만들었다. 세 군집은
태그를 입력으로 쓰지 않았는데도 각 군집의 태그 분포와 일치했다 — 열람 범위를 적용한 조회에서
`조사`·`adr`·`문서관리`로 갈렸다. 소요는 **군집 계산만 6ms 안팎, 서비스 경계 16~24ms**다.

설계 단계에 기록한 `resolution=1.0` → 4군집(25·20·16·5)은 **구현으로 재현되지 않았다**. 입력
정렬과 seed를 고정하기 전의 측정으로 보이며, 어느 쪽이든 같은 그래프가 조건에 따라 다른 분할을
낸다는 결정 5의 근거를 그대로 보여준다. 이 항과 **결정 3·5의 일치율은 모두** 결정 2의
정렬·seed를 적용한 구현으로 다시 잰 값이다 — 설계 단계 스파이크의 0.86·0.84·0.94는 정렬·seed를
고정하기 전 측정이라 폐기했다.
