# PRD: OpenArchive — OpenSQL 기반 AI 문서 데이터 플랫폼

> **2026-08-14 기준선.** 웹서비스 관점에서 작성된 이전 PRD를 대체한다(이전 판은 git 이력).
> 문제 → 사용자 → 가치 → 경계 → 핵심 능력 → 하지 않는 것 → 발전 경로 순서로 제품을
> 다시 도출한 결과이며, 기존 구현의 정당화에서 출발하지 않았다 — 기존 결정과 일치하는
> 항목은 "이미 있어서"가 아니라 문제에서 같은 결론이 다시 나왔기 때문에 유지된다.
> 코어 계약의 정본은 ADR-015, 플랫폼 정의는 ADR-031이다. 이 기준선이 새로 확정한
> 결정(1차 소비자 명시, 프로그래매틱 공급과 관측 가능성의 승격, 원본 비보관 원칙,
> Identity 요구사항)은 **ADR-032**에 기록했고, 각 절에도 근거와 함께 적는다.

## 1. 문제

조직의 문서를 AI가 신뢰하고 쓸 수 있는 데이터로 만드는 일은, 오늘날 각 팀이
애플리케이션 코드로 직접 조립하는 파이프라인(파싱 → 청킹 → 임베딩 → 벡터 저장 →
변경 동기화)에 맡겨져 있다. 이 방식은 두 개의 비용을 만든다.

- **구축 비용** — 어떤 조직이 만들어도 거의 같은 모양의 파이프라인을, 팀마다 글루
  코드로 다시 만든다. 차별화되지 않는 반복 노동이다.
- **신뢰 비용** — 임베딩·벡터 인덱스·문서 관계는 전부 원본의 **파생 데이터**다. 원본은
  RDBMS에, 벡터는 별도 엔진에 있으면 둘을 잇는 트랜잭션이 없어 실패한 잡, 절반만
  갱신된 문서, 버전이 섞인 청크가 생기고 **그 사실을 관측할 방법조차 없다.** 소비자가
  AI라서 피해는 증폭된다 — AI는 낡은 근거를 출처까지 달아 인용하고, 권한 검사가 AI
  경로에서 한 번 빠지면 검색창에서 안 새던 문서가 에이전트를 통해 샌다.

핵심 통찰: **파생 데이터의 정합성은 애플리케이션 문제가 아니라 데이터베이스 문제다.**
데이터베이스는 인덱스와 제약으로 파생물의 정합성을 지키는 일을 원래부터 해 왔다.
OpenArchive는 임베딩과 관계 그래프를 "앱이 내보내는 산출물"이 아니라 "DB가 유지하는
인덱스"처럼 다루도록 그 책임을 DB 계층으로 옮긴다. 정합성이 트랜잭션 경계 안에
들어오면 보장할 수 있게 되고, 어긋난 구간은 쿼리로 관측할 수 있게 된다.

## 2. 사용자

| 사용자 | 겪는 문제 | OpenArchive와의 관계 |
|---|---|---|
| **플랫폼 운영자** (도입하는 개발자·팀) | 위 파이프라인을 직접 만들고 유지해야 한다 | 설치하고, 소스를 연결하고, 운영한다. 이 제품이 없었으면 저 파이프라인을 짰을 사람 |
| **AI 에이전트** (MCP 클라이언트) | 근거 없이 답하거나, 낡은·권한 밖 근거로 답한다 | **1차 소비자.** 검색 결과를 발췌·출처·기준 버전과 함께 받는다 |
| **시스템 통합 개발자** | 문서 데이터를 공급·소비할 표준 경로가 없다 | REST로 소비하고, 커넥터로 공급한다 |
| **지식 노동자 · 큐레이터** | 키워드 검색으로는 못 찾고, 문서 더미를 정리할 도구가 없다 | Web UI로 검색·탐색하고, 태그·편집·중복 확인으로 말뭉치를 다듬는다 |
| **오픈소스 기여자** | — | 파서·커넥터·프로바이더를 확장점에 끼운다 |

- **AI 에이전트와 프로그램은 사람과 대등한 1차 소비자다.** Web UI는 여러 인터페이스 중
  하나이지만 축소판이 아니다 — 완전한 검색·소비 인터페이스이며, 여기에 더해 큐레이션과
  계약의 가시화(§5 C2)라는 고유 역할을 가진다.
- **심사위원은 사용자가 아니다.** 대회는 제약 조건과 배포 마일스톤으로 다룬다
  (`PROJECT_CONTEXT.md`). 심사·데모 편의로 제품을 왜곡하지 않는다.

## 3. 정의와 가치

**OpenArchive는 다양한 문서 소스에서 수집한 문서를 AI가 쓸 수 있는 형태로
변환·동기화·공급하는, OpenSQL 기반 AI 문서 데이터 플랫폼이다** (ADR-031). 그 코어가
보장하는 계약은 하나다: **AI에게 주는 근거가 어느 시점에도 하나의 일관된 버전이고,
최신 버전으로 수렴함을 데이터베이스가 보장한다** (ADR-015).

> **보장 범위를 정확히 쓴다 (ADR-015).** "항상 최신"이 아니다. 재임베딩 중에는 이전
> 버전 청크로 검색되고, 워커 폴링 주기와 임베딩 소요만큼 반영이 늦다. 보장하는 것은
> **버전 일관성**(활성 청크가 여러 버전으로 섞이지 않음)과 **최신으로의 수렴**이며,
> 어긋난 구간은 정합성 검증 쿼리로 **관측할 수 있다.** 관측 가능한 주장이 검증 불가능한
> 주장보다 강하다.

일반적인 DIY RAG 스택과의 책임 분담이 이 제품의 가치를 정의한다. 차이는 기능 개수가
아니라 마지막 세 줄에 있다.

| 책임 | 일반적인 DIY RAG 스택 | OpenArchive |
|---|---|---|
| 파싱·청킹·임베딩 실행 | 앱 코드 | 플랫폼 (워커가 실행, **기동은 DB가**) |
| 원본 변경 → 파생 갱신 | 앱 (스케줄러·큐, 대개 best-effort) | **DB** (트리거 + 트랜잭셔널 아웃박스, 계약으로 보장) |
| 정형 필터 + 벡터 검색 | 앱에서 후처리, 또는 벡터 DB의 제한된 필터 | 단일 SQL 결합 |
| 답변 생성 | 앱 | **하지 않음** (클라이언트 책임, ADR-015) |
| 정합성의 증명 | 없음 — 어긋나도 모른다 | **쿼리로 관측** — 어긋난 구간을 세고, 0으로 수렴함을 보인다 |
| 권한의 일관성 (사람·AI 동일) | 소비 경로마다 재구현, AI 경로에서 누락 잦음 | 코어의 열람 술어 하나를 전 경로가 공유 (ADR-027) |
| 장애 복구 | RDBMS·Vector DB 두 시스템 각각 | 한 시스템 — 큐·벡터·버전·관계가 함께 복구 |

비슷한 오픈소스와의 차이도 같은 축이다. Paperless-ngx는 파이프라인 조율을 앱(Celery)이
맡고, Onyx(구 Danswer)는 벡터를 별도 엔진(Vespa)에 둔다 — 원본과 파생 데이터의
정합성이 앱 코드의 책임이 된다. OpenArchive는 조율과 벡터가 **같은 DB 트랜잭션 경계
안**에 있다.

**OpenSQL의 역할**은 배포 대상 그 이상이며 셋이다.

1. **논지의 실행 엔진.** "파생 데이터 정합성을 DB로 옮긴다"는 주장은 정형 데이터·벡터·
   작업 큐·관계 그래프를 하나의 트랜잭션 도메인에 담는 DB가 있어야 성립한다.
2. **가용성의 단위.** 모든 상태가 한 시스템에 있으므로 그 한 시스템의 HA가 곧 파이프라인
   전체의 HA다. 플랫폼은 복구를 구현하지 않고 상속한다 (ADR-006).
3. **신뢰의 주어.** 계약의 증명 수단(트랜잭션·제약·관측 쿼리)이 전부 DB의 산물이다 —
   "데이터베이스가 보장한다"는 문장의 주어다.

동시에 2단 구조를 유지한다: **코어는 표준 PostgreSQL 17 + pgvector에서 완전히
동작하고, OpenSQL은 고가용성이 필요한 프로덕션의 배포 대상이다** (`ROADMAP.md`).
이식성이 오픈소스로서의 채택 가능성을 만들고, OpenSQL이 프로덕션 서사를 만든다.

## 4. 경계 — Core와 Interface

"플랫폼"이 공허한 수식어가 되지 않도록 판별 기준 세 개를 정의에 포함한다.

1. **N×M 구조** — 여러 공급자(업로드·API·커넥터)와 여러 소비자(Web UI·REST·MCP)가
   **하나의 계약**(정합성 + 열람 범위)에서 만난다.
2. **UI 제거 생존성** — Web UI를 들어내도 제품 가치(파이프라인 + 계약 + API/MCP 공급)가
   온전하다.
3. **확장의 코어 불변성** — 커넥터·파서·프로바이더를 추가할 때 코어 코드가 바뀌지 않는다.

현재 상태를 과장 없이 적는다: **소비자 쪽 N은 증명되어 있다** — Web UI·REST·MCP가 같은
services 계층을 소비하고 검색은 응답 동등성 테스트가 있다 (ADR-031). **공급자 쪽 N도 세
주체에서 구현됐다** — 사람의 파일 업로드, 프로그램의 JSON 텍스트 API, AI 에이전트의 MCP
`create_document`가 같은 INSERT와 DB 파생 계약으로 만난다 (ADR-035·036). 다만 HTTP 경로의
테스트는 in-process 클라이언트가 호출하며, `backend`를
import하지 않는 별도 프로세스가 HTTP만으로 완주하는 것은 **아직 자동 검증되지 않았다** —
예제(`examples/ingest_text.py`)의 의존 독립성과 경로 유효성까지가 CI가 지키는 범위다
(ADR-035 트레이드오프 1). 판별 기준 3은 MCP 공급 인터페이스에서 처음 실측했다. 선행 step의
코어 공개범위 보강은 `backend/app/` **2 files changed, 9 insertions(+), 1 deletion(-)**였고,
그와 분리된 MCP 추가 step은 `backend/app/`·`backend/migrations/` **변경 0줄**로 기존 텍스트
진입점을 재사용했다. 인터페이스·테스트 변경은 **3 files changed, 198 insertions(+), 2 deletions(-)**다
(step 0 테스트와 리뷰 대응까지 더한 `backend/mcp_server/`·`backend/tests/` 누적은
**4 files changed, 244 insertions(+), 3 deletions(-)**이며, `backend/app/`의 9삽입·1삭제는 여기 포함되지 않는다).
0줄은 코어 계약의 선행 결함 보강을 숨긴 수치가 아니라 두 step을 분리해 재측정한 값이다 (ADR-036).

경계는 이렇게 긋는다. **코어는 "누가 말을 걸든 참이어야 하는 것"의 집합이다.**

- **Core** — 저장 스키마와 그것을 강제하는 트리거·제약, 정합성 계약(ADR-015), 열람
  의미론(ADR-027: 볼 수 없는 문서는 존재하지 않는 것처럼 보인다), 파생 실행(워커 —
  프로세스는 앱에 있지만 조율 상태는 전부 DB에 있다), 검색 의미론(정형+벡터+그래프의
  단일 SQL), 그리고 코어를 코드로 노출하는 유일한 문인 services 계층.
- **Interface** — 코어가 그 존재를 몰라도 되는 모든 것. 소비(Web UI·REST·MCP)와
  공급(파일 업로드·인제스천 API·커넥터 — 전부 "문서를 INSERT하는 클라이언트")과
  교체 가능한 의존(임베딩 프로바이더 — 단, 출력 형태 `vector(1024)`는 코어가 고정).

경계 규칙은 한 줄이다: **인터페이스는 사용성에서 서로 달라도 되지만, 계약을 약화할 수
없다.** 실효성 테스트는 "인터페이스를 추가·제거할 때 코어가 몇 줄 바뀌는가 = 0"이며,
로그인 도입 때 MCP 수정이 0줄이었다는 실측이 있다 (ADR-028·031).

**원본 비보관은 제품 원칙이다.** OpenArchive는 파일 보관소를 목표로 하지 않는다. 핵심
관리 대상은 AI가 사용할 문서 데이터(문서 텍스트와 파생 상태)다. 업로드한 원본 파일은
보관하지 않으며 다시 받을 수 없다 — 저장·편집·버전 관리의 대상은 문서 텍스트이고, 그중
파일 업로드로 들어온 것이 추출 텍스트다 (ADR-017, ADR-035). 다만 입력 방식에 따라 원본의 authoritative source가 어디인지는 달라질 수
있으며, 외부 소스 연동(ROADMAP 2단계) 시 별도 정책으로 정한다.

## 5. 핵심 능력

기능 목록이 아니라 능력 다섯으로 정의한다. 구현 상태 표기는 1차 제출 범위를 바꾸지
않는다 — 범위는 이슈로 관리한다 (`ROADMAP.md`).

| # | 능력 | 상태 |
|---|---|---|
| C1 | **수집 → 자동 파생** — 어떤 경로로 들어오든 파생은 DB가 기동한다 | 구현됨 |
| C2 | **정합성 계약과 그 관측** — 버전 일관성 · 최신 수렴 · 어긋남의 가시화 | 구현됨 |
| C3 | **열람 범위가 지켜지는 하이브리드 검색** — 정형+벡터+그래프 단일 SQL | 구현됨 |
| C4 | **동등한 다중 공급·소비** — 사람·프로그램·AI가 같은 계약 위에서 | 소비 3면 · HTTP 텍스트 공급 · 위임 API 토큰 구현 · 커넥터 미구현 |
| C5 | **전체 상태의 생존성** — 장애 후 한 시스템으로서 함께 복구 | DB 프로세스 장애 복구 검증됨 · 워커 프로세스 감독 도입 (ADR-038) · 노드 승격 미검증 (ADR-020) |

### C1. 수집 → 자동 파생

- **문서 업로드 → 자동 임베딩 파이프라인**: PDF/DOCX/TXT/MD 업로드 시 파일에서
  텍스트를 추출해 저장하고, DB 트리거가 임베딩 작업을 생성한다. 워커가 청킹·임베딩·
  벡터 저장까지 자동 처리한다. **공급 코드에는 임베딩 호출이 없다** — 공급자는 INSERT만
  하고, 파생(임베딩 잡·버전 이력·관계·위키링크)은 전부 DB 트리거가 만든다 (ADR-001·029·030).
- **텍스트 버전 관리와 자동 재임베딩**: 문서를 수정하면 텍스트 버전 이력이 쌓이고, 변경
  감지 트리거가 재임베딩을 자동 기동한다. 재업로드 없이 직접 편집할 수 있다 — 편집
  대상은 문서 텍스트의 새 논리 버전이며 원본 파일이 아니다 (ADR-017). 재임베딩 완료
  전까지는 이전 벡터로 검색이 계속된다 (검색 공백 없음). 과거 텍스트 버전의 본문은 문서와
  같은 열람 범위 안에서 조회할 수 있고, 그 버전으로 되돌리면 이력을 되감는 것이 아니라
  **새 버전이 만들어져** 같은 파생 계약을 다시 탄다 (ADR-037).

### C2. 정합성 계약과 그 관측

계약의 내용은 §3의 보장 범위 그대로다: 버전 일관성 + 최신 수렴. 이 기준선은 여기에
**관측 가능성을 독립된 제품 표면으로 승격한다.** 대부분의 RAG 스택은 "지금 인덱스가
원본과 맞는가?"라는 질문에 답할 수 없다. OpenArchive는 정합성 검증 쿼리로 답하고,
시스템 상태 화면이 임베딩 잡 카운터와 정합성 검증 결과를 보여준다 — 어긋난 구간이
생겼다가 0으로 돌아오는 것을 화면으로 증명할 수 있다. 데이터 플랫폼에서 freshness
모니터링이 기본기인 것과 같은 위상이며, 차별점(§3 비교표)의 증명 수단이 곧 기능이다.
상태 쿼리와 결과 모델은 services 계층에 있어 Web UI 라우터에 묶이지 않으며, 현재 HTTP 표면은
로그인한 사용자에게만 이를 제공한다.

### C3. 열람 범위가 지켜지는 하이브리드 검색

- **하이브리드 시맨틱 검색**: 태그·문서 유형·권한 같은 정형 필터와 pgvector 코사인
  유사도를 단일 SQL로 결합한 검색. 모든 경로가 같은 열람 술어를 지킨다 (ADR-027).
- **문서 관계 저장과 그래프 검색**: 임베딩 완료 트리거가 청크 이웃에서
  `overlaps`·`related` 관계를 만들고, 검색은 벡터 진입점에서 열람 가능한 관계와 직전
  텍스트 버전·위키링크를 깊이 2까지 확장한다 (ADR-027·029·030). 관련 문서와 태그 추천도
  같은 저장 관계를 사용한다. 볼 수 없는 문서는 결과뿐 아니라 순회 경로와 집계에서도
  제외한다.

  > 유사도 점수는 **비대칭 지표**라 중복 판정에 쓰지 않는다. "중복입니다"가 아니라
  > "내용이 유사한 문서가 있습니다"로 표시하고, 판단은 사람이 한다. 완전히 동일한
  > 텍스트는 `content_hash` 일치로 따로 확정한다.

### C4. 동등한 다중 공급·소비

**소비** — 세 인터페이스가 같은 services 계층을 소비한다 (ADR-031).

- **Web UI**: 완전한 검색·소비 인터페이스이자, 큐레이션과 계약 가시화의 고유 표면.
  열람 범위 안에서 고아 문서, 동일 텍스트, 여러 대목에서 만나는 문서, 미분류 문서,
  깨진 위키링크를 진단하고, 관계 지도에서 덩어리와 덩어리 사이 연결을 그래프로
  보여주며, `[[제목]]` 링크와 백링크로 문서를 오간다. 순위 기반 관계에서 정의할 수
  없었던 “빠진 연결” 진단은 만들지 않았다.
- **REST API**: 프로그램의 소비·공급 경로. 사람이 발급한 위임 API 토큰을 Bearer로 보내며,
  `read`·`read_write` scope와 독립 폐기를 지원한다 (ADR-034, §6).
- **MCP 근거 게이트웨이**: AI 에이전트에 문서의 근거를 공급한다. `search_documents`
  등의 툴로 의미 검색 결과를 발췌·출처·기준 버전과 함께 반환한다. `create_document`는
  `MCP_USER_ID`를 소유자로 삼아 `txt`·`md` 문서 텍스트를 같은 코어 진입점으로 공급하며,
  주체가 없으면 쓰기를 거부한다 (ADR-036).

  > **답변 생성은 플랫폼이 하지 않는다** (ADR-015). 생성 LLM을 탑재하지 않으며, 답변은
  > MCP 클라이언트가 만든다. "AI가 사내 문서만을 근거로 답하게 한다"고 쓰지 않는
  > 이유는, 클라이언트가 자기 지식으로 답하는 것을 우리가 막을 수단이 없기 때문이다.
  > 우리의 책임은 **근거 공급**까지다.

**공급** — Web UI의 파일 업로드(형식 4종), `POST /api/documents/text`의 JSON 텍스트 공급,
MCP `create_document`(`txt`·`md`)가 구현됐고, 세 입력 경로 모두 임베딩·관계·링크 파생을 테스트가
단언한다 — 파일 업로드와 JSON 텍스트는 파생을 서로 대조하고, MCP 경로는 같은 파생 5종을 값으로
고정한다 (ADR-035·036). 이로써 C4가 요구한 사람·프로그램·AI
에이전트의 공급 경로가 모두 구현됐다. 예제(`examples/ingest_text.py`)는 `backend` 패키지를 import하지
않고 표준 라이브러리만으로 로그인·공급·상태 폴링의 HTTP 경로를 보여주나, **그 예제가 실제
서버에 붙어 완주하는지는 CI가 확인하지 않는다** (ADR-035 트레이드오프 1). 프로그램은 사람이
발급한 `read_write` 위임 API 토큰만으로 세션 쿠키 없이 공급·검색·열람할 수 있고, 이 전 구간은
통합 테스트가 검증한다 (ADR-034). 다만 커넥터는 아직 없고 독립 예제의 실서버 완주도 CI 밖이므로
프로그래매틱 공급이 완전히 증명됐다고 말하지 않는다.

### C5. 전체 상태의 생존성

- **DB 프로세스 장애 자동 복구 (검증됨)**: DB 프로세스 장애 시 Patroni가 자동
  재기동하고(감지 0.05~8.5초 · 서비스 재개 13.0~22.4초 실측 6표본, ADR-020), API·워커는 끊긴 연결을
  재수립한다(읽기 요청은 1회 재시도, ADR-023). 작업 큐가 DB 안에 있어 미처리 임베딩
  작업도 유실 없이 재개되고 정합성 카운터가 0으로 수렴한다 — 문서·벡터·큐·관계가
  한 시스템으로서 함께 복구되므로, 이 검증된 경로에는 "벡터는 돌아왔는데 큐는
  유실된" 반쪽 복구가 없다 (`scripts/demo_recovery.sh` 타임라인).
- **워커 프로세스 장애 자동 복구 (배포 호스트)**: 워커가 SIGKILL·OOM으로 사라지면
  스스로 살아날 수 없고, 되살리지 않으면 임베딩 파이프라인이 통째로 멈춘다 — DB
  장애와 달리 화면은 멀쩡한 채 새 문서만 영원히 검색되지 않는다. 배포 호스트에서는
  systemd 유닛이 워커를 되살리고, 재기동한 워커가 좀비 잡을 임계 후에 회수한다.
  그 대기 동안에도 다른 잡은 계속 처리되어 크래시의 영향은 잡 하나로 격리된다.
  워커를 반복적으로 죽이는 잡은 재시도 예산을 소진한 뒤 `error`로 격리되어 나머지
  파이프라인을 막지 않는다 (ADR-038). **재부팅 생존은 여전히 없다** — 그건 DB도
  함께 사라지는 문제라 워커만 살려도 붙을 곳이 없다.
- **노드 장애 페일오버 (미검증)**: 노드 간 리더 선출·승격과 OpenProxy의 새 Primary
  추적은 OpenSQL 멀티노드 아키텍처의 경로이지만, 대회 지시에 따른 **Single 구성에서는
  검증할 수 없었고 하지 않았다** (ADR-020). 노드 사망으로부터의 복구도 마찬가지다.
  HA 설계(단일 엔드포인트 접속·명시적 트랜잭션·폴링 주 경로·WAL 내구 큐)는 유지하며,
  노드를 늘리는 것으로 요건이 충족되도록 남겨 둔다 (ADR-020 결정 2).

  > 정확한 표현은 "무중단"이 아니라 **"짧은 중단 후 자동 복구"**다. Single 구성에서
  > 실측된 중단은 DB 프로세스 재기동 수 초이며 그 구간의 요청은 실패한다. 멀티노드의
  > 장애 감지~승격은 Patroni 설정 기준(`ttl=30s`) 수십 초로 예상되나 실측하지 못했다.
  > 문서·데모에서 과장하지 않는다.
- **백업·PITR (구성하지 않음)**: `archive_mode = on`이지만 `archive_command = "/bin/true"`라
  WAL을 보관하지 않으며 barman도 세우지 않았다 (ADR-020 결정 6). Single에서 노드 사망에
  대응하는 수단은 HA가 아니라 DR인데, 그 DR도 이 설치에는 없다.

## 6. Identity · 인증 · 권한 요구사항

코어 계약에 열람 의미론이 포함되므로 모든 코어 연산은 "열람 범위"를 전제로 실행되고,
그 기준점이 주체(identity)다. §4의 경계 규칙을 적용하면 세 개념의 소속이 갈린다:
**Authorization은 코어다**(열람 술어는 하나, 전 경로 공유). **Identity는 코어의
어휘다**(소유와 열람 범위가 붙는 주체 식별자 — 인터페이스 중립). **Authentication은
인터페이스별 구현이다**(브라우저는 세션, 프로그램은 토큰, 로컬 MCP는 프로세스 신뢰 —
방식은 달라도 전부 같은 종류의 주체로 해석된 뒤 코어에 도달한다).

### 요구사항

| # | 요구사항 |
|---|---|
| R1 | 모든 코어 연산은 해석된 주체(또는 미인증)를 **명시적으로** 받는다. services가 `user_id`를 명시 인자로 받는 구조가 이것이다 |
| R2 | 미인증·미해석 주체는 항상 **가장 좁은 범위로 떨어진다** (fail-closed). 배포 경계에 따라 둘을 구분한다 — 공개 HTTP 표면의 미인증 요청은 **신뢰되지 않는 익명(untrusted anonymous)**으로 아무 문서도 보지 못하고(ADR-028), 사용자가 자기 자격으로 기동한 로컬 프로세스(stdio MCP)는 **신뢰된 로컬 컨텍스트(trusted local context)**로 public까지 본다(ADR-025) |
| R3 | 자격증명은 주체와 분리되고, 한 주체가 여러 자격증명을 가질 수 있으며, **각각 독립적으로 폐기 가능**해야 한다 |
| R4 | **사칭 불가** — 주체 식별자를 요청 데이터(헤더·툴 인자)로 받지 않는다. 주체는 서버가 발급·보관한 자격증명의 검증으로만 해석된다. `X-User-Id` 제거(ADR-028)와 MCP 툴 인자 금지(ADR-025)가 이 원칙의 사례다 |
| R5 | **공급의 귀속** — 어떤 경로로 들어오든 문서는 삽입 시점에 소유자와 visibility가 확정된다. MCP는 `MCP_USER_ID`를 소유자로 쓰고 미설정이면 공급을 거부한다(ADR-036). 커넥터가 넣는 문서도 예외 없다 |
| R6 | 귀속(누가 넣었나)과 출처(어디서 왔나)는 다른 개념이다. provenance는 identity 모델이 아니라 별도 스키마의 몫이며, 외부 소스 연결 시점에 정한다 (§4 원본 비보관 원칙과 같은 태도) |

### 주체별 필요 수준

| 주체 | 역할 | 필요한 identity 수준 | 현재 상태 |
|---|---|---|---|
| 사람 (Web UI) | 소비 + 공급 + 큐레이션 + 관리 | 완전한 개인 주체. 소유·열람 범위·관리 권한(열람과 분리, ADR-028)이 붙는다 | ✅ username/password + 서버 측 세션, 관리자 발급 계정. 자기 비밀번호는 `/settings`에서 바꾸고, 잊은 경우는 운영자 CLI가 재설정한다 (ADR-040) |
| 프로그램 (REST) | 소비·공급 | 주체로 해석되는 **비대화형 자격증명** — 장수명 · 독립 폐기 · 쿠키 비의존 | ✅ 사람 주체의 위임 API 토큰 · `read`/`read_write` (ADR-034) |
| Connector | 공급 특화 프로그램 | 프로그램과 동일 + 귀속 규칙(R5) | 자격증명 경로 ✅ · 커넥터 구현 ❌ |
| AI Agent (MCP) | 위임받은 소비자·공급자 | 자기 주체가 아니라 **위임되거나 부여된 범위** | ✅ 로컬 stdio 1인 구성에서 읽기 3개·쓰기 1개 (ADR-025·036) |
| 미인증 | — | 주체 없음 — R2의 두 구분을 따른다 | ✅ 방향 일치 |

### 이 기준선이 확정하는 것

- **IA-1 (주체 모델의 확장 가능성)**: 주체 모델은 비인간 주체로 확장 가능해야 하며,
  사람임을 전제하는 필드·정책을 새로 추가하지 않는다. 현재 프로그램 자격증명은 사람 주체가
  발급하는 **위임 토큰**으로 확정했다 (ADR-034). 서비스 주체(자체 계정)는 외부 소스 연결과
  provenance 정책이 필요한 ROADMAP 2단계에서 재검토한다.
- **IA-2 (최소 권한과 독립 폐기)**: 비대화형 자격증명은 독립적으로 폐기 가능해야 하고,
  클라이언트가 필요한 작업 범위보다 넓은 권한을 요구하지 않도록 **제한할 수 있어야
  한다. 현재 scope는 기본 `read`와 `read_write` 두 단계이며 토큰 행 삭제로 각각 독립 폐기한다
  (ADR-034). 발급·폐기는 사람 주체가 웹의 계정 설정 화면에서 직접 한다 — 세션 전용 경계를
  지키면서 발급을 사람 손에 두는 자리다 (ADR-040). 리소스 단위 세분화는 현재 범위의 non-goal이다.
- **IA-3 (에이전트 불변식)**: AI 에이전트도 동일한 authorization 계약을 우회할 수 없다.
  **에이전트는 자신에게 위임되거나 부여된 권한을 넘을 수 없다.** 현재 로컬 MCP는 사람
  주체 위임으로 읽고 공급하며, 공급 문서의 소유자는 `MCP_USER_ID`로 고정되고 주체 없는 쓰기는
  거부된다 (ADR-036). 향후 서비스 주체가 생기면 해당 주체로 동작할 수 있다. 원격
  MCP의 transport·인증 방식은 지금 결정하지 않는다 (ADR-025 트레이드오프 유지).

## 7. 하지 않는 것

- **답변 생성 LLM을 탑재하지 않는다.** 책임은 근거 공급까지다 (ADR-015). 재검토는
  ROADMAP 4단계 착수 시점의 별도 ADR로만 한다.
- **"항상 최신" · "실시간 동기화"를 주장하지 않는다.** 보장은 버전 일관성 + 최신
  수렴이며, 지연은 존재하고 관측된다 (ADR-015).
- **파일 보관소가 아니다.** §4의 원본 비보관 원칙. ECM의 보존·기록관리·규정준수 기능을
  만들지 않는다.
- **범용 데이터 이동 도구가 아니다.** 다루는 것은 문서성 텍스트 데이터뿐이다. 테이블·
  제약·프로시저를 옮기는 DB 마이그레이션은 다른 제품의 영역이다 (`ROADMAP.md`).
- **범용 벡터 저장소가 아니다.** 임의 데이터의 임베딩을 맡기는 embedding-as-a-service가
  아니다. 문서라는 도메인이 계약(버전·열람·관계)의 전제다 (ADR-032).
- **멀티테넌트 SaaS가 아니다.** 한 설치 = 한 조직 (ADR-028).
- **자동 파괴적 큐레이션을 하지 않는다.** 중복·유사는 후보로 제시하고 판단은 사람이
  한다 (§5 C3의 비대칭 유사도 원칙). 이 제동의 재검토는 ROADMAP 3단계 착수 시점에만
  한다 — 착수 조건에 「자동 병합하지 않는다」 재검토가 명시돼 있다.
- **AI 클라이언트를 대체하지 않는다.** 챗 UI·에이전트 프레임워크를 만들지 않는다.

## 8. 발전 경로

단계와 착수 조건의 정본은 `ROADMAP.md`다. PRD가 적는 것은 관통선 하나다: **모든
단계에서 OpenArchive의 정체성은 "파생 산출물이 원천을 검증 가능하게 추적한다"이며,
단계가 올라갈수록 파생의 수준이 올라간다.**

| ROADMAP 단계 | 파생의 수준 |
|---|---|
| 0. 신뢰 가능한 파이프라인 (현재) | 벡터·관계 수준 — 텍스트에서 임베딩·그래프가 파생 |
| 1. 프로그래매틱 플랫폼 | 동일 — 공급 주체가 사람에서 프로그램으로 확장, 같은 계약의 적용을 증명 |
| 2. 외부 소스 연결 | 시스템 경계를 넘는 파생 — 출처(provenance)와 source-of-truth 규칙으로 계약 확장 |
| 3. 지식 큐레이션 최소형 | 지식 수준 — 중복 판정·선별·병합 후보를 기존 프리미티브(`content_hash`·overlaps·버전·태그)로, 판단은 사람이 |
| 4. Knowledge Base / Living LLM Wiki | 정리된 지식 그 자체가 파생물 — "이 페이지는 어떤 소스의 어떤 버전에서 나왔고 지금 얼마나 낡았는가"를 증명 |

장기 비전은 현재 제품의 피벗이 아니라 같은 불변식의 복리다 — 지속 갱신되는 위키가
신뢰받으려면 파생 상태의 증명이 필요한데, 그 증명 장치가 지금의 코어 계약이다. 4단계의
생성을 어디에 둘지(코어 밖의 특권 클라이언트 vs 옵션 레이어 내장)는 그 시점의 ADR로
정하며, 그때까지 ADR-015 결정 3(생성 LLM 미탑재)은 유효하다.

## 9. 검토 후 미채택

- **키워드 + 벡터 RRF 결합** (ADR-016): `to_tsvector('simple')` 원안은 한국어 조사 때문에
  0건을 반환해 `pg_trgm`으로 바꿔 실 BGE-M3 63문서·299청크에서 측정했다. **trigram은 질의어의
  포함 여부는 판정하지만 순위를 만들지 못한다** — `word_similarity`가 후보의 대부분을 1.000
  동점으로 매겨(`OpenSQL` 125개 중 109개) 순서가 보조 정렬로 갈린다. RRF는 순위를 입력으로
  받으므로 한쪽이 무작위면 융합이 성립하지 않는다. 검색은 벡터 진입점과 그래프 확장을 유지한다.
  **한국어 키워드 랭킹은 형태소 분석기가 생긴 뒤에 다시 본다.**

## 10. MVP 제외 사항

- 실무 ECM의 전체 인증·인가 — 사람 주체의 세션 로그인·관리자 발급 계정과 프로그램용 위임
  API 토큰은 범위에 들어왔지만 문서 단위 `public`/`private`와 `read`/`read_write`만 지원하는
  최소형이다 (ADR-028·034). 그룹·공간·권한 상속·디렉터리 연동·서비스 주체는 여전히 MVP 밖이다
- 셀프서비스 비밀번호 재설정 — 메일 발송 인프라를 요구한다. 잊은 비밀번호는 운영자가
  `openarchive reset-password`로 푼다. 관리자가 남의 비밀번호를 바꾸는 경로는 권한 경계상
  두지 않는다 (ADR-040)
- 플랫폼 내 답변 생성 LLM — MCP 클라이언트에 위임 (ADR-015)
- HWP/HWPX 파싱 — 파서 품질 리스크가 큼. 4종(PDF/DOCX/TXT/MD) 완성 후 여유 시에만 검토
- SSE/웹소켓 실시간 알림 — 프론트 폴링(2초)으로 대체
- 임베딩 배칭·캐싱·폴백 체인 — 데모 규모에서 불필요한 최적화
- 다국어 UI, 모바일 대응
