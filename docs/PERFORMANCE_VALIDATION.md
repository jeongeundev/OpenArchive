# 검색·문서 처리 성능 검증

기능 테스트와 성능 검증은 서로 다른 질문에 답한다. 테스트는 권한·버전·작업 생성 규칙을 확인하고,
이 문서의 도구는 자료와 요청이 늘어날 때 검색 계획·응답 시간·작업 대기를 측정한다.
측정값을 최대 사용자 수나 모든 장비의 성능 보장으로 해석하지 않는다.

## 재현 준비

소스 체크아웃과 `backend/.venv`가 필요하다. 검색 계획 도구는 `[dev]`, 실제 문서 처리 도구는
`[dev,local]` 의존성을 설치한다. 실제 환경은 운영 문서대로 OpenProxy VIP 단일 DSN을
`DATABASE_URL`에 주입한다. 접속 비밀번호를 명령 기록이나 결과 파일에 직접 넣지 않는다.
로컬 `pgvector/pgvector:pg17`에서도 실행할 수 있지만 OpenProxy 동작의 증거는 되지 않는다.

검증 전용 DB에서 실행한다. 기본 스키마에 `vector`·`pg_trgm` 확장과 제품 마이그레이션이
설치되어 있어야 한다. 클러스터 설정·애플리케이션 스키마·검색 SQL은 도구가 변경하지 않는다.

## 검색 계획과 HNSW

```bash
backend/.venv/bin/python scripts/benchmark_search.py --out benchmark-results/search.json
```

기본 크기는 500개 문서 × 40개 청크 = 20,000개 청크다. 1024차원의 독립적인 정규화 합성
벡터를 사용하고, 모든 벡터가 서로 다른지 검사한다. 실제 BGE 의미 검색 품질 표본은 아니다.

도구는 고유 이름의 일반 검증 스키마를 한 트랜잭션 안에서 만들고, 제품 마이그레이션을 적용한다.
기존 public 확장을 사용하므로 CREATE SCHEMA 권한이 필요하다. 벡터는 인덱스 없는 검증
테이블에 COPY로 넣고, 제품과 같은 HNSW 인덱스를 만든 뒤 ANALYZE한다. 이것은 대량
초기 적재 조건이며, 운영 중 증분 삽입 비용과 구분한다. 일괄 인덱스 생성에만 `maintenance_work_mem=256MB`를 적용한다. 검색에는 이 설정을
변경하지 않는다. 종료 시 성공·실패 모두 rollback한다.
OpenProxy에서 누수되는 임시 테이블이나 세션 단위 search_path 설정은 사용하지 않는다.

검색에는 제품의 `SEARCH_SQL`, `hnsw.ef_search=200`, `random_page_cost=1.1`, `jit=off`를
사용한다. HNSW를 강제로 선택하지 않는다. 광범위 검색·태그·파일 유형 조건에서 실행 계획과
직접 결과 개수, 비공개 문서 누출 여부를 기록한다. 실제 관계 그래프를 만들지는 않으므로
관계가 많은 전체 검색 비용까지 대표하지 않는다.

비교 실행은 후보 거리 정렬에 `+ 0`을 붙여 HNSW 사용만 막는 정확한 거리 계산이다.
문서·발췌용 B-tree 인덱스는 유지한다. 결과 문서의 집합 일치율은 근사 검색과 정확한 거리
검색의 차이를 보여주며, 사용자가 찾는 정답의 정확도를 뜻하지 않는다. EXPLAIN의 시간은
계측 부담이 있으므로 일반 실행 시간과 분리한다.

## 지속 업로드·검색과 큰 파일

```bash
backend/.venv/bin/python scripts/benchmark_pipeline.py --out benchmark-results/pipeline
```

기본 측정은 서로 다른 임시 계정 4개, API 프로세스 1개, 실제 BGE-M3 워커 1개다.
30초 동안 초당 4개의 문서를 고정 간격으로 보내고, 네 계정이 검색을 계속한다. 입력은
프로젝트 README·아키텍처 문서에서 가져오며, 계정별 검색 응답에 다른 계정의 비공개 문서가
포함되지 않는지 검사한다. API 포트 18024는 비어 있어야 한다.

이어서 프로젝트 문서 텍스트와 합성 잡음 이미지를 가진 20MB급 DOCX를 올리고 작은 문서를
뒤에 보낸다. 원본 바이트 크기와 추출 텍스트 길이를 분리한 유효한 파일이며, 이미지는 원본
저장 크기를 만들기 위한 fixture다. 이미지의 의미나 OCR 품질을 측정하지 않는다. DOCX의
추출 텍스트는 서비스 상한인 500,000자 이내다. 이 상한은 원본 업로드 50MB 제한과 별개다.

본문이 500,001자인 TXT가 HTTP 400으로 거절되고 문서가 남지 않는지도 먼저 확인한다.
원본 크기가 50MB 이하라는 이유만으로 무제한 텍스트가 허용되는 것은 아니다. 큰 작업 뒤의
작은 문서가 얼마나 기다리는지와 최종 준비 상태를 확인하며, 다양한 PDF·OCR 문서의 비용과는
구분한다.

1초 간격으로 문서·청크·대기/처리/실패 작업을 관찰한다. 최종 판정은 HTTP 실패가 없고,
작업이 모두 끝나며, 미준비 문서와 청크 버전 불일치가 0인지다. 원본 바이트의 해시도 확인한다.
상한 초과 TXT의 예상된 400은 HTTP 실패 집계와 구분한다. 검색 준비된 문서를 가진 계정의
검색이 비어 있는 경우도 별도로 센다. 초당 완료량·큐 증가·유입 종료 후 대기 시간은 함께 봐야 한다. 저장 성공 응답만으로 검색 준비가
완료됐다고 판단하지 않는다.

도구는 자신의 API·워커를 종료하고 본 회차 계정의 문서·파일·작업·계정·세션만 삭제한다.
프로세스를 강제 종료하거나 DB가 계속 접근 불가능하면 정상 정리 경로가 끝나지 않을 수 있다.
결과의 `cleaned_up`과 검증 계정 접두사 `pipeline-bench-`의 잔존 여부를 확인한다.

결과 JSON과 API·워커 로그는 지정한 출력 폴더에 쓴다. 소스 체크아웃·접속 DB·모델·장비와
측정 조건을 함께 기록해야 결과를 비교할 수 있다. 오류 로그는 원인을 조사할 때 필요하지만,
외부 공유 전 접속 정보 등 민감한 내용이 없는지 확인한다.

## 실제 OpenSQL 측정 — 2026-10-03

Apple Silicon의 x86-64 Rocky Linux VM 3노드, PostgreSQL 17.8·pgvector 0.8.1·OpenProxy 1.1.3을
사용했다. 앱·실제 BGE-M3 모델은 맥 네이티브다. 주 노드로 라우팅되는 plain 트랜잭션이며,
장애 주입이나 클러스터 설정 변경은 하지 않았다. 서버 장비의 성능을 대표하지 않는다.

### 20,000 청크의 검색

500개 문서의 20,000개 벡터가 모두 서로 다른 것을 확인했다. 15개 계획 모두 HNSW를 사용했고,
각 실행에서 비공개 문서 누출 없이 직접 결과 10개를 반환했다. 관계 그래프는 비어 있다.

| 조건 / 각 5회 | 제품 SQL 중앙값 | 정확한 거리 계산 중앙값 | 정확한 결과와의 문서 집합 일치율 |
|---|---:|---:|---:|
| 광범위 | 351ms | 4,742ms | 70% |
| 태그 | 142ms | 589ms | 52% |
| 유형 | 110ms | 2,134ms | 80% |

전체 중앙값은 155ms 대 2,134ms다. 조건별 비용을 위 표처럼 구분해야 한다. 각 쌍에서 제품 SQL을
먼저 실행해 캐시 영향이 있고, 반복 횟수도 적으므로 통계적 성능 보장으로 쓰지 않는다.
합성 벡터에서의 근사 검색 일치율은 실제 문서의 정답 재현율이 아니다. 이 측정에서 일부 정확한
거리 검색 결과를 놓친 사실도 함께 기록한다.

인덱스 생성은 기본 메모리 64MB에서 약 13분 이상 진행하다 제한 시간에 가까워져 검증 작업만
취소했다. 완료 시간으로 기록하지 않는다. 검증 트랜잭션에 256MB를 적용한 재측정은 COPY 58초,
인덱스 생성 358초였다. 검색 시간과 초기 인덱스 생성 시간은 다르며, 운영 중 증분 적재 성능을
이 숫자로 대신하지 않는다. 검증 스키마는 rollback으로 사라졌다.

### 지속 유입과 워커 수

각 회차에 검증 계정 4개가 30초 동안 초당 4개, 총 120개 문서를 공급했다. 검색은 계정별로
순차 반복했으므로 느린 조건에서는 검색 횟수가 줄어든다. 동일한 검색 QPS를 강제한 비교는 아니다.
입력 텍스트 SHA-256은 두 회차에서 같았다. 요청 유입을 끝낸 뒤 모든 작업이 수렴했다.

| 워커 수 | 업로드 중앙값 / 95% 지점 | 검색 횟수 | 검색 중앙값 / 95% 지점 | 유입 종료 후 수렴 | 관찰된 최대 작업 대기·처리 합계 |
|---|---:|---:|---:|---:|---:|
| 1 | 156 / 231ms | 235 | 254 / 338ms | 34.0초 | 87 |
| 2 | 323 / 478ms | 183 | 412 / 526ms | 21.7초 | 82 |

HTTP 실패·빈 검색·다른 계정의 비공개 문서 노출은 없었다. 위 최대값은 1초 간격 표본 중의
최대이며 순간 최대를 보장하지 않는다. 워커 2개는 큐 수렴을 앞당겼지만 요청 응답은 느려졌다.
CPU·GPU·DB 구간별 사용량을 분리 계측하지 않았으므로 지연 증가의 책임을 특정하지 않는다.
일괄 적재의 대기와 대화형 검색 지연의 균형으로 워커 수를 정해야 한다.

다중 워커 재현은 위 명령에 `--workers 2`를 추가한다. 회차는 차례로 실행한다.

### 20MB급 원본과 긴 처리 작업

DOCX 원본은 20,091,593바이트, 추출 텍스트의 청크는 133개였다. 이미지 부분은 텍스트 임베딩
대상이 아니며, 모델이 처리한 것은 프로젝트 문서 텍스트다. 단일 워커에서 저장 응답은 4.8초,
그 뒤 작업 수렴은 25.7초였다. 두 워커에서는 각각 5.0초와 25.9초였다. 두 회차 모두 원본
해시가 일치했고, 최종 미준비·작업 실패·청크 버전 불일치는 0이었다.

큰 파일 뒤에 보낸 작은 문서는 작업 생성부터 선점까지 단일 워커 약 22.3초, 두 워커 약 2.9초를
기다렸다. 이 시간은 DB의 `started_at - created_at`이며 생성 트랜잭션의 커밋 전 시간도 포함한다.
단일 워커에서는 앞의 긴 작업이 뒤의 작은 작업을 기다리게 한다는 운영 한계를 확인했다.

### 실제로 발견하고 수정한 HTTP 500

첫 부하 회차에서 검색 1회가 `InvalidSqlStatementName`(SQLSTATE 26000)으로 실패했다.
로그에는 OpenProxy가 바꾼 이름의 prepared statement가 서버에 없다는 오류가 남았다.
프록시 내부에서 그 상태가 만들어진 정확한 경로까지는 확인하지 않았다.

실제 pgvector DB 테스트에서 반복 실행한 명령문을 서버에서 `DEALLOCATE ALL`로 제거하면
같은 실패가 재현됐다. 애플리케이션 공통 풀의 `prepare_threshold=None`으로 자동 준비를 꺼,
클라이언트가 사라진 명령문 이름을 다시 참조하지 않도록 했다. 파라미터 바인딩·VIP 접속·
트랜잭션·권한 SQL은 유지하며, 이 오류를 503으로 바꾸거나 재시도로 감추지 않는다.
이는 PL/pgSQL 함수 내부 generic plan과 별개이며 관계 함수의 설정도 유지한다.

수정 후 단일·두 워커 재측정에는 검색 500이 없었다. 한 회차에서의 속도 변화만으로 자동 준비를
끄는 비용 전체를 분리할 수는 없다. 명령문 재사용의 이점보다 관측된 호환성 실패를 피하는
선택이며, 후속 성능 측정에는 이 설정을 포함한다.

### 재시도 기록의 필요성

수정 후 각 회차의 임베딩 126건·관계 126건은 모두 한 번에 완료됐다. 이번 HTTP 500은
임베딩 재시도 문제가 아니라 API 세션 조회의 연결 호환성 문제였다. 기존 워커 상태·시도 수·
마지막 오류와 API 로그로 원인을 찾을 수 있었으므로, 별도 시도 이력 테이블은 추가하지 않았다.
여러 번 실패했다가 성공하는 작업을 조사할 때 과거 오류가 부족한지는 별도 운영 관찰 대상이다.


## 측정 소스와 후속 변경

위 20,000 벡터·지속 유입 표는 미리보기 필드 추가 전 검색 구현(`f3612d4`)의 측정이다.
이후 같은 버전 주변 청크의 미리보기 데이터를 추가했고, 자연어 조건의 4,000 벡터 비교에서는
SQL 중앙값 126ms 대 132ms를 관측했다. 후속 측정을 기존 20,000 벡터 결과에 대신 넣지 않는다.
조건과 발췌 품질의 미해결 사례는 [검색 품질 검증](SEARCH_QUALITY_VALIDATION.md)에 있다.
