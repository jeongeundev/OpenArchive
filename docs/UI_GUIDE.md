# UI 디자인 가이드

## 디자인 원칙
1. 도구처럼 보여야 한다. 마케팅 페이지가 아니라 매일 쓰는 문서관리 대시보드.
2. 데이터가 주인공이다. 문서 목록·임베딩 상태·검색 결과가 장식 없이 즉시 읽혀야 한다.
3. **사용자 화면은 인프라를 드러내지 않는다.** 사용자가 확인해야 하는 것은 "장애가 났다"는 사실이 아니라 **"업로드와 검색이 오류 없이 계속 동작한다"**는 결과다. 접속 DB 노드, 페일오버 발생 여부 같은 운영 정보는 사용자 화면에 넣지 않는다.
4. 운영·데모용 관측은 **별도 채널**로 분리한다 — 관리자 전용 상태 패널, `GET /api/system/status`, 워커·API 터미널 로그. 복구 증거는 여기서 보여준다.

> **원칙 3의 배경**: 고가용성의 가치 명제는 "사용자가 장애를 인지하지 않는다"이다(`PROJECT_CONTEXT.md` 핵심 구현 목표 1). 사용자 화면에 노드 IP를 띄우는 것은 그 명제와 모순된다. 데모에서는 사용자 화면(정상 동작)과 관측 채널(장애·복구 증거)을 **나란히** 보여주는 것이 더 강한 증명이다.

## 화면 구성

### 사용자 화면 (3화면)
1. `/` — 문서 목록 테이블 + 업로드 드롭존. 각 행에 임베딩 상태 배지(2초 폴링 갱신)
2. `/documents/[id]` — 메타데이터, **텍스트 버전 이력**, 청크 목록, **추출 텍스트 편집**, 재업로드(새 버전), 관련 문서, 태그 추천
3. `/search` — 질의 입력 + 태그/유형 필터 + 결과 목록(유사도 점수, 매칭 청크 발췌, **문서 상세 링크**). "실행된 SQL 보기" 토글

> 이 세 화면은 **인프라 상태를 일절 노출하지 않는다.** 페일오버가 일어나도 화면 구성은 달라지지 않으며, 사용자는 업로드와 검색이 계속 성공하는 것만 본다.

> 검색 결과의 링크는 **문서 상세 화면으로** 간다. 원본 파일로 가지 않는다 — 원본 파일은 보관하지 않기 때문이다(아래 용어 규칙).

### 용어 규칙 — 원본 파일과 추출 텍스트를 구분한다

업로드된 PDF·DOCX는 텍스트만 추출해 저장하고 **파일 자체는 보관하지 않는다**(ADR-017). 화면 문구가 이를 뭉뚱그리면 "PDF를 편집한다"는 오해가 생긴다.

| 화면에 쓸 말 | 쓰지 말 것 | 이유 |
|---|---|---|
| 추출 텍스트 | 본문, 원문 | 원본 파일과 구분되지 않는다 |
| 텍스트 버전 이력 | 문서 버전 이력 | 파일 버전 이력으로 읽힌다 |
| 문서 상세 링크 | 원문 링크 | 원본 파일로 가지 않는다 |

### 추출 텍스트 편집 (`/documents/[id]`)

정합성 파이프라인을 화면에서 직접 보여주는 장치다. 한 문장을 고치고 저장하면 상태 배지가 `pending → processing → ready`로 바뀐다.

- **편집 영역 레이블은 "추출 텍스트"**다. `content_type`이 `pdf`·`docx`면 편집 영역 위에 안내를 **상시 표시**한다 (접었다 펴는 툴팁이 아니라 항상 보이는 한 줄):

  > 원본 파일이 아니라 업로드 시 추출된 텍스트를 편집합니다. 저장하면 새 텍스트 버전이 만들어집니다.

- 보기 ↔ 편집 **토글**. 편집 중에는 저장·취소만 노출하고 다른 액션(삭제·재업로드)은 비활성화한다
- 저장 시 화면이 읽어온 `version`을 함께 보낸다. **409를 받으면 덮어쓰지 않는다**:

  > 다른 곳에서 문서가 수정되었습니다. 새로고침 후 다시 시도하세요.

  편집 내용을 지우지 말고 화면에 남긴다 — 사용자가 복사해 둘 수 있어야 한다
- 저장 후 2초 폴링으로 상태 배지를 갱신한다. 배지 색은 기존 시맨틱 색을 그대로 쓴다

### 관련 문서 · 태그 추천 (`/documents/[id]`)

- 각 관련 문서 항목에 **점수**와 **"v{n} 기준"**을 함께 표시한다. `based_on_version`은 "지금 보이는 결과가 몇 번 버전의 벡터에서 나왔는가"를 답하며, 버전 일관성 보장을 화면에서 뒷받침한다
- 태그 추천은 클릭하면 해당 태그가 문서에 추가되는 형태. 추천은 제안일 뿐 자동 적용하지 않는다
- **미색인 문서**(청크가 아직 없음 — 최초 업로드 직후 또는 임베딩 실패)에는 빈 목록 대신 안내를 노출한다:

  > 임베딩이 완료되면 표시됩니다.

  오류로 보이게 하지 않는다. 빨간색·경고 아이콘을 쓰지 않고 보조 텍스트(text-neutral-500)로 둔다

### 유사 문서 표시 — "중복"이라고 쓰지 않는다

유사도 점수는 비대칭 지표라 중복을 확정할 수 없다(ADR-018). 문구와 동작을 다음으로 제한한다.

| | 표시 | 동작 |
|---|---|---|
| `content_hash` 완전 일치 | "동일한 텍스트의 문서가 있습니다" | 링크만 제공 |
| 점수 상위 항목 | "내용이 유사한 문서가 있습니다" | 링크만 제공 |

- 업로드를 막거나, 자동 병합하거나, "중복" 배지를 띄우지 않는다
- 임계값으로 경고를 켜지 않는다. 관련 문서 목록에 점수를 함께 보여주는 것으로 충분하며, 판단은 사용자가 한다

### 운영 화면 (1화면, 데모·운영 전용)
4. `/admin/status` — 관리자 전용 관측 패널
   - 현재 접속 DB 노드 (`inet_server_addr()`)
   - `pending` / `processing` / `error` 잡 수
   - **정합성 검증**: 원본 버전과 청크 버전이 어긋난 문서 수 (`c.version <> d.version`). 평상시 0, 재임베딩 중에만 증가했다가 다시 0으로 수렴한다 — **"원본-벡터 정합성"을 숫자로 보여주는 지표**
   - 임베딩 프로바이더명
   - 최근 재연결 이벤트 로그
   - `error` 문서 목록 + 재임베딩 버튼 (`POST /api/documents/{id}/reembed`)

> 정합성 검증 카운터가 데모의 핵심 지표다. 문서를 수정하면 잠깐 1로 올랐다가 워커가 처리하면 0으로 돌아온다. 페일오버를 일으켜도 결국 0으로 수렴하는 것을 보여주면, 이 과제가 요구한 "장애 상황에서도 원본과 벡터의 정합성이 유지된다"를 한 화면으로 증명할 수 있다.

사용자 내비게이션에 노출하지 않는다. 데모 시 사용자 화면과 나란히 띄워 "장애가 있었고, 복구됐고, 사용자는 몰랐다"를 한 화면에 담는다.
