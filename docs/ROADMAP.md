# 로드맵

> **이 문서는 후보의 목록이지 약속이 아니다.** 무엇을 지금 하지 않는지, 왜 하지 않는지를 기록하고,
> 항목을 채택할 때는 ADR로 근거를 남긴다. 1차 제출 범위는 이슈로 관리한다 — 이 문서는 그 다음을 다룬다.

## 정체성: 어디까지가 코어인가

OpenArchive의 코어는 **표준 PostgreSQL + pgvector 위에서 도는 문서 지식 플랫폼**이다.
저장·임베딩 파이프라인 조율(트리거)·원본-벡터 정합성·하이브리드 검색·관계 그래프가 전부
DB 계층에 있고, 애플리케이션 코드에는 파이프라인을 조율하는 부분이 없다.

- **OpenSQL은 고가용성이 필요한 프로덕션의 배포 대상이다.** 개발과 전체 테스트는 공개
  `pgvector/pgvector:pg17` 이미지에서 돈다 (ADR-026). 코어가 표준 스택이라, 누구나 자기
  PostgreSQL 위에 이 플랫폼을 올릴 수 있고 기업은 HA가 번들된 OpenSQL로 프로덕션을 구성한다.
- **비슷한 오픈소스와의 차이.** Paperless-ngx는 파이프라인 조율을 앱(Celery)이 맡고, Onyx(구
  Danswer)는 벡터를 별도 엔진(Vespa)에 둔다 — 원본과 파생 데이터의 정합성이 앱 코드의 책임이 된다.
  OpenArchive는 조율과 벡터가 **같은 DB 트랜잭션 경계 안**에 있어, 정합성을 앱이 아니라 DB가
  보장하고 어긋난 구간을 쿼리로 관측할 수 있다 (PRD 「정의와 가치」 절).

### 다섯 구분으로 본 현재 구조

시스템을 설명할 때 다음 다섯 구분을 쓴다. **설명용 개념 모델이며 공식 용어가 아니다**
(ADR-031 결정 2) — 커밋 스코프·디렉토리·"DB 계층" 같은 기존 어휘를 대체하지 않는다.

| 구분 | 현재 구현 | 상태 |
|---|---|---|
| **Ingestion** (수집) | `POST /api/documents`(파일 업로드)와 `POST /api/documents/text`(JSON 텍스트) → `services/documents.py`의 두 입력 어댑터 → 공통 INSERT 헬퍼 | 진입점 2개, 파일 4종 + 직접 텍스트 2종. 파생 계약은 동일 (ADR-035) |
| **Processing** (변환·임베딩) | DB 트리거(잡 생성·코얼레싱) + 워커(청킹·임베딩) + edge 트리거(관계 생성) | 견고 — 조율이 전부 DB 안에 있다 |
| **Storage** (저장·정합성) | 테이블 8개(문서 6 + 인증 2), 제약·CASCADE·`vector(1024)` 타입, 정합성 관측 쿼리 | 코어 계약(ADR-015)의 자리 |
| **Retrieval** (검색·관계) | 단일 SQL 검색(정형+벡터+그래프) · 저장 edge · 위키링크 · 진단·클러스터 | 전 경로가 같은 열람 술어를 공유 (ADR-027) |
| **Interface** (소비) | Web UI · REST API · MCP — 같은 services 계층을 소비하는 대등한 인터페이스 (ADR-031 결정 3) | 위임 API 토큰으로 REST의 비대화형 소비·공급 가능 (ADR-034). 커넥터·MCP 쓰기는 다음 확장 |

## 확장점과 후보

원칙: 아래 항목 대부분은 코어를 바꾸지 않는다. 수집기는 `documents`에 INSERT하는 클라이언트일
뿐이고(임베딩 잡은 트리거가 만든다), 파서·임베딩 프로바이더는 인터페이스 뒤에 있다. 그래서
각 항목이 독립적인 기여 단위가 된다. 항목의 채택 여부와 순서는 아래 「단계적 발전 경로」에
비추어 판단한다 (ADR-031 결정 4).

### 파서 (`backend/app/services/parsing.py`)

| 후보 | 시기 | 메모 |
|---|---|---|
| HWP/HWPX | 2차 후보 | HWPX(ZIP+XML)부터. 파서 품질 리스크로 1차에서 보류한 이력 (PRD MVP 제외) |
| 스캔 PDF OCR | 장기 | 현재는 "스캔 이미지 PDF 미지원"을 명시적으로 거부한다 |
| 이미지 캡션 | 장기 | 캡션 생성 모델도 open-weight 제약을 따른다 (ADR-003) |

### 수집 커넥터 (= `documents` INSERT 클라이언트)

1차 범위는 대량 투입 최소형(#54)까지다. 그 다음:

| 후보 | 시기 | 메모 |
|---|---|---|
| 감시 폴더 | 2차 후보 | Paperless-ngx의 consumption 폴더 문법 |
| Obsidian vault 동기화 | 2차 후보 | `[[제목]]` 위키링크가 이미 있어(ADR-030) 궁합이 가장 좋다 |
| IMAP(이메일 수집) | 장기 | |
| 외부 DB 커넥터 | 장기 | 원본 PK·수정 시각·내용 해시 기반 증분 동기화. 삭제는 실삭제 대신 보관 전환이 안전하다. 동기화 문서와 OpenArchive 안에서의 텍스트 편집(ADR-017)의 충돌은 채택 전에 source-of-truth 규칙을 ADR로 정해야 한다 |

### 검토 워크플로

- **inbox 태그 최소형** (2차 후보): 업로드 시 일괄 태그의 연장 — 새 문서에 검토용 태그를 붙이고,
  검토 후 태그를 떼는 흐름. 상태 기계를 새로 만들지 않고 기존 태그·필터(ADR-024)를 재사용한다.
  승인 플로·상태 컬럼은 이 최소형으로 부족하다는 것이 확인된 뒤에만 검토한다.

### 임베딩 프로바이더 (`bge-m3` / `fake` 추상화 존재)

- open-weight 모델 추가, 리랭커 (장기). 벡터 컬럼은 `vector(1024)` 고정 — 프로바이더가 바뀌어도
  차원은 바꾸지 않는다 (CLAUDE.md 규칙).

### 검색

- **한국어 형태소 분석기 기반 키워드 랭킹** (2차 후보): trigram은 순위를 만들지 못해 RRF를
  접었다 (ADR-016). 형태소 분석기가 생기면 키워드+벡터 융합을 다시 본다 — PRD가 예약해 둔 항목.

### MCP · 이벤트

- MCP 쓰기 도구(`create_document` 등) (2차 후보): 현재 MCP는 읽기 전용 3개 도구다 (ADR-025).
  대회 규정도 MCP 커넥터·플러그인 형태의 개발을 명시적으로 권장한다.
- 이벤트 웹훅 (장기): "임베딩 완료" 등 이벤트 발행 — 서드파티 통합의 진입로.

### 권한

- 그룹·공간 단위 권한, SSO (장기): 현재는 한 설치 = 한 조직, 문서별 public/private 최소형이다
  (ADR-028). 열람 범위 술어가 한 곳(`visibility.py`)에 있어 확장 지점도 한 곳이다.

## 단계적 발전 경로

확장점 후보를 개별로 저울질하지 않고 이 경로에 비추어 정한다 (ADR-031 결정 4). 각 단계는
앞 단계의 증명 위에 서고, 착수 전 필요한 결정은 그 시점의 ADR/spec으로 확정한다 — 이 표는
목표와 착수 조건까지만 적는다.

| 단계 | 목표 | 착수 전 필요한 결정 |
|---|---|---|
| **0. 신뢰 가능한 파이프라인** (현재) | 원본-벡터 정합성·장애 복구·하이브리드 검색을 실측으로 증명한다 | — (1차 제출 범위, 이슈로 관리) |
| **1. 프로그래매틱 플랫폼** (M11 후보) | **프로그래매틱 인제스천을 1급 경로로 증명한다.** 성공 기준: 외부 프로세스가 `backend` 패키지를 import하지 않고 **HTTP만으로** 문서를 공급하며, 파이프라인(임베딩·관계·링크)이 웹 업로드와 동일하게 동작한다 | 텍스트 직접 생성 API 의미론·CORS 미도입은 **ADR-035**, 위임 토큰 인증과 `X-User-Id` 제거의 정합은 **ADR-034**로 확정. 남은 결정: 첫 커넥터 선정 · MCP 쓰기 도구 포함 여부 |
| **2. 외부 소스 연결** | 커넥터를 늘리고 증분 동기화를 지원한다 | source-of-truth 규칙 ADR(동기화 문서 vs OpenArchive 안에서의 텍스트 편집 ADR-017 — 위 외부 DB 커넥터 메모) · 출처(provenance) 스키마 |
| **3. 지식 큐레이션 최소형** | 이미 있는 프리미티브를 워크플로로 승격한다 — 중복 판정(`content_hash`·`overlaps`)→병합, inbox 태그 검토, 버전 해소. ADR-029 노선대로 벡터+SQL로, 생성 LLM 없이 | `UI_GUIDE.md`의 "자동 병합하지 않는다" 제동 재검토 |
| **4. Knowledge Base / Living LLM Wiki** | 문서 소스를 연결하면 선별·정리·관계화된 지식이 지속 갱신되는 위키에 도달한다 | ADR-015 결정 3(생성 LLM 미탑재) 재검토 — 생성을 밖에 둘지(MCP 경유 외부 AI) 옵션 레이어로 내장할지 |

## 하지 않는 것

> 제품 차원의 전체 목록은 **PRD 「하지 않는 것」 절이 정본**이다 (ADR-032). 아래는
> 확장 후보를 저울질할 때 직접 걸리는 항목만 다시 적은 것이다.

- **범용 DB 마이그레이션** (테이블·제약·프로시저 이전) — 별도 제품의 영역이다. 우리가 다루는
  것은 문서성 데이터의 수집뿐이다.
- **플랫폼 내 답변 생성 LLM** — 근거 공급까지가 책임이다 (ADR-015). 위 단계 경로의 Stage 4
  착수 시에만 재검토한다.
- **"항상 최신" 보장** — 보장 범위는 버전 일관성 + 최신 수렴이다 (ADR-015).

## 운영 메모

OpenSQL 평가 라이선스 만료(2026-09-10, ADR-021) 이후의 개발은 공개 pgvector 이미지에서
계속된다. 코어가 표준 스택이기 때문에 가능한 일이며, OpenSQL 고유 동작(OpenProxy 등)을 다시
검증할 일이 생기면 그 시점의 라이선스로 VM을 재구성한다 (`docs/SETUP_OPENSQL.md`).
