# 프로젝트 예시 질문 검색 평가

2026-10-03, 사용자가 검토하고 사용을 승인한 예시 질문 6개로 평가했다. 질문은 도구 작성자가
제안한 것이며, 독립적인 실제 사용자 질문 평가로 부르지 않는다. 결과를 보고 검색 코드를
조정하지 않았다. 이 문서는 프로젝트 검색의 검증 기록이며 발표 자료가 아니다.

## 방법

검색하기 전에 질문·기대 답변·관련 문서 목록을 고정했다.
평가 입력은 [project-examples.json](../scripts/eval/project-examples.json)에 있다.
README·아키텍처·운영·성능 검증·OpenSQL 구성 차이·PRD·로드맵의 7개 파일을 사용했다.
파일별 SHA-256을 입력에 기록해 측정 당시 자료를 구분한다. 제품의 `chunk_text`로 만든
214개 청크와 질문 모두 실제 `BAAI/bge-m3`로 임베딩했다.

실제 OpenProxy 단일 엔드포인트에서 제품 `search_documents`를 k=10으로 실행했다.
검증 문서는 고유 소유자의 비공개 문서로 적재하고 동일 소유자·검증 태그로 검색했다.
plain 트랜잭션과 제품 검색 설정을 사용했다. 문서·청크 쓰기는 전부 rollback했으며,
전후 기존 문서·청크·작업 개수가 같음을 확인했다. 관계 그래프는 생성하지 않았다.
업로드/OCR 경로 또는 전체 운영 자료를 대상으로 한 평가는 아니다.

문서 순위와 발췌의 답변 충족 여부를 구분한다. 전자는 사전 지정한 문서 목록 기준이며,
후자는 기록된 API 발췌 전체를 기대 답변과 비교한 수동 판정이다. 웹 화면의 첫 300자
미리보기는 별도로 확인했다. 생성형 답변의 정확도를 평가한 것은 아니다.

사전 지정 문서는 첫 번째 결과에서 4/6, 상위 5개에서 6/6, 상위 10개에서 6/6 발견됐다.
문서가 7개뿐인 작은 표본이므로 이 수치를 대규모 자료의 검색 성공률로 일반화하지 않는다.

비공개 문서 질문의 README 발췌에는 실제 답이 있었지만, 사전 정답 목록에 README를
포함하지 않아 지정 문서 기준 순위는 2위다. 결과를 본 뒤 정답 목록을 수정하지 않았다.
이 사례는 문서 제목만으로 정답을 지정하는 평가에도 한계가 있다는 뜻이다.

API 발췌 전체의 충분 판정은 2/6, 부분적 2/6, 부족 2/6이었다. 이는 평가자의 작은 표본
판정이며 자동 채점이나 외부 평가가 아니다. 순위만 보면 성공한 장애·수정 질문도
첫 발췌만 읽으면 답을 얻지 못한다. 수정 질문은 세 번째 README 발췌에 이전 버전 검색
설명이 있었지만, 첫 번째 아키텍처 발췌를 충분하다고 인정하지 않았다.

## 웹 미리보기에서 확인한 한계

현재 `SearchResults`는 발췌 전체의 앞 300자만 표시한다. 이 6개 질문의 첫 결과 모두
첫 300자만으로는 기대 답변을 충분히 제공하지 못했다. 비공개 범위와 작은 작업 대기처럼
API 발췌 안에 답이 있는 경우도 답이 뒤에 있어 잘렸다. 이 판정은 기록된 문자열을 제품의
300자 절단 규칙과 비교한 것이며, 브라우저 조작을 통한 사용자 테스트는 아니다.

검색 자체가 정답 문서를 찾는 것과, 그 문서에서 답이 있는 대목을 바로 보여주는 것은
서로 다른 과제다. 개선 우선순위는 **질문에 맞는 발췌 중심과 미리보기 범위를 고르는 것**이다.
정답을 뒤에 둔 긴 발췌를 모두 표시하면 화면이 길어지므로, 길이 제한을 없애는 것만으로
해결하지 않는다. 특히 문서 수정·DB 장애의 대목 선택과, 답이 뒤쪽에 있는 미리보기를
회귀 사례로 보존할 필요가 있다.

초기 평가에서는 제품의 청킹·순위·발췌·화면 구현을 변경하지 않았다. 이후 개선은 아래에 기록한다.
후속 개선은 별도 검증셋에서 기존 검색을 해치지 않는지 확인해야 하며,
이 6개 질문에만 맞춘 예외 규칙을 추가하는 근거로 쓰지 않는다.

## 재현 자료

- 질문·기대 답변·사전 관련 문서·입력 파일 해시: `scripts/eval/project-examples.json`
- 현재 입력을 기존 평가기로 문서 순위만 재측정하려면 `queries` 항목의 `relevant` 제목과 같은
  제목으로 원본 파일을 public 문서로 색인한 검증 전용 DB에서 아래 명령을 실행한다.
  기존 평가기는 사용자 주체를 전달하지 않으므로 이번 비공개 fixture에 그대로 적용할 수 없다.
- 아래 도구는 관계 결과도 포함한 문서 순위를 집계하므로, 이번 관계 없는 직접 검색과 비교할
  때 관계 생성 여부·자료 해시·모델·검색 소스 버전을 함께 기록한다. 발췌 수동 판정은 별도로 한다.

```bash
EMBEDDING_PROVIDER=local backend/.venv/bin/python scripts/eval_search.py \
  scripts/eval/project-examples.json --out benchmark-results/project-examples.json
```

현재 문서에는 신규 평가 결과가 포함돼 있으므로 측정 당시 파일 해시와 다를 수 있다.
같은 입력의 재현이 필요하면 이 문서를 추가하기 직전 소스 커밋 `f3612d4`의 파일을 사용한다.


## 후속 개선 — 미리보기와 전체 발췌

질문에 맞는 대목을 바로 보여주는 개선과, 문서 자체를 찾는 검색을 구분해 적용했다.
기존 전체 발췌 `content`를 유지하고 `preview`를 추가했다. 웹은 서버의 미리보기를 사용하고,
「발췌 더보기」를 누르면 주변 문맥 전체를 표시하며 다시 접을 수 있다. API·MCP에도 같은
미리보기를 제공한다. 관계 결과와 이전 판 결과에는 새 대목 선택을 적용하지 않는다.

미리보기는 이미 선택된 문서의 같은 버전 주변 청크 안에서 고른다. 한국어 단어 시작의
두 글자와 영문·숫자 토큰을 비교하며, 여러 대목에 반복되는 표현은 덜 반영한다.
이것은 형태소 분석이나 의미 이해가 아니다. 번호 질문은 기존 SQL이 선택한 중심 청크에서
해당 ADR·조항 번호부터 보여준다. 전체 발췌·문서 순위·유사도·열람 필터는 유지한다.
재임베딩 중 새 본문을 읽어 미리보기에 섞지 않는 회귀 테스트도 통과했다.

같은 질문 6개, 같은 입력 파일로 변경 전 서비스와 변경 후 서비스를 번갈아 실행했다.
소스 입력은 `fde4e8b` 기준이다. 최초 평가 뒤 README에 검증 문서 링크가 추가되었으므로
최초 평가와 별개로 같은 입력을 다시 비교했다. 문서 순위·점수·전체 발췌가 전부 같았다.
비공개 범위와 큰 파일 뒤의 작은 문서 대기는 첫 미리보기에서 바로 확인할 수 있게 됐다.
첫 미리보기만으로 기대 답변을 충분히 제공한 사례는 0/6에서 2/6이었다.

**서버 장애·문서 수정 질문의 핵심 대목 선택은 아직 해결되지 않았다.** 첫 결과의 기존
문맥 안에 원하는 설명이 없으면 미리보기 가공만으로 답을 만들 수 없다. 업로드 진단과
OpenSQL 장점 질문도 미리보기만으로 충분한 답을 제공하지 못했다. 완성된 의미 기반 발췌
선택이나 전체 검색 품질 문제의 해결로 기록하지 않는다.

예시 질문의 모델 예열 후 서비스 실행 중앙값은 변경 전 216ms, 변경 후 240ms였다.
다른 측정에서 별도 100문서·서로 다른 4,000개 합성 벡터를 사용해, 동일 트랜잭션에서
변경 전후 SQL을 순서를 번갈아 비교했다. 자연어 조건 9회 모두 HNSW·직접 문서 10개·
비공개 누출 0을 확인했고, 기존 결과 열 12개는 같았다. SQL 중앙값은 126ms 대 132ms였다.
이 소규모 회차는 용량 보장이나 장비 간 성능 비교가 아니다.

채택하지 않은 방식도 남긴다.

- 선택된 문서에서 가까운 청크 3개와 주변을 추가 조회하는 방식은 기존 4,000 벡터 비교에서
  SQL 중앙값 119ms를 186ms로 늘렸고, 질의어 일치만으로는 엉뚱한 대목을 골랐다.
- 요청 중 BGE-M3로 짧은 대목을 다시 임베딩하는 방식은 예시 질문 중앙값 약 2.27초로
  증가했고, 미해결 질문을 충분히 해결하지 못했다.
- 별도 CrossEncoder 모델도 검증용으로 비교했다. BGE 계열 모델은 후보 전체 비교에 수 초가
  들었고, 경량 모델도 이 한국어 표본에서 잘못된 대목을 골랐다. 제품 모델·의존성·기본 설정에는
  추가하지 않았다. 측정용 모델 비교 스크립트와 원본 로그는 내부 기록으로 보관한다.

다음 과제는 **답이 기존 발췌 밖에 있는 질문의 대목 후보를 개선하는 것**이다.
새 후보 생성·의미 비교는 미리보기와 다른 설계 변경이므로, 별도의 고정 평가 질문과
응답 시간·색인 비용을 함께 검증해야 한다. 이번 6개에 맞춘 질문별 예외를 추가하지 않는다.

## 후속 개선 — 추가 본문 후보

기존 SQL은 상위 `k * 5` 벡터 청크를 찾은 뒤 문서별 최고 청크 하나만 남긴다.
미해결 질문의 답이 이 후보 안에 이미 있었지만, 문서별 중복 제거에서 버려졌다.
따라서 첫 발췌를 교체하는 대신 직접 결과에 `passages`를 추가했다. 같은 문서·같은 버전의
후보를 거리순으로 최대 8개 반환한다. 각 대목은 중심 청크 번호, 주변 ±1청크의 본문,
기준 버전, 해당 청크의 유사도를 갖는다. REST·MCP에서 사용할 수 있고 관계·이전 판 결과는
빈 배열이다. 웹 첫 미리보기와 기존 발췌의 선택은 그대로다.

변경 전 기준은 `ef5af1e`이며 자료는 앞선 비교와 같은 `fde4e8b`의 7문서·214청크다.
실제 BGE-M3 질의 벡터와 실제 OpenProxy에서 k=10, 고유 소유자의 비공개·태그 격리 fixture로
확인했다. 승인된 예시 6개는 새 필드로 기존 결과가 바뀌지 않는지 확인하는 비교에만 사용했다.
문서 순위·첫 발췌·미리보기·점수·기준 버전·관계 정보가 모두 같았다. 기존 전체 검증과
106질의 평가를 처음부터 반복하지 않았다.

추가 대목의 본문은 고정된 기대 답변과 수동 비교했다.

| 기존 미해결 질문 | 추가 후보에서 확인한 설명 |
|---|---|
| DB 서버 하나가 꺼지면 서비스는 어떻게 돼? | 운영 가이드 중심 청크 21·22의 재기동·복구와 비동기 복제 시 커밋 유실 가능성, 아키텍처 등 다른 직접 결과의 승격·재연결·중단 설명 |
| 문서를 수정하면 예전 검색 결과는 어떻게 처리돼? | 첫 아키텍처 결과의 중심 청크 53·54·94 주변에서 이전 버전 청크 유지, 단일 트랜잭션의 청크 교체, 검색 기준 버전 설명 |

이는 **여러 후보를 읽으면 실제 근거를 확인할 수 있다는 결과**다. 첫 발췌나 300자 미리보기의
충분 판정을 높였다는 뜻은 아니다. DB 장애 설명은 구성과 노드 역할을 구분해야 하며, 과거 동기
복제 측정의 유실 0을 현재 비동기 복제의 무손실 보장으로 읽어서는 안 된다.

구현 후 비교 실행 전에 다음 표현 변형 4개도 고정했다. 같은 자료의 추가 회귀 사례이며 독립적인
사용자 평가셋은 아니다. 상위 직접 결과의 후보에서 복구·승격·유실 가능성 또는 이전 청크 유지·
버전 교체 설명을 확인했다. 정답 순위나 새 성공률로 집계하지 않았다.

- 데이터베이스 노드가 중단되면 복구와 데이터 유실은 어떻게 되나요?
- Primary가 멈췄을 때 서비스는 다시 연결되나요?
- 본문을 고친 뒤 임베딩이 끝나기 전에는 어떤 버전이 검색되나요?
- 새 벡터가 준비되는 동안 기존 검색 청크는 삭제되나요?

새 모델·색인·마이그레이션·추가 본문 조회는 없다. 별도의 100문서·서로 다른 4,000개 합성 벡터에서
변경 전후 SQL 실행 순서를 번갈아 비교했다. 9회 모두 HNSW를 사용했고 기존 결과 열 12개가 같았으며
비공개 누출은 0이었다. SQL 중앙값은 119ms→127ms였다. 예시·변형 총 10질의의 각 3회 서비스 비교는
질의 임베딩을 제외한 중앙값 212ms→228ms였다. 전송·클라이언트 렌더링 시간은 포함하지 않았다.
소규모 측정으로 대규모 용량이나 전체 응답 지연을 보장하지 않는다.

반환 비용은 증가한다. 예시 6개의 직접 결과를 JSON으로 직렬화한 부분집합은 중앙값 약 33KB→197KB였다.
실제 HTTP 전체 응답 측정이 아니라 추가 본문의 크기 비교다. 본문은 후보별로 겹칠 수 있다.
최대 8개는 반환량 상한이고 전체 후보 수는 여전히 `k * 5`라, 작은 k에서는 같은 답 대목을 놓칠 수
있다. 기존 후보 밖에 있는 답을 찾거나 자동으로 가장 충분한 답을 선택하는 기능은 제공하지 않는다.

청킹을 Markdown 절별로 나누는 사전 비교도 했다. 같은 자료의 청크가 214→254개로 늘었지만 두 질문의
첫 발췌 문제는 남았고 작은 문서 대기 질문의 첫 문서도 바뀌었다. 제품에 반영하지 않았다.

검색·API·MCP 관련 테스트 96개와 변경 파일의 ruff 검사를 통과했다. 새 회귀 테스트는 먼 후보 대목의
보존, 문서별 상한, 전체 후보 한도, 권한·태그·유형 필터, 재임베딩 중 이전 버전, 확장 결과의 빈 배열,
질의만 임베딩하는 동작을 실제 pgvector 컨테이너에서 검증한다. 실제 OpenSQL fixture는 rollback했고
전후 기존 문서·청크·잡 개수가 같았다. 합성 벡터 검증 스키마도 rollback 뒤 제거됨을 확인했다.
내부 비교 스크립트와 측정 원본은 무시되는 `notes/`에 보관하며 저장소에 추가하지 않는다.

## 별도 질문 검증 — 업로드부터 검색 후보까지

2026-10-03, 앞선 6개와 표현 변형 4개에 사용하지 않은 질문 8개를 검색 전에 고정했다.
입력은 [project-passages.json](../scripts/eval/project-passages.json)이며 질문·기대 설명·
지정 근거 문장·원본 위치·자료 해시를 포함한다. 질문은 도구 작성자가 만든 추가 사례로,
독립적으로 수집한 사용자 질문이나 외부 평가셋이 아니다. 입력 SHA-256은
`8c5b644c24fd5ce7bbbdb33e94cd5e200885149c51f38be04a9050841d53c069`이며 실행 후에도 같았다.
결과를 보고 질문·정답 기준이나 제품 코드를 수정하지 않았다.

### 경로와 판정

자료는 같은 `fde4e8b`의 7문서다. 실제 OpenProxy 연결의 고유 스키마에 제품 마이그레이션을
적용하고, 파일 업로드 API로 Markdown 7개를 비공개 문서로 생성했다. DB 트리거가 만든
임베딩 잡을 제품 `process_once`와 실제 BGE-M3로 처리했다. 업로드 7개가 모두 201을 반환했고,
7개 임베딩 잡이 done·문서가 ready가 됐다. 저장 원본 바이트와 추출 텍스트 청킹 결과를
각각 확인했으며 214청크·서로 다른 벡터 214개였다. 임베딩 잡 처리 합계는 약 26.3초였다.

검색은 같은 소유자·태그·md 필터로 k=5와 k=10을 각각 실행했다. 검색 REST API는 ASGI
전송으로, MCP는 도구 함수를 호출해 결과 문서·발췌·미리보기·추가 후보·기준 버전이 일치하는지
확인했다. 모든 기준 버전은 1이었다. 인증 주체와 연결만 주입했으므로 로그인·토큰 인증,
실제 TCP/stdio 전송, 브라우저는 이번 검증 범위가 아니다. 관계 트리거가 만든 edges 잡 7개는
처리하지 않아 관계 없는 직접 검색을 평가했다. 외부 plain 트랜잭션 안에서 제품의 트랜잭션은
savepoint로 실행했으므로, 독립 프로세스 사이의 커밋·폴링·복제 지연을 평가한 것도 아니다.

자동 집계는 공백을 정규화한 뒤 지정 문서에서 **고정한 근거 문장을 모두 포함하는지** 검사했다.
이는 문자열 근거 포함 지표이며 일반적인 의미 정확도 채점이 아니다. 별도로 한 평가자가
기대 설명과 본문을 읽어 충분·부분·부족을 판정했다. 문자열이 다르지만 같은 설명을 하는
경우를 충분으로 인정하되, 고정 근거 기준 자체는 변경하지 않았다.

알림 유실 질문은 후보 확보 자체의 실패다. 같은 자료 해시의 기존 BGE 벡터로 오프라인 정확 순위를
확인했고, 해당 문서의 상위 8청크 순서가 실제 반환 후보와 같았다. 고정 근거를 담는 중심 청크
52·53·54는 전체 77·65·62위, 문서 안에서는 54·47·46위였다. k=10의 기존 전체 후보 한도 50 밖이다.
이 진단은 새로운 HNSW 측정이 아니라 저장된 벡터의 정확 순위 비교다. 추가 후보의 선택 방식만
바꾸거나 문서별 반환 상한 8만 늘려서는 이 사례의 근거를 확보할 수 없다.

### 비용과 정리

이번 8질의의 실제 질의 임베딩·API 처리·JSON 직렬화를 포함한 ASGI 응답 중앙값은
k=5 약 269ms, k=10 약 286ms였다. MCP 도구 호출은 각각 약 243ms·280ms였다.
실제 API 응답 바이트 중앙값은 약 116KB·160KB였다. 질의당 각 조건을 한 번씩 실행한 작은
표본이며, 외부 네트워크·stdio·브라우저 지연이나 동시 부하를 포함하지 않는다.
앞선 질의 임베딩 제외 측정 212→228ms와 직접 비교하지 않는다.

추가 후보 보존은 이 자료의 관계 실패 질문에서 근거 누락을 줄였지만, 응답이 커지고 알림 유실
질문의 후보 누락과 첫 미리보기 선택 문제는 남았다. 다음 개선은 이 두 실패를 구분해 다뤄야 한다.

검증 스키마를 포함한 모든 쓰기를 rollback했고 스키마 제거를 확인했다. 기존 문서·청크·잡·원본
파일 개수는 전후 721·721·1,442·4로 같았다. backend 코드·테스트 해시가 기존 96개 통과 기록과
동일함을 확인해 그 검증을 재사용했으며, 기존 통합 검사·106질의·4천 벡터 측정을 반복하지 않았다.
실행 스크립트·API 본문·수동 판정·진단·원본 로그는 무시되는 `notes/`에만 보관한다.

## 후속 개선 — 후보 확보와 미리보기 선택 분리

앞 절의 고정 질문·근거·자료 해시를 유지하고 두 변경을 분리했다. 후보 확보는 직접 결과의
`passages`에 붙이는 같은 버전의 주변 문맥만 ±1에서 ±2청크로 넓힌다. 알림 근거 중심 청크가
벡터 후보 밖에 있어도, 기존 중심 후보 51·55의 이웃인 청크 53을 본문에 포함할 수 있다.
전역 후보 `k * 5`, 문서별 중심 후보 최대 8개, 순위·점수·기존 전체 발췌는 유지한다.
이는 가까운 근거를 보완하는 변경이며, 중심 후보의 ±2 밖에 있는 답을 찾는 방법은 아니다.

미리보기는 기존 전체 발췌 범위 안에서 이웃 청크를 연결하고, 기존 분할에 행 시작의 300자
창을 추가한다. 한국어 단어 내부의 문자 쌍과 영문·숫자 토큰의 포함 수를 비교한다.
같은 수이면 첫 행의 일치를 우선하고 그다음에는 기존 후보 순서를 유지한다. 짧은 대목을
우대하는 길이 보정은 같은 수의 어휘를 가진 부분 설명을 고르는 문제가 있어 제거했다.
번호 질문은 기존 번호 시작 규칙을 유지한다. 추가 본문 후보는 미리보기 선택에 사용하지 않는다.

### 분리 검증

실제 OpenProxy의 격리 스키마에 같은 7문서·214청크와 해시가 일치하는 기존 실제 BGE 벡터를
사용했다. 질의는 실제 BGE로 임베딩했다. 변경 전, 후보 문맥 확장만 적용, 두 변경 적용을
k=5·10에서 각각 비교했다. 업로드·워커는 변경하지 않아 완료한 파이프라인 검증을 재사용했다.
마지막 미리보기 동점 규칙 변경은 실제 SQL에서 얻은 동일 본문을 재생해 확인하고, 실제 DB의
검색·API·MCP 회귀 테스트로 서비스 연결을 확인했다. 인증·외부 전송·동시 부하는 측정하지 않았다.

| 고정 근거 기준 — k=5·10 각각 동일 | 변경 전 | 후보 확보만 변경 | 미리보기도 변경 |
|---|---:|---:|---:|
| 상위 5문서의 추가 후보에 모든 근거 포함 | 7/8 | 8/8 | 8/8 |
| 첫 미리보기에 모든 고정 문장 포함 | 2/8 | 2/8 | 4/8 |

후보 확보만 바꾸면 미리보기·시작 청크가 그대로였고, 미리보기만 바꾸면 추가 후보가 그대로였다.
기존 6질문도 함께 확인해 문서 순서·점수·버전·전체 발췌가 보존됨을 확인했다.
8질문의 첫 미리보기 수동 충분성은 3→4개였다. 멀티 워커 질문은 이미 다른 문장으로도 충분했고,
원본 파일 교체 질문이 새로 충분해졌다. 멱등키 질문은 422를 보여주지만 같은 요청의 재사용을
함께 설명하지 못한다. 관계 실패·색인 전과 관계 없음·알림 유실의 첫 미리보기는 여전히 부족하다.
기존 DB 장애·문서 수정 질문에서도 답 대목 자동 선택은 해결되지 않았다. 작은 고정 자료의
개선이며 전체 검색 정확도로 일반화하지 않는다.

질문 절 분리, 단순 어휘 후보 선택, 짧은 청크 재색인, 인접 중심 후보 제거도 사전 탐색했다.
알림 근거를 반환 상한 안에 안정적으로 넣지 못하거나 재색인이 필요해 채택하지 않았다.
예전에 기각한 전체 발췌 교체·온라인 재임베딩·별도 재순위 모델을 제품에 재도입하지 않았다.

### 비용과 정리

이번 SQL 변경에 한정해 동일 4천 벡터에서 9회 비교했다. 중앙값은 약 142→147ms,
HNSW 사용은 9/9이며 기존 첫 13열이 동일했다. 후보 본문에는 제한된 주변 조회가 추가된다.
현재 반환 필드의 일부만 직렬화한 8질문 중앙값은 k=5 약 105→154KB,
k=10 약 149→225KB였다. API 전체 응답 측정과 필드가 달라 앞 절의 바이트 수와 직접 비교하지 않는다.
근거 문맥 확장의 주요 비용은 응답 크기 증가다.

실제 DB 검색·API·MCP 테스트 99개와 변경 파일 ruff, diff 검사가 통과했다.
전체 백엔드·프런트 검사, 이전 106질의, 업로드·워커 검증은 변경 범위 밖이라 반복하지 않았다.
모든 fixture 쓰기는 rollback했고 기존 문서·청크·잡·원본 파일은 721·721·1,442·4로 유지됐다.
SQL 비용 fixture도 rollback 후 제거를 확인했다. 실험·측정 원본은 무시되는 `notes/`에만 둔다.

## 후속 개선 — 후보 문맥 중복 축소와 선택 실험

이번 변경은 겹치거나 이어진 `passages` 문맥을 합쳐 반환량을 줄인다. 중심 후보 선택·±2 주변
조회는 유지하고 SQL이 청크 번호·본문을 전달한다. 서비스는 동일한 원래 청크를 한 번만 사용해
그룹을 만들고, 가장 높은 점수의 중심 후보를 그룹의 번호·점수로 표시한다. 여러 중심 후보가
한 항목이 될 수 있으며 그 항목은 기존 단일 문맥보다 길 수 있다. 그룹 수는 최대 8개다.
본문의 반복 문장이나 청크 간 150자 overlap은 출처를 훼손할 수 있어 문자열 추정으로 삭제하지 않는다.

### 보존과 비용

직전 변경의 고정 7문서·214청크와 해시가 일치하는 실제 BGE 벡터를 사용해 실제 OpenProxy
격리 스키마에서 변경 전후를 비교했다. 질의는 실제 BGE로 임베딩하고, 고정 질문 8개와 기존
6개를 k=5·10에서 확인했다. 문서 순위·점수·버전·전체 발췌·미리보기·미리보기 시작 청크는
동일했다. 포함한 원래 청크 집합의 보존도 별도로 확인했다.

| 고정 8질문 — 조건별 중앙값 | 변경 전 | 문맥 병합 후 |
|---|---:|---:|
| k=5 추가 후보의 모든 근거 포함 | 8/8 | 8/8 |
| k=10 추가 후보의 모든 근거 포함 | 8/8 | 8/8 |
| 첫 미리보기의 모든 고정 문장 포함 — k=5·10 각각 | 4/8 | 4/8 |
| k=5 반환 필드 일부의 JSON 바이트 | 약 155KB | 약 118KB |
| k=10 반환 필드 일부의 JSON 바이트 | 약 225KB | 약 154KB |

바이트 수는 title·chunk_index·content·score·based_on_version·preview·passages만 직렬화한
값이며 API 전체 응답 측정이 아니다. k=10에서 약 32% 줄었다. 14질문·두 k 조건의 반환 후보
항목 수는 전체 654→298개였다. 같은 자료의 서비스 호출 중앙값은 약 251→253ms이며,
질의 임베딩을 제외하고 각 조건을 한 번씩 실행한 작은 표본이다. 속도 향상이나 외부 전송 비용의
보장으로 해석하지 않는다. 이번 JSON 표현·병합 변경에 대해 4천 벡터 규모 측정은 반복하지 않았다.

### 미리보기 선택을 바꾸지 않은 이유

기존 300자 선택 규칙을 후보 전체에 적용하면 DB 장애 질문에서 MCP·서버 설정 안내를,
문서 수정 질문에서 과거의 `ready` 필터가 검색을 끊던 설명을 먼저 골랐다. 알림 유실 질문에서도
워커 프로세스 사망을 고른다. 단순 범위 확대로 자동 답 선택이 개선됐다고 볼 수 없다.

기존의 첫 문서만 재순위하던 실험과 달리, 이번에는 상위 5문서의 후보 문맥을 문단 단위로
정리하고 중복을 줄인 뒤 로컬 캐시에 있는 두 모델을 실험했다. 작은 mMiniLM은 14질문에서
DB 장애·문서 수정 오선택이 남았다. BGE 재순위 모델은 문단과 다음 문단을 함께 넣어
DB 장애·문서 수정·대기 질문 3개를 확인했다. DB 질문의 첫 대목은 OpenProxy 노드 사망 시
고아 트랜잭션·keepalive 설명이었다. 문서 수정은 과거 동작 설명과 현재 근거를 함께 찾지만,
첫 300자에는 과거 설명이 먼저 나온다. 관측 추가 시간이 약 9~12초이고 장애 답 선택도
해결하지 못해 제품에 모델·의존성·설정을 추가하지 않았다.

DB 장애 답은 노드 역할·구성·전환 중 중단·복제 유실 가능성을 함께 설명해야 하고,
문서 수정 답은 과거 설계 설명과 현재 동작을 구분해야 한다. 현재 문서 순위를 유지한 채 첫 문서의
어휘 일치만 고르는 것으로 해결됐다고 주장하지 않는다. **후보 중복 축소는 반영했고, 후보에서
실제 답을 첫 미리보기로 자동 선택하는 목표는 미해결로 남긴다.**

fixture는 rollback했고 격리 스키마 제거와 기존 문서·청크·잡·원본 파일 721·721·1,442·4
보존을 확인했다. 업로드·워커·전체 프런트·기존 통합 검증은 변경 범위 밖이라 재실행하지 않았다.
실험 스크립트·모델 점수·측정 원본·기준 소스 복사는 무시되는 `notes/`에만 둔다.

최종 검색·API·MCP 테스트 **101개**, 변경 파일 ruff와 diff 검사가 통과했다. 마지막 병합 규칙은
동일 실제 SQL 후보와 고정 원본으로 문서별 결과 150건을 재생해, 반환 본문과 원래 청크 집합의
동일성을 확인했다. 저장소에는 제품 코드·테스트·공개 문서만 반영하며 내부 원본은 추가하지 않는다.

## 후속 개선 — 웹에서 확보한 본문 근거 읽기

### 확인한 연결 누락과 변경

웹의 검색 결과 타입·컴포넌트는 `content`·`preview`만 사용하고 `passages`는 사용하지 않았다.
앞선 후보 확보 8/8은 API·MCP 소비자가 읽을 수 있는 결과였고, 웹 사용자에게 그 근거가 모두
표시된다는 뜻이 아니었다. 웹 타입과 결과 카드에 「검색된 본문 대목 N개」 펼치기를 연결했다.
카드의 문서 상세 링크가 출처이며 각 대목에 텍스트 버전을 표시한다. 서버가 합친 문맥을
다시 잘라 숨기거나 HTML로 해석하지 않고 응답의 순서대로 표시한다. 첫 발췌·미리보기·
문서 순위는 그대로이며 추가 서버 요청·임베딩은 없다. 없는 필드·빈 후보를 가진 응답에는
추가 펼치기를 만들지 않는다. 관계 결과도 기존 표시를 유지한다.

실제 SQL에서 얻은 고정 8질문의 k=10 결과를 웹 컴포넌트에 재생하고 각 지정 출처의
본문 대목을 펼쳤다. 고정 근거 문장이 모두 표시되는 사례는 **8/8**이었다. 이는 원래 본문을
읽을 수 있는지 확인한 렌더링 검증이며, 사용자 인증·API 전송·브라우저 전체 동작을 다시
검증한 것이 아니다. 표시할 문서 ID는 재생용으로 치환하고 출처 제목·본문·버전·후보 순서는
실제 결과를 유지했다. 첫 미리보기의 고정 문장 포함은 기존 **4/8** 그대로다. 이 변경을
자동 정답 선택의 개선이라고 주장하지 않는다.

### 채택하지 않은 색인 탐색

요청 시 재순위 비용을 피하는 대안으로, 같은 고정 7문서의 문단·목록·표 행을 최대 500자로
나누고 원래 제목 계층을 앞에 붙여 실제 BGE로 임베딩했다. 824개 단위의 오프라인 정확
벡터 순위를 확인했다. DB 장애의 첫 대목은 워커 heartbeat·lease 설명, 문서 수정의 첫 대목은
`import`의 중복 입력 설명이었다. 핵심 질문의 답 선택을 개선하지 못해 워커·색인 구조·
모델·운영 자료에는 적용하지 않았다. 고정 근거·기대 답은 바꾸지 않았다.

웹 검색 결과 컴포넌트 테스트 **13개**, 실제 SQL 본문의 웹 재생 **8개**, 변경 파일 ESLint와

## 후속 작업 — 공개 평가기에 본문 근거 지표 추가

`scripts/eval_search.py`는 문서 Recall·MRR만 집계하므로, 관련 문서가 첫 결과여도 답 대목이
없거나 미리보기가 틀린 상황을 자동으로 구분하지 못했다. 기존 문서 지표를 유지하면서 선택
`evidence` 입력을 지원한다. 고정 출처 제목에서 **모든 근거 문장이 포함되는지**를 다음 세
위치별로 따로 집계한다.

- 직접 첫 결과의 전체 발췌: `first_excerpt`
- 직접 첫 결과의 미리보기: `first_preview`
- 직접 상위 5문서의 본문 후보: `top5_passages`

공백만 정규화하고 문자열 포함을 검사한다. 동의어·같은 의미의 설명은 자동 인정하지 않고,
서로 다른 본문을 연결해 없는 문장을 만들지 않는다. 관계 결과·과거 버전 결과는 본문 지표에서
제외한다. 문서 Recall·MRR의 기존 관계 포함 규칙은 유지한다. 근거 입력이 없는 질의는
본문 집계의 분모에서 제외하고, 빈 근거 목록·문장·출처는 오류로 거부한다. 누락한 근거의
출처·문장도 질의별 JSON에 기록한다. 이것은 의미 정확도나 정답 충분성 자동 채점이 아니다.

`--user`·`--tag`는 정답 제목 해석과 실제 검색에 같은 열람·태그 범위를 적용한다. 같은 제목의
비공개 문서나 다른 코퍼스가 정답 개수에 섞이는 것을 막는다. OpenProxy를 위한
`prepare_threshold=None`을 사용한다. 주체를 생략하면 public 범위이며 CLI가 로그인 인증을
하는 것은 아니다. 도구는 읽기만 하고 fixture 업로드·임베딩·정리를 수행하지 않는다.

고정 자료가 별도 검증 DB에 동일 제목으로 색인돼 있을 때 다음처럼 실행한다. 운영 자료 대신
검증 소유자·태그를 사용하고 `DATABASE_URL`은 검증 환경에서 설정한다. 기존 격리 fixture는
rollback했으므로 현재 운영 DB에서 이 명령만 실행해 재현할 수 있는 것은 아니다.

```bash
EMBEDDING_PROVIDER=local backend/.venv/bin/python scripts/eval_search.py \
  scripts/eval/project-passages.json --user '<평가 소유자>' --tag '<검증 태그>' \
  --out notes/evidence-evaluation/results.json
```

검색 k는 기존과 같은 10이다. JSON에는 실행 k·주체·태그와 **읽은 평가 입력의 SHA-256**을
남긴다. 원본 측정 JSON은 저장소에 반영하지 않는다. `evidence`가 없는 기존 평가셋도 그대로
지원한다. 실제 BGE만 사용하는 기존 CLI 제한도 유지한다.

### 검증

기존 실제 DB·BGE 결과를 새 공개 집계기로 재생한 고정 8질문의 결과는 다음과 같다.
검색 구현은 바꾸지 않았으며 새로운 DB 검색·모델 추론·성능 측정이 아니다.

제외·기존 평가셋 호환을 테스트했다. 실제 로컬 pgvector DB에서도 비공개 소유자·태그와
동명 문서가 있는 상태에서 정답 해석과 검색의 범위가 같음을 확인했다. 이 범위 테스트의
FakeProvider는 SQL·집계 계약만 검증하며 의미 검색의 품질 측정에는 쓰지 않는다.

앞선 구조 문단 벡터 824개에서 조건·결과별 벡터 점수의 최솟값으로 복합 질문을 고르는
탐색도 별도로 했다. DB 장애는 `serve` 프로세스 종료, 문서 수정은 `import` 중복 처리,
대기 질문은 측정 절차를 먼저 골라 채택하지 않았다. 그 결과를 현재 제품 색인의 모든
질의 분해 방식이 실패했다는 일반 결론으로 해석하지 않는다. 자동 미리보기 선택은 여전히
미해결이며 이번 작업은 앞으로 그 실패를 반복 가능한 기준으로 구분하도록 하는 평가기 개선이다.
실험 벡터·점수·재생 결과와 로그는 무시되는 `notes/`에 보관한다.

평가기 관련 테스트 18개, 변경 Python 파일의 Ruff, `git diff --check`가 통과했다.
검색 서비스와 화면 코드는 이번 평가기 작업에서 변경하지 않아 앞선 검증을 반복하지 않았다.

## 후속 작업 — 첫 미리보기 실패의 위치 구분

고정 근거를 사용해 첫 직접 결과의 **최소 연속 창 길이**를 진단한다. 공백은 포함 여부에서는
정규화하지만 길이는 실제 원문 문자 수로 센다. 같은 출처의 모든 근거가 한 발췌나 한 본문
후보에 있어야 하며, 후보·문서·버전을 연결하지 않는다. 반복되거나 겹친 근거 위치도 비교한다.
이 길이는 근거를 넣을 수 있는 이론적 하한이며, 읽기 좋은 문단 창이나 충분한 답변을 보장하지
않는다. 정답 근거를 제품의 미리보기 선택에 사용하지 않는다.

공개 평가기의 질의별 `preview_diagnosis`는 다음을 기록한다. `first_excerpt_minimum_chars`와
`first_document_passage_minimum_chars`가 `null`이면 그 범위의 한 본문에 모든 근거가 없다.

| reason | 진단 |
|---|---|
| `complete` | 현재 첫 미리보기에 고정 근거가 모두 있음 |
| `selection` | 첫 발췌에 300자 이하의 근거 창이 있지만 선택하지 못함 |
| `scope` | 첫 발췌에서는 불가능하지만 첫 문서의 다른 본문 후보에서는 300자 이하로 가능 |
| `length` | 한 본문에 근거는 있지만 최소 창도 300자를 넘음 |
| `missing` | 첫 문서의 발췌·개별 후보 어느 곳에도 모든 근거가 함께 없음 |

`missing`은 상위 5문서 전체의 후보 확보 실패와 같지 않다. 다른 문서의 근거나 여러 후보에
흩어진 근거는 기존 `top5_passages` 포함 지표로 따로 확인한다. 근거가 없는 기존 평가셋에는
진단을 붙이지 않는다. 관계·revision 결과는 제외하며 검색 주체·태그 범위는 기존과 같다.

기존 실제 DB·BGE 검색 결과를 재생한 고정 8질문에서는 성공 4건과 다음 실패 4건을 구분했다.
새 검색·모델 추론·성능 측정은 하지 않았다.

| 실패 질문 | 진단 | 첫 발췌 최소 창 | 첫 문서 본문 후보 최소 창 |
|---|---|---:|---:|
| 업로드 키 재시도와 다른 내용 | selection | 150자 | 150자 |
| 색인 전과 관계 없음 구분 | selection | 291자 | 291자 |
| 관계 계산 실패와 복구 | scope | 없음 | 127자 |
| DB 알림 유실과 폴링 | scope | 없음 | 93자 |

현재 발췌에서 행 끝 기준의 뒤쪽 300자 창을 추가하는 선택 실험은 근거 포함 4/8로 개선되지
않아 제품에 반영하지 않았다. 후보 전체에 기존 어휘 규칙을 적용하는 이전 기각 접근도
오선택이 지속되므로 적용하지 않는다. 검색 서비스·화면·문서 순위는 이번 작업에서 변경하지
않았다. 다음 선택 개선은 발췌 안의 선택 실패와 후보 범위 밖의 실패를 별도로 다뤄야 한다.

평가기 관련 테스트 22개와 Ruff·`git diff --check`가 통과했다. 실제 pgvector DB의 기존
권한·태그 테스트에서도 진단 결과 전달을 확인했다. 내부 실험·재생 원본은 `notes/`에만 보관한다.

## 후속 개선 — 표의 비교 조건 보존

멱등성 질문의 기존 미리보기는 `같은 키 + 다른 요청` 행부터 시작해 `422`는 보여 주지만,
바로 앞의 `같은 키 + 같은 요청` 행에 있는 기존 문서 반환 조건을 빠뜨렸다. 선택한 행을
바꾸거나 정답 문자열로 분기하지 않고 **표 행의 앞 문맥만 보완**한다.

선택한 대목이 Markdown 데이터 행 시작에 있고 바로 앞 행도 데이터 행이면 두 행을 합친
원문 길이를 확인한다. 300자 이하면 앞 행부터 선택 행 끝까지만 표시한다. 구분선·일반 문장·
행 중간 시작·긴 행에는 적용하지 않는다. 뒤 행이나 빈 줄을 넘어선 다른 문맥은 붙이지 않는다.
전체 발췌에서 가져온 연속 원문이며 시작 청크를 다시 계산한다. 번호 질문은 기존 규칙을 쓴다.
의미를 이해해 두 행의 관련성을 판정하는 방식은 아니므로, 다른 질문에서 뒤 행의 설명을
잘라낼 가능성까지 해결했다고 보지 않는다. 전체 발췌와 본문 후보 펼치기는 계속 사용할 수 있다.

### 검증 결과

고정 평가 입력·근거·자료 해시는 유지했다. 기존 실제 DB·BGE 검색 결과 150개 문서 결과를
재생했으며 미리보기 12개가 바뀌었다(k=5·10 두 조건 합계). 첫 미리보기가 바뀐 질문은
멱등성 질문 하나이고, 나머지 고정 7질문과 기존 승인 예시 6질문의 첫 미리보기는 동일하다.
검색을 새로 실행한 의미 품질 측정이나 SQL 성능 측정은 아니다.

| 지표 — k=5·10 각각 동일 | 변경 전 | 변경 후 |
|---|---:|---:|
| 상위 5문서 본문 후보의 고정 근거 포함 | 8/8 | 8/8 |
| 첫 전체 발췌의 고정 근거 포함 | 6/8 | 6/8 |
| 첫 미리보기의 고정 근거 포함 | 4/8 | 5/8 |

기존 성공 4건은 유지됐다. 새 성공은 같은 키·같은 요청의 기존 문서 반환과 같은 키·다른 요청의
거부를 함께 보여 주는 267자 표 대목이다. 기존 DB 장애·문서 수정 질문의 첫 미리보기는
동일하며 여전히 부족하다. 이 작은 작성 예시 집합의 개선을 전체 검색 품질로 일반화하지 않는다.

표 문맥·300자 제한·구분선 및 일반 문장 제외·부분 행 제외·들여쓴 첫 행의 경계 처리를
순수 함수 테스트로 확인했다. 실제 pgvector DB에서는 보완된 미리보기의 원문 포함,
기준 버전·청크 번호·벡터 점수 유지와 검색 서비스 연결을 확인했다. 검색·REST·MCP 회귀
검사를 다시 실행했다. SQL·색인·업로드·워커·프론트 코드는 이번 변경에 포함하지 않아
이전에 완료한 전체 파이프라인·4천 벡터·정적 빌드 검증은 반복하지 않았다.

### 채택하지 않은 선택 실험

한 문장·행 안에 질의 어휘가 집중된 정도를 먼저 비교하는 실험은 색인 상태 질문을 개선했지만
기존 워커 경쟁 질문의 고정 근거를 놓쳐 4/8에 머물렀다. 순위 규칙으로 채택하지 않았다.

별도로 [Qwen3-Reranker-0.6B 공식 모델 카드](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)의
지시형 재순위 방식을 로컬 Transformers로 실행했다. 질문의 조건과 결과를 직접 설명하는
현재 대목을 우선하도록 지시했고, 기존 실제 SQL/BGE 결과의 첫 문서 본문 후보에서 300자
창을 비교했다. 정답 근거는 모델 입력에 넣지 않았다. MPS·float16·batch 8에서 DB 장애는
컨테이너의 DB 미포함 안내를 골랐고, 문서 수정은 과거의 잘못된 ready 필터 설명부터 골랐다.
추가 시간은 각각 약 56.1초·49.6초였다(모델 로드는 제외, 이 창 수·로컬 조건의 관측치).
멱등성·직접 수정 재추출 질문도 실행했지만 핵심 두 질문의 오선택과 지연이 확인돼 나머지
질문 실행을 중단했다. 8질문 전체 성적이나 일반적인 모델 성능으로 해석하지 않는다.
모델·의존성을 제품에 추가하지 않았고 실험 원본·로그·부분 결과는 무시되는 `notes/`에만 둔다.

최종 검색·REST·MCP 회귀 테스트 **105개(21.50초)**, 변경 Python 파일의 Ruff와
`git diff --check`가 통과했다. 평가기·평가기 테스트·고정 입력의 해시는 이전 22개 통과
기록과 같아 해당 검증을 재사용했다.

## 형식별 실문서 기준선 (#167)

2026-10-04, 업로드 형식마다 실제 문서가 추출부터 검색 후보까지 근거를 보존하는지 재는 평가셋을 고정했다.
앞 절들의 자료는 Markdown 7개뿐이었다. 이 평가셋은 #96(ask)과 #168(키워드·재순위)이 전후 비교에 같이 쓴다.

### 자료와 질문

자료는 정책브리핑 보도자료 첨부 10개다 — HWP 1, HWPX 1, XLSX 2(그중 1개는 9월판→10월판 **원본 교체**),
텍스트 PDF 1(17쪽), 혼합 PDF 1(1·3쪽 텍스트, 2쪽 스캔), 스캔 JPG 1, PPTX 2(인포그래픽·발표자 노트 1, 그림뿐인
슬라이드 1), DOCX 1(영문). 이 중 HWP와 혼합 PDF는 기존 테스트 픽스처이고, 스캔 JPG와 그림뿐인 슬라이드는
같은 관세청 보도자료 PDF의 1·2쪽을 스캔처럼 가공한 파생본이다. 그 밖에 다른 계정의 비공개 HWPX 1개를 같은 태그로 넣었다. 출처·가공은
[SOURCE.md](../scripts/eval/formats/SOURCE.md)에 있다. 첨부의 공공누리는 **텍스트에 한해서**라
(내장 로고·삽화는 별도 허락) 파일을 저장소에 넣지 않고 적재기가 fileId로 받아 SHA-256을 대조한다.
한국어 DOCX는 보도자료 약 8천 건에서 찾지 못해 영문 문서를 한국어로 묻는 교차 언어 사례로 두었다.

질문 24개와 기대 답·정답 문서·근거 문장은 [formats.json](../scripts/eval/formats.json)에 검색 전에 고정했다
(SHA-256 `793e2cfcd39fa5e7b5ee67ba51db75a9f5fcc697fd330ebb99e788bcc8e9cb7f`). 표 3·시트명 1·슬라이드 1·
노트 1·제품명 1·OCR 4·조항 2·번호 4·여러 대목 종합 1·교차 언어 1·현재 버전 1과(영문 DOCX 질문은 조항 1개를 포함해 2개), 정답 문서가 없는 질문 4개(과거 판본
1·근거 없음 2·권한 1)다. 도구 작성자가 만든 질문이며 독립적인 사용자 질문이 아니다. OCR 문서의 근거는
OCR 결과가 아니라 원본 PDF 텍스트 레이어에서 뽑았다 — 오인식은 그대로 추출 실패로 집계된다. 같은 답이 다른
문서에 다른 표현으로 있으면 대안 근거(`evidence_alternatives`)로 둔다 — 세관장 확인 법령·품목 수는 스캔 본문과
인포그래픽 양쪽에 있다.

**2026-10-10 개정(#177)**: 그림뿐인 슬라이드가 OCR 대상이 되어, 「근거 없음」 질문 `none-image-only`를 정답이 있는
OCR 질문 `slide-ocr-name`(정답 문서 = 그림 슬라이드, 근거 = 원본 PDF 2쪽 텍스트 레이어의 「이진희 관세청 통관국장은」)으로
바꿨다. 이제 OCR 5·근거 없음 1이고 정답 있는 질문은 21개다(SHA-256 `e0c6693ddc7d8189fcdf533bf2e187f3ba786b8b59b1ec188a341c0bf44348ce`). 아래 결과는 개정 전
평가셋으로 잰 기준선이며, 다음 측정부터 이 질문이 정답 있는 질문으로 집계된다.

### 경로와 판정

실제 OpenSQL HA 클러스터(OpenProxy VIP 단일 엔드포인트)의 앱 DB(기존 문서 64건)에 평가 전용 계정·태그(`eval167`)의
비공개 문서로 적재하고, 측정 후 지웠다(문서 64건·잡 상태 전후 동일). 적재는 업로드와 같은 진입점
(`create_document`)과 원본 교체(`replace_original_file`)를 쓰고, OCR·임베딩·관계 잡은 제품 워커가 실제
BGE-M3·tesseract 5.5.1(macOS 앱 호스트)로 처리했다. 적재 뒤 35초 안에 모든 잡이 실패 없이 끝났다.
적재기는 원본 교체가 다음 텍스트 버전(v2)을 만들었는지와 보관된 원본(`get_original_file`)의 SHA-256이 넣은
파일과 같은지를 단언한다 — 10개 문서 모두 같았다. 검색은 제품 `search_documents`를 평가 계정·태그로 k=10
실행했다. 생성형 답변·지연은 재지 않았다.

실패 원인은 근거 문장(공백 정규화 문자열 포함)으로 가린다 — 출처 문서의 저장 본문에 없으면 **추출**,
상위 5문서 안의 출처 문서 발췌·후보에 없으면 **후보 부족**, 후보에는 있으나 **출처 문서의 첫 발췌**에 없으면
**선택**이다. 대목 선택을 출처 문서마다 보는 것은 여러 문서에 걸친 근거가 첫 결과 하나로는 정의상 충분할 수
없기 때문이고, 어느 문서가 첫 자리인지는 순위 지표가 따로 잰다. 대안 근거가 있으면 원인과 첫 발췌 충분성이
가장 나은 쪽으로 채점한다. 의미 채점이 아니다.

두 가지(출처 문서별 선택, 대안 근거)를 고치고 제품명 질문을 더해 다시 적재·측정한 위 값이 기준선이다. 처음부터
있던 23질문의 순위·상위 3문서는 두 측정에서 모두 같았다. 근거 포함이 바뀐 것은 대안 근거를 둔 법령·품목 수
질문 1건, 원인이 바뀐 것은 그 질문과 인포그래픽 노트 질문 2건(둘 다 선택 → 충분)뿐이다. 정답 없는 질문의
최고점도 소수 셋째 자리까지 같았다.

| 정답 없는 질문 | 결과 |
|---|---|
| 교체 전 9월판에만 있는 값 | 현재 판 결과에는 없고 「이전 버전」(via=revision, v1) 자리에 표시돼 나왔다 |
| 그림뿐인 슬라이드 속 내용 | 업로드가 「문서에서 텍스트를 추출하지 못했습니다」로 거부돼 문서가 없다. 최고점 0.571 (#177 뒤로는 OCR 질문으로 바뀌었다 — 위 개정) |
| 어느 문서에도 없는 내용 | 최고점 0.538 |
| 다른 계정의 비공개 문서 내용 | 결과 어디에도 없음(누출 0). 최고점 0.335 |

정답 없는 질문도 항상 결과가 나온다(최고점 0.34~0.72). 과거 판본 질문의 0.715는 현재 판 문서 자체가 맞는
문서라서 높다. 결과가 있다는 것만으로 근거가 있다고 볼 수 없으며, "근거 없음" 판정은 #96의 답변 경로가 다뤄야 한다.
정답 있는 질문의 점수 분포는 이번에 기록하지 않아 임계값 비교는 하지 않는다.

**보존이 확인된 것**: HWP·HWPX 본문과 표 셀, XLSX 시트명·행, PPTX 슬라이드·발표자 노트·제품명, DOCX 조항,
혼합 PDF의 OCR 쪽(2쪽 근거 2개 모두 첫 발췌)과 그 뒤 텍스트 쪽(3쪽 근거도 검색됨 — 쪽 순서 자체는 평가기가
아니라 #175의 추출 테스트가 고정한다), 원본 교체 후 현재 판만의
값(v2). 텍스트 PDF의 본문 문장 근거 2개도 첫 발췌에 있었다.

**추출 실패 2건**:
- 텍스트 PDF의 **표 셀 경계가 사라진다**. 원본 10쪽 「수도권 16,815 5,209」(poppler `pdftotext -layout`)가
  저장 본문에서 「수도권16,8155,209」로 붙어 숫자를 가를 수 없다. 표 밖 문장에 같은 값이 없으면 답할 수 없다.
  → #176에서 고쳤다(아래 「#176 표 셀 간격 이후」).
- 스캔 JPG의 고시 정식 명칭이 OCR에서 깨졌다. 같은 근거가 첫 측정(래스터를 poppler로 만든 판)에서는 읽혔고 대신
  「5,851개」가 「5.851개」로 깨졌다 — 가공 판에 따라 어느 문장이 깨지는지가 달라지는 OCR 오차 수준의 결과다.

**선택 2건**: 수능 졸업생 증감은 정답 문서가 첫 결과지만 첫 발췌가 다른 대목이었다. 「여러 대목 종합」은
첫 결과(지원자 현황 표)의 발췌에는 서울 행이 있으나 둘째 문서(접수 결과)의 발췌가 전체 지원자 수 대목이 아니었다
— 그 대목은 후보에만 있다. 인포그래픽 노트 질문은 정답 문서가 둘째 자리라 순위 지표에서 빠지지만, 그 문서의
첫 발췌에는 노트 근거가 있어 원인은 충분이다(첫 결과 발췌 지표와 원인 지표가 갈리는 사례).

`via_only=1`은 관계 확장만으로 잡힌 정답이 아니다. 현재 판 질문의 정답 문서가 직접 결과와 「이전 버전」
자리에 함께 나와 기존 지표(정답 ∩ 경유 문서)에 걸렸다.

### #176 표 셀 간격 이후

2026-10-10, PDF 텍스트 레이어가 pypdfium2의 글자·위치로 만들어지도록 바뀌었다 — 같은 줄의 셀은 공백으로 띄우고,
공백 없이 끝난 줄은 판면 오른쪽 끝까지 찼을 때만(그런 줄이 둘 이상인 쪽에서) 다음 줄과 잇는다(ADR-059 결정 5). 같은 평가셋을 **로컬 pgvector**(앱과
같은 마이그레이션, 실제 BGE-M3·tesseract 5.5.1)에 세 판으로 적재·측정했다. 추출은 DB와 무관해 HA를 다시 쓰지 않았다.
main은 pypdf 판에 따라 결과가 갈려 두 판을 모두 쟀다 — pypdf 6.17부터 셀은 띄우지만 줄 끝 낱말 중간에서 줄을 바꾼다.
main + pypdf 6.14는 위 기준선(HA)의 지표를 그대로 재현했다. 그림뿐인 슬라이드는 #177 뒤라 거부되지 않고 OCR로 적재됐다.

| 지표 (정답 문서가 있는 20질문) | main + pypdf 6.14 | main + pypdf 6.20 | #176 (pypdf 6.20) |
|---|---:|---:|---:|
| 정답 문서 첫 결과 · MRR | 18/20 · 0.950 | 18/20 · 0.950 | 18/20 · 0.950 |
| 상위 5문서 본문 후보에 모든 근거 | 18/20 | 18/20 | 19/20 |
| 출처 문서 첫 발췌에 모든 근거 (원인 = 충분) | 16/20 | 16/20 | 17/20 |
| 첫 결과 전체 발췌에 모든 근거 | 15/20 | 15/20 | 16/20 |
| 첫 미리보기에 모든 근거 | 10/20 | 10/20 | 11/20 |
| 원인 — 선택 / 후보 부족 / 추출 | 2 / 0 / 2 | 2 / 0 / 2 | 2 / 0 / 1 |

main의 두 판은 합계가 같지만 실패한 질문이 다르다. 6.14에서는 표 셀 질문(「수도권 16,815 5,209」)이, 6.20에서는
1인당 상업용 면적 질문이 추출 실패다 — 근거 「제주(30.82㎡)」가 줄 끝에서 「제주⏎(30.82㎡)」로 끊긴다. #176은
두 질문 모두 충분이다. 6.14 대비 바뀐 것은 표 셀 질문(추출 실패 → 충분, 첫 미리보기까지)과 정답과 무관한 2·3위
문서의 자리 바뀜 2건(정답 있는 질문 1·정답 없는 질문 1)뿐이고, 정답 없는 질문의 최고점은 네 질문 모두 같았다.

본문 회귀는 평가셋 밖의 정상 PDF 114개 4,661쪽(#93·#191 코퍼스와 픽스처)으로 따로 쟀다. 공백 아닌 글자를 맞춰 놓고
pypdf 6.14의 구분(공백·줄바꿈)과 비교하면 사라진 구분은 0이고 셀 사이 공백만 더해졌다(짝지은 pypdf가 6.14든 6.20이든
같다). 긴 줄(30자 이상) 끝이 한글⏎한글로 끊긴 자리는 6.14 622 · 6.20 18,353 · #176 1,859이며, #176에 남은 자리는 대부분
「총칙⏎제1조」 같은 블록 경계다. 남은 한계는 폭이 거의 같은 가운데 줄이 둘 이상인 쪽(표지)에서 그 줄들과 바로 다음 줄이 붙는 것, 표 칸 안에서 줄이 바뀐 낱말(칸이 쪽 여백까지 차지 않는다)과 표 행
경계다. 추출 시간은 4,661쪽에 pdfium 11초, pypdf(공백 문자·깨짐 판정) 약 100초로 pypdf가 대부분이다 — 전과 같다.
