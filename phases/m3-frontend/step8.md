# Step 8: docs-sync

## 읽어야 할 파일

먼저 아래 파일들을 읽고, **직전 step들이 실제로 무엇을 만들었는지** 코드로 확인한 뒤 문서를 고쳐라:

- `frontend/src/lib/` 전체, `frontend/src/components/` 전체, `frontend/src/app/` 전체 — step 0~7 산출물
- `/docs/UI_GUIDE.md` — 화면 구성 절, 추출 텍스트 편집 절, 레이아웃 절
- `/docs/ARCHITECTURE.md` — "API 설계" 표, "프론트엔드 패턴" 절, "상태 관리" 절
- `/docs/ADR.md` — ADR-015(보장 범위), ADR-017(인라인 편집), ADR-020(Single 구성)
- `/README.md` — 주요 기능 표, 빠른 시작, 구현 현황 관련 서술
- `backend/app/api/documents.py` — `PUT`이 받는 것이 무엇인지(JSON `{content, version}`뿐이다)

이 step은 **코드를 고치지 않는다.** 문서가 구현과 어긋난 지점만 정정한다.

## 배경 — 왜 이 step이 있는가

M2에서 문서 step을 두지 않은 결과, `README`·`ARCHITECTURE`가 구현보다 뒤처진 채 PR이 올라갔고 리뷰 지적 사항이 됐다. M3는 화면을 만들면서 문서에 적힌 것과 실제 구현이 갈라진 지점이 세 곳 생겼다. phase 안에서 닫는다.

## 고쳐야 할 세 가지

### 1. "재업로드(새 버전)"는 존재하지 않는다

백엔드 `PUT /api/documents/{id}`는 **JSON `{content, version}`만** 받는다. multipart 파일 재업로드 경로가 없고, M3에서도 만들지 않았다. 새 파일을 올리려면 업로드 후 이전 문서를 삭제하는 것이 현재 동선이다.

- `docs/UI_GUIDE.md` 화면 구성 2번의 "재업로드(새 버전)"를 삭제한다
- 같은 문서 "추출 텍스트 편집" 절의 "다른 액션(삭제·재업로드)은 비활성화한다"에서 재업로드를 뺀다
- `docs/ARCHITECTURE.md` "API 설계" 표의 `PUT` 행에서 "새 파일 또는"을 정리하고, 그 아래 구현 현황 주석이 중복 서술이 되면 함께 정돈한다
- `docs/ARCHITECTURE.md` "프론트엔드 패턴" 절의 화면 설명에서도 재업로드를 뺀다

### 2. "청크 목록"은 만들 수 없다

청크 내용을 조회하는 엔드포인트가 없다. 상세 화면은 `chunk_count`와 `chunk_version`으로 **"청크 {n}개 · v{m} 기준"** 요약을 보여주며, 두 버전이 다르면 재임베딩 중임을 문구로 알린다.

- `docs/UI_GUIDE.md`와 `docs/ARCHITECTURE.md`의 "청크 목록"을 실제 구현(청크 수·기준 버전 요약)에 맞게 고친다
- **청크 조회 API를 만들겠다는 계획을 문서에 추가하지 마라.** 결정된 바 없다

### 3. 프론트엔드 구성이 문서와 다르다

`docs/ARCHITECTURE.md` "프론트엔드 패턴"·"상태 관리" 절을 실제 구현으로 갱신한다. 코드를 읽고 사실만 적어라:

- 네 화면이 모두 Client Component다. 데모 사용자 식별이 `localStorage`에 있고 화면이 폴링하기 때문이다 — 기존의 "Server Components 기본, 인터랙션 구간만 Client Component"는 실제와 다르다
- 폴링 정책: 목록과 `/admin/status`는 상시 2초, 문서 상세는 `pending`·`processing`일 때만 2초이고 `ready`·`error`면 멈춘다
- 폴링이 실패해도 마지막 성공 데이터를 지우지 않는다(사용자 화면이 장애 중에도 비지 않게 하기 위함 — UI_GUIDE 디자인 원칙 3)
- 데모 사용자 전환은 헤더의 셀렉터로 하며, 변경 시 `window.location.reload()`로 화면 전체를 다시 그린다. 전역 상태 라이브러리를 쓰지 않는다는 기존 방침은 유지된다
- `docs/UI_GUIDE.md` 레이아웃 절에 헤더 구성(제품명 + 문서·검색 링크 + 사용자 전환)을 한 줄 추가한다. **`/admin/status`는 내비게이션에 없다**는 사실을 함께 남긴다

### 4. README 갱신

- 프론트엔드 4화면이 구현됐다는 사실을 기존 서술 방식에 맞춰 반영한다. 구현 현황을 적는 표·문장이 이미 있으면 그 형식을 따르고, 없으면 새 절을 만들지 마라
- "빠른 시작"의 프론트엔드 실행 절차가 실제로 맞는지 확인한다(`npm install && npm run dev`, `http://localhost:3000`)
- 주요 기능 표의 "관련 문서·태그 추천"은 **M4에서 구현된다.** 완료된 것처럼 쓰지 마라

## 작업 원칙

- **코드를 고치지 마라.** 문서와 구현이 어긋나면 문서를 고친다. 이 step에서 프론트·백엔드 소스를 수정해야 할 것 같으면 그것은 이 step의 범위가 아니다 — `blocked`로 기록하고 중단하라
- 문서에 적힌 것 중 **구현되지 않은 것을 구현됐다고 쓰지 마라.** 특히 관련 문서·태그 추천(M4), MCP 서버(M4), 복구 데모 스크립트(M5), `reconnect_events`(M5)
- 기존 문서의 서술 톤·표 형식·용어를 유지하라. 문체를 개선하지 마라(변경 범위를 요청받은 것에 한정한다)
- 관련 없는 오탈자·형식을 "정리"하지 마라

## Acceptance Criteria

문서만 바뀌므로 코드 검증은 회귀 확인이다. 전부 통과해야 한다:

```bash
bash scripts/check.sh
```

아래 세 커맨드는 **통과/실패를 판정하는 것이 아니라 출력을 읽고 판단하는 것이다.** 매치가 남았다면 그 문장이 정당한지(금지 규칙을 설명하거나 과거 결정을 인용하는 문장인지) 하나씩 확인하라. 매치가 없을 때 `grep`이 종료 코드 1을 내는 것은 실패가 아니므로 `|| true`를 붙여 둔다:

```bash
grep -rn "재업로드" docs/ README.md || true
grep -rn "청크 목록" docs/ README.md || true
grep -rn "항상 최신\|실시간 동기화" docs/ README.md || true
```

## 검증 절차

1. 위 커맨드를 실행하고, 남은 매치가 정당한 것인지(금지 규칙을 설명하는 문장인지) 하나씩 확인한다.
2. 체크리스트를 확인한다:
   - 문서가 실제 코드와 일치하는가? (추측으로 쓰지 말고 `frontend/src/`를 읽고 확인했는가)
   - M4·M5 범위를 완료로 표시하지 않았는가?
   - 새 ADR을 만들거나 기존 결정을 바꾸지 않았는가?
   - 코드 파일을 수정하지 않았는가?
3. 결과에 따라 `phases/m3-frontend/index.json`의 step 8을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- **새 ADR을 추가하지 마라.** 이유: 이 step은 기존 결정을 문서에 반영하는 것이지 새 결정을 하는 자리가 아니다. ADR이 필요해 보이면 `summary`에 그 사실만 적어라
- **기존 ADR의 결정을 바꾸지 마라.** 문서 간 불일치를 발견하면 `summary`에 남기고 임의로 판단하지 마라
- **코드를 수정하지 마라.** 문서 step이다
- **실측하지 않은 성능 수치·측정값을 쓰지 마라.** 이유: 이 저장소의 수치는 전부 실측 근거가 있고(`OPENSQL_RESEARCH.md` §12), 추정치를 섞으면 그 신뢰가 무너진다
- **"무중단"·"failover 시연"을 쓰지 마라.** Single 구성이라 승격할 replica가 없다(ADR-020)
- 기존 테스트를 깨뜨리지 마라
