# Step 4: auth-frontend

## 배경 — 화면이 붙어야 로그인이 실재한다

step 2·3이 API를 바꿨지만 프론트는 아직 `userHeaders()`로 `X-User-Id`를 보낸다
(`frontend/src/lib/api.ts:28`). **그 코드가 남아 있는 한 화면은 로그인을 모른다.**

쿠키는 **브라우저가 자동으로 실어 보낸다** — 헤더를 손으로 붙이던 코드가 통째로 사라지는
자리다. `fetch`에 `credentials`만 맞추면 된다.

## 읽어야 할 파일

- `frontend/src/lib/api.ts` — **`userHeaders()`가 이 step에서 사라진다.**
  `fetch` 옵션이 어떻게 조립되는지 전부 읽어라
- `docs/UI_GUIDE.md` — 화면 규칙. 새 화면 둘이 이것을 따른다
- `frontend/src/app/` — 기존 화면 구조와 스타일
- `backend/app/api/` 인증 라우터 — 응답 형태

## 작업

### 1) 테스트를 먼저 쓴다

- 로그인 폼이 렌더되는가
- 실패 시 **한 종류의 메시지**가 나오는가 (사유를 가르지 않는다 — step 1과 같은 이유)
- 로그인 상태와 익명 상태에서 헤더/내비게이션이 다른가
- 로그아웃 후 익명 화면으로 돌아가는가
- 관리자가 아닌 사용자에게 **사용자 관리 진입점이 보이지 않는가**

### 2) `userHeaders()`를 제거한다

- `X-User-Id`를 붙이던 코드를 지운다
- `fetch`가 쿠키를 싣도록 옵션을 맞춘다 (same-origin이라 기본값으로 충분한지 확인하고,
  아니면 명시한다)
- **이 변경으로 고아가 된 것만 지운다** — 사용자 선택 UI가 있었다면 함께 사라진다

### 3) 로그인 화면

- 사용자명·비밀번호 · 제출 · 실패 메시지. **그 이상을 만들지 마라**
- 가입 링크·비밀번호 찾기·소셜 로그인을 만들지 마라 — **없는 기능이다**
- 로그인 후 원래 가려던 곳으로 돌아가면 좋지만, **필수는 아니다**

### 4) 사용자 관리 화면 (관리자 전용)

- 목록 · 생성 · 삭제. **관리자에게만 진입점이 보인다**
- 진입점을 숨기는 것만으로 끝내지 마라 — API가 이미 막고 있지만, **화면에서도 막는다**
- 삭제 시 **그 사용자의 문서가 어떻게 되는지 사용자에게 알린다**(step 3이 정한 대로)

### 5) 익명 상태의 화면

**익명은 아무것도 못 본다**가 아니라 **`public`만 본다**. 화면이 이것을 정확히 반영해야 한다.

- 익명에게 업로드·편집 버튼이 보이면 안 된다 (눌러도 실패한다)
- **"로그인하면 더 보입니다" 같은 안내로 개수를 흘리지 마라** — ADR-027 결정 2와 같은 원칙이다

## Acceptance Criteria

```bash
cd frontend

# 1) 타입·린트·테스트
npm run lint && npm run build && npm test

# 2) userHeaders가 사라졌는가 — 출력이 없어야 한다
grep -rn "userHeaders" src/
grep -rn "X-User-Id" src/

# 3) 개수를 흘리는 문구가 없는가 — 출력이 없어야 한다
grep -rnE "숨겨진|더 보|N건 더|비공개 [0-9]" src/

# 4) 관리자 진입점이 조건부인가
grep -rnE "is_admin|isAdmin" src/ | head

# 5) 눈으로 확인 — 이 step의 진짜 AC다
cd .. && docker compose up -d
(cd backend && uvicorn app.main:app --port 8000 &)
(cd frontend && npm run dev &)
#   → 브라우저에서:
#     · 익명으로 열었을 때 public만 보이고 업로드 버튼이 없는가
#     · 로그인 후 내 private이 보이는가
#     · 로그아웃하면 즉시 익명으로 돌아가는가
#     · 일반 사용자에게 사용자 관리가 안 보이는가
#     · DevTools에서 쿠키가 httponly인가 (JS로 못 읽는가)

# 6) 전체 검증
bash scripts/check.sh
```

## 검증 절차

1. 위 AC 커맨드를 실행하고 **브라우저에서 직접 확인한다.**
2. 아키텍처 체크리스트를 확인한다:
   - **`userHeaders()`가 완전히 사라졌는가?** 남으면 두 인증 경로가 공존한다
   - **쿠키가 JS에서 안 읽히는가?** DevTools 콘솔에서 `document.cookie`로 확인한다
   - **익명 화면이 개수를 흘리지 않는가?**
   - **없는 기능(가입·비밀번호 찾기)을 만들지 않았는가?**
   - **인접 컴포넌트를 "개선"하지 않았는가?** (`CLAUDE.md`)
3. 결과에 따라 `phases/m8-auth-diagnostics/index.json`의 step 4를 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- **가입·비밀번호 찾기·소셜 로그인 화면을 만들지 마라.** 이유: 없는 기능이다.
  계정은 관리자만 만든다 (#37)
- **토큰을 localStorage에 넣지 마라.** 이유: httponly 쿠키를 고른 이유가 그것이다
- **"로그인하면 N건 더" 같은 안내를 넣지 마라.** 이유: 개수가 새는 것 자체가 위반이다 (ADR-027)
- **백엔드를 고치지 마라.** 이유: step 2·3에서 끝났다. 모자라면 `summary`에 적는다
- **인접 컴포넌트를 리팩터링하지 마라.** 이유: `CLAUDE.md` 외과적 변경
