# Step 4: rrf-frontend

## 배경 — 검색이 나아진 것이 보여야 한다

step 3이 랭킹을 바꿨다. **화면이 그대로면 아무도 모른다.** #29가 이 기능을 고른 이유 중
하나가 *"검색 품질 차이로 화면에 바로 보인다"*였다.

> ⏭ **step 3이 "미채택"으로 끝났으면 이 step은 없다.** index.json에 사유를 적고
> step 5로 간다 — 융합이 나아지지 않았는데 화면에 자랑하면 거짓말이 된다.

## 읽어야 할 파일

- `docs/UI_GUIDE.md` — 화면 규칙
- `frontend/src/app/search/` — 검색 결과 화면. m7 step 9가 관계 표시를 이미 얹었다
- `backend/app/api/schemas.py` — step 3이 더한 필드
- `docs/ADR.md` **ADR-015** — 사용자 대상 문구 규칙

## 작업

### 1) 무엇을 보일지 정한다

**점수를 보이는 것은 답이 아니다.** RRF 점수는 사용자에게 의미가 없는 숫자다.

보일 값어치가 있는 것:

- **매칭 근거** — 이 결과가 *단어가 일치해서* 나왔는지, *의미가 비슷해서* 나왔는지, 둘 다인지
- **스니펫에서 질의어 강조** — 키워드 경로가 잡은 것이 눈에 보이는 가장 싼 방법이다

> **근거 표시는 두 랭킹 중 어디에 들었는지로 충분하다.** 순위 숫자나 융합 점수를
> 노출하지 마라 — 설명할 수 없는 숫자는 신뢰를 깎는다.

### 2) 스니펫 강조

- 질의어가 본문에 그대로 있으면 강조한다
- **`pg_trgm`은 부분 일치라 정확히 같은 문자열이 아닐 수 있다** — 없으면 강조하지 않는다.
  억지로 맞추지 마라
- **주입을 조심하라** — 본문은 외부 입력이다. 기존 렌더의 이스케이프 방식을 그대로 쓴다

### 3) 문구

- **"AI 검색"·"똑똑한 검색" 같은 표현을 쓰지 마라** — 무엇이 일어나는지 말하지 않는다
- **"항상 최신"·"실시간"을 쓰지 마라** (ADR-015)
- 근거 표시는 짧게. 배지 하나면 충분하다

### 4) 테스트

- 근거 배지가 렌더되는가
- 질의어가 스니펫에 없을 때 강조가 깨지지 않는가
- 관계 확장 표시(m7 step 9)와 **겹쳐서 어수선해지지 않는가** — 한 결과 카드에
  근거 배지와 도달 경로가 함께 붙는다

## Acceptance Criteria

```bash
cd frontend

# 1) 타입·린트·테스트
npm run lint && npm run build && npm test

# 2) 점수를 노출하지 않는가 — 출력이 없어야 한다
grep -rnE "rrf|RRF.*score|융합 점수" src/

# 3) 금지 문구가 없는가 — 출력이 없어야 한다
grep -rnE "AI 검색|똑똑한|항상 최신|실시간" src/

# 4) 이스케이프를 새로 만들지 않았는가 — 기존 방식을 쓰는지 눈으로 확인
grep -rnE "dangerouslySetInnerHTML" src/

# 5) 눈으로 확인 — 이 step의 진짜 AC다
cd .. && docker compose up -d
(cd backend && uvicorn app.main:app --port 8000 &)
(cd backend && python -m app.worker &)
(cd frontend && npm run dev &)
#   → 브라우저에서 질의 셋을 비교한다:
#     · 정확한 단어 ("OpenProxy") — 키워드 근거가 붙는가
#     · 의미 질의 ("문서가 바뀌면 어떻게 되나") — 의미 근거가 붙는가
#     · 조사가 붙은 단어 ("정합성은") — 결과가 나오는가
#     · 카드에 근거 배지 + 관계 도달 경로가 함께 있어도 읽히는가

# 6) 전체 검증
bash scripts/check.sh
```

## 검증 절차

1. **step 3의 결과를 먼저 확인한다.** "미채택"이면 이 step을 건너뛴다.
2. 위 AC 커맨드를 실행하고 **브라우저에서 세 질의를 직접 비교한다.**
3. 아키텍처 체크리스트를 확인한다:
   - **조사가 붙은 질의가 실제로 잡히는가?** 이것이 `pg_trgm`을 고른 이유다.
     안 잡히면 step 3을 다시 봐야 한다
   - **점수를 노출하지 않는가?**
   - **카드가 어수선하지 않은가?** 배지가 셋 넘게 붙으면 줄여라
   - **이스케이프를 새로 만들지 않았는가?**
4. 결과에 따라 `phases/m9-wikilink-rrf/index.json`의 step 4를 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - step 3 미채택으로 생략 → `"status": "completed"`, `"summary": "생략 — 사유"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- **RRF 점수나 순위 숫자를 노출하지 마라.** 이유: 설명할 수 없는 숫자는 신뢰를 깎는다
- **"AI 검색"·"똑똑한 검색"을 쓰지 마라.** 이유: 무엇이 일어나는지 말하지 않는다
- **"항상 최신"·"실시간"을 쓰지 마라.** 이유: ADR-015
- **강조를 억지로 맞추지 마라.** 이유: `pg_trgm`은 부분 일치다. 없으면 강조하지 않는다
- **본문 이스케이프 방식을 새로 만들지 마라.** 이유: 외부 입력이다
- **백엔드를 고치지 마라.** 이유: step 3에서 끝났다
