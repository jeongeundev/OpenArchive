# Step 2: adr-zip

## 배경 — 새 의존성 하나와, 그것을 브라우저에 둔 이유를 기록한다

앞의 두 step이 ZIP 업로드를 완성했다. 이 step은 **코드를 한 줄도 고치지 않고** 두 가지를
기록한다.

1. **결정** — ZIP을 서버가 아니라 브라우저에서 푼 이유. 이것은 ADR-017(원본 파일을 보관하지
   않는다)에서 따라 나온 결과이며, 아카이브를 서버가 받지 않기로 한 판단이다
2. **의존성** — JSZip이 이 프로젝트의 네 번째 프론트엔드 런타임 의존성이 됐다. 대회 규정상
   오픈소스 출처와 라이선스가 심사 대상이므로 기술 스택 표에 드러나야 한다

## ✅ 이미 닫힌 결정 — 다시 판단하지 말고 아래대로 진행하라

### 결정 1 — ADR 번호는 **033**이다

`docs/ADR.md`에서 032 다음이 034이며 **033이 비어 있다.** 이 자리가 ZIP 업로드에 예약되어
있었다. 파일 안의 번호 순서(032 → 033 → 034)에 맞는 위치에 삽입하라 — 끝에 붙이지 마라.

### 결정 2 — SBOM 파일을 만들지 않는다

`README.md`가 "의존하는 오픈소스의 출처와 라이선스는 SBOM으로 함께 공개합니다"라고 적고 있지만
**SBOM 파일은 아직 존재하지 않는다.** 그것은 제출 트랙(이슈 #10 — 영상·서류 3종)의 몫이다.
이 step에서는 **기술 스택 표에 JSZip을 추가**하는 것까지만 한다. 새 SBOM 파일을 만들지 마라.

### 결정 3 — ROADMAP의 커넥터·수집함 항목은 건드리지 않는다

"지식 수집함(검토 상태 기계)"과 "외부 커넥터"는 이 최소형에서 의도적으로 제외되어 ROADMAP에
착지한 항목이다. ZIP이 구현됐다고 해서 그것들의 상태가 바뀌지 않는다.

- `docs/UI_GUIDE.md` — 업로드 화면 관련 서술이 있으면 현재 동작과 맞추기 위해

## 작업

### 1) `docs/ADR.md`에 **ADR-033**을 추가한다

032와 034 사이에 기존 형식(`### ADR-033: 제목` / `**상태**:` / `**결정**` / `**이유**` /
`**트레이드오프**`)으로 쓴다. 담을 것:

- **결정** — ZIP은 브라우저에서 JSZip으로 풀고, 나온 문서를 기존 단건
  `POST /api/documents`로 투입한다. 서버 API·스키마 변경은 0이다
- **이유** — ADR-017에서 따라 나온다. 원본 파일을 보관하지 않는 제품이 아카이브를 서버로
  받으면 zip bomb·경로 탈출(`../`)·파일명 인코딩을 서버가 떠안는다. 브라우저에서 풀면 서버로
  나가는 것은 지금과 똑같이 개별 문서뿐이다
- **필터 규칙과 그 근거** — 지원 확장자 외 항목은 "건너뜀"으로 **보여주고**,
  `__MACOSX`·숨김 파일은 목록에서 **아예 뺀다**. 두 처리가 다른 이유(사용자가 만든 적 없는
  항목이 건너뜀 목록을 채우면 진짜 이유가 묻힌다)를 적어라
- **중첩 ZIP을 풀지 않는다** — 재귀 해제의 깊이 제한·순환 판단을 도입하지 않는다
- **의존성** — JSZip 버전과 MIT 라이선스

트레이드오프에 남길 것: 해제가 사용자 브라우저의 메모리에서 일어나므로 아주 큰 아카이브는
탭의 자원에 걸린다는 것, 그리고 서버에는 배치라는 개념이 없어 **부분 실패가 배치 단위로
롤백되지 않는다**는 것(파일별 상태 행이 그 대신이다).

### 2) `README.md`의 기술 스택 표에 JSZip을 추가한다

프론트엔드 행에 더하거나 별도 행을 만든다. 기존 항목들처럼 **라이선스를 함께 적어라**
(예: `BAAI/bge-m3` 행이 `(MIT, 1024차원)`으로 적혀 있다). 링크는 기존 항목의 방식을 따른다.

라이선스 절(:308)의 SBOM 문장은 **그대로 둔다** (결정 2).

### 3) `docs/ROADMAP.md`에서 대량 투입 관련 항목을 갱신한다

"다중 파일·ZIP 업로드"가 2차 후보나 미구현으로 적혀 있으면 현재 상태로 옮긴다.
**수집함·커넥터 항목은 그대로 둔다** (결정 3). 해당 서술이 없으면 아무것도 추가하지 마라 —
없는 자리를 만들어 채우지 않는다.

### 4) 화면 동작이 문서와 어긋나는 곳을 맞춘다

`docs/UI_GUIDE.md`나 `README.md`에 업로드 화면 설명이 있고 그것이 ZIP을 받지 못한다고 읽히면
현재 동작에 맞춘다. **없으면 만들지 마라.**

## Acceptance Criteria

```bash
# 1) 코드는 한 줄도 바뀌지 않았다 — 이 step은 문서 전용이다
git diff --stat HEAD -- backend/ frontend/ examples/ scripts/
#   → 출력이 비어 있어야 한다

# 2) ADR-033이 존재하고 번호 순서에 맞는 자리에 있다
grep -n "^### ADR-03[2-4]" docs/ADR.md
#   → 032 → 033 → 034 순서로 출력되어야 한다

# 3) 문서에 적은 JSZip 버전이 실제 설치본과 같은지 눈으로 대조한다
grep -n "jszip" frontend/package.json
grep -in "jszip" README.md docs/ADR.md
#   → 두 출력의 버전이 일치해야 한다

# 4) SBOM 파일을 새로 만들지 않았다 (결정 2)
git status --porcelain | grep -ic sbom
#   → 0이어야 한다. grep을 그냥 파이프하면 "일치 없음"이 exit 1이라 실패로 오해된다.

# 5) 전체 검증 (문서만 고쳤으므로 통과해야 한다)
bash scripts/check.sh
#   → 마지막 줄에 "검증 실패"가 없어야 한다
```

## 검증 절차

1. 위 AC 커맨드를 순서대로 실행한다.
2. **문서를 직접 다시 읽으며 확인한다** (grep으로 대신하지 마라):
   - ADR-033의 필터 규칙 서술이 `zip.ts`의 실제 동작과 일치하는가? 추측으로 쓰지 않았는가?
   - ADR-017·ADR-031의 기존 서술을 지우지 않았는가?
   - ROADMAP의 수집함·커넥터 항목이 그대로인가? (결정 3)
   - 사용자 대상 문구에 "항상 최신"·"실시간 동기화"가 새로 들어가지 않았는가?
3. 결과에 따라 `phases/m10-zip-ingest/index.json`의 step 2를 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- **코드를 고치지 마라.** 이유: 문서가 구현과 어긋나면 그것은 문서가 틀렸거나 앞 step의
  결함이다. 후자라면 `blocked`로 중단하고 사유를 적어라 — 코드 변경이 `docs(adr)` 커밋에
  섞이면 리뷰에서 보이지 않는다.
- **SBOM 파일을 만들지 마라.** 이유: 결정 2. 제출 트랙(#10)의 몫이다.
- **ADR-036 번호를 쓰지 마라.** 이유: 다른 작업(MCP 쓰기 도구)에 배정되어 있다.
- **기존 ADR의 결정문·이유·트레이드오프를 지우지 마라.** 이유: ADR은 append 이력이다.
  규칙 문서의 금지어 **원문을 지워 검사를 통과시키는 일**이 이 프로젝트에서 실제로 있었다.
- **ROADMAP에 새 확장 후보를 추가하지 마라.** 이유: 이 step은 구현된 것을 기록할 뿐이다.
- **`CLAUDE.md`를 고치지 마라.** 이유: ADR이 정본이며, 규칙 승격은 사용자가 판단한다.
- **기존 테스트를 깨뜨리지 마라.**
