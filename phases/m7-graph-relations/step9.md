# Step 9: frontend-relations

## 배경 — phase가 끝날 때 단독 시연이 성립해야 한다

#32가 phase를 자르는 기준을 정했다 — **"phase가 끝날 때마다 단독 시연이 성립하는가."**
계층별(DB→API→프론트)로 자르면 마지막까지 가야 보이는 것이 생겨 뒤를 통째로 버릴 수 없다.

step 8까지는 **API 응답에만** 관계가 있다. 이 step이 그것을 화면에 올려 m7을 닫는다.
m8·m9가 잘려도 **여기까지가 완결된 시연**이어야 한다.

## 읽어야 할 파일

- `docs/UI_GUIDE.md` — **UI 규칙 전부.** 새 표현을 만들기 전에 여기 있는 어휘를 먼저 쓴다
- `frontend/src/app/search/` · `frontend/src/app/documents/` — 지금 검색 결과와 문서 상세가
  그려지는 자리. **기존 스타일에 맞춘다** (`CLAUDE.md`: 다르게 했을지라도 기존 스타일을 따른다)
- `backend/app/schemas.py` — step 7·8이 더한 `kind`·`via` 필드의 실제 이름과 타입
- `docs/ADR.md` **ADR-027** — 화면에도 그대로 적용된다. **`🔒` 같은 자리를 만들지 마라**
- `docs/ADR.md` **ADR-015** — 사용자 대상 문구 규칙

## 작업

### 1) 관계 종류의 사용자 어휘를 정한다

`overlaps`·`points_to`·`broader`를 그대로 노출하지 마라. **화면에 쓸 한국어 이름**을 정하고
`docs/UI_GUIDE.md`에 표로 남긴다 — 다음 화면(m8의 진단 목록·덩어리 그래프)이 같은 말을 쓴다.

| 저장값 | 화면 표현(예시 — 확정은 이 step이 한다) |
|---|---|
| `overlaps` | 전반적으로 같은 내용 |
| `points_to` | 이 대목에서 만난다 |
| `broader` | 더 포괄적인 문서 / 더 자세한 문서 (방향에 따라) |
| `related` | 관련 있음 |

> **`broader`는 방향이 의미다.** 내가 `src`면 상대가 상세, 내가 `dst`면 상대가 포괄이다.
> 한 이름으로 뭉치면 방향을 저장한 의미가 사라진다.

### 2) 검색 결과에 확장을 표시한다

- **직접 매칭과 확장 결과를 눈으로 구분**할 수 있어야 한다. 확장 결과에는
  *"문서 A에서 「이 대목에서 만난다」로 이어짐"*처럼 **어떻게 도달했는지**를 적는다
- **직접 매칭이 위**다 (step 8이 이미 그 순서로 준다)
- 확장이 없는 질의에서는 **아무것도 늘지 않아야 한다** — 빈 영역이나 "확장 결과 없음"
  같은 자리를 만들지 마라

### 3) 문서 상세의 관련 문서를 종류별로 묶는다

지금은 점수순 평면 목록이다. **`kind`로 묶고 그룹 안에서 정렬**한다.

- **점수를 종류 사이에 걸쳐 비교하지 마라** — `score`의 척도가 `kind`마다 다르다(ADR-029)
- `reason`을 문구로 구분한다

| `reason` | 문구 방향 |
|---|---|
| `not_indexed` | 아직 처리 중임을 알린다 (기존 문구 유지) |
| `no_edges` | **처리는 끝났고 관련 문서가 없다** |
| `null` | 정상 목록 |

> **두 문구를 같게 쓰지 마라.** *"아직 처리 중"*과 *"관련 없음"*은 사용자에게 전혀 다른 말이다.
> step 7이 두 상태를 갈라 둔 이유가 이것이다.

### 4) 문구 규칙을 지킨다

- **"항상 최신"·"실시간 동기화"를 쓰지 마라.** 보장 범위는 **버전 일관성 + 최신 수렴**이다
  (ADR-015)
- **관계는 "추천"이지 "사실"이 아니다** — `broader` 판정은 어휘 겹침 기반의 추정이다.
  단정하는 문구를 피한다
- **`🔒`·"권한 없는 문서 N건"·"비공개 3건 숨김" 같은 표시를 만들지 마라.** 표시 자체가
  존재와 개수를 누출한다 (ADR-027 결정 2)

### 5) 테스트

`frontend/`의 기존 테스트 방식에 맞춘다.

- 종류별 그룹이 렌더되는가
- `no_edges`와 `not_indexed`가 **다른 문구**로 렌더되는가
- 확장 결과에 도달 경로가 표시되는가
- 확장이 없을 때 빈 영역이 생기지 않는가

## Acceptance Criteria

cd frontend

grep -rn "not_indexed" src/ | head

# 3) 금지 문구가 없는가 — 출력이 없어야 한다

(cd frontend && npm run dev &)

## 검증 절차

1. 위 AC 커맨드를 실행하고 **브라우저에서 직접 확인한다.** 이 step은 화면이 산출물이라
   테스트 통과만으로 끝나지 않는다.
2. 아키텍처 체크리스트를 확인한다:
   - **`broader`의 방향이 화면에서 갈리는가?** 한 이름으로 뭉쳤으면 저장한 방향이 죽는다
   - **종류를 넘나드는 점수 비교가 없는가?** 척도가 다르다
   - **익명으로 열었을 때 private의 흔적이 없는가?** 개수·자리·회색 항목 어느 것도 안 된다
   - **확장이 없는 질의에서 화면이 그대로인가?** 빈 영역이 생기면 검색이 나빠져 보인다
   - **m7만으로 시연이 성립하는가?** 이 질문에 "아니오"면 phase 경계가 잘못된 것이다 —
     무엇이 부족한지 `summary`에 적어라
3. 결과에 따라 `phases/m7-graph-relations/index.json`의 step 9를 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- **`🔒`나 숨김 개수 표시를 만들지 마라.** 이유: ADR-027 결정 2. 표시 자체가 정보다
- **"항상 최신"·"실시간 동기화"를 쓰지 마라.** 이유: ADR-015
- **저장값(`overlaps` 등)을 화면에 그대로 노출하지 마라.** 이유: 사용자 어휘가 아니다
- **종류를 섞어 점수순으로 한 줄에 세우지 마라.** 이유: `score`의 척도가 `kind`마다 다르다
- **문서 단위 그래프 시각화를 만들지 마라.** 이유: #29가 기각했다(노드=문서면 헤어볼이 된다).
  주제 덩어리 그래프는 **m8**이다
- **백엔드를 고치지 마라.** 이유: 이 step은 화면이다. API가 모자라면 그 사실을
  `summary`에 적고 m8로 넘긴다
- **인접 컴포넌트를 "개선"하지 마라.** 이유: 변경된 모든 줄이 이 step의 요청으로
  추적되어야 한다 (`CLAUDE.md`)
